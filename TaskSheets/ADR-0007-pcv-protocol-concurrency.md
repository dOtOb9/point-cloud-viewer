# ADR-0007: `pcv://` 並行リクエストの直列化を直す

- 状態: 採択（**追記あり: 末尾の「頭打ちの正体は『1ノードあたりの読み出しコスト』だった」を
  必ず読むこと。並行化そのものではなく`read_node`の実装が真因だった**）
- 日付: 2026-09-22
- 前提: [ADR-0001](./ADR-0001-architecture.md)、[M1-point-rendering.md](./M1-point-rendering.md)
  の「追記: 原因の候補を特定した」、[ADR-0003](./ADR-0003-copc-crate.md) の実測値

## 決定

`src-tauri` の `pcv://` ハンドラを `register_uri_scheme_protocol`（同期版）から
`register_asynchronous_uri_scheme_protocol` に切り替え、ノード読み出し（ディスクI/O +
LAZ伸長 + 詰め替え）を `tauri::async_runtime::spawn_blocking` でブロッキング用スレッド
プールに逃がす。あわせて `CopcState` の中身を「`CopcFile` を1個`Mutex`で共有」から
「独立した`CopcFile`を8個プールする（`CopcPool`）」に変える。**この2つはセットでないと
効果が無い**（帰結節を参照）。

## 背景

### 直す前に測った（仮説の検証）

M1-point-rendering.md は「同期ハンドラはRustのメインスレッドで実行されるため、ノード
読み出しが直列化する」という仮説を立てていた。ADR-0003はルートノード1つの読み出しに
20〜28msかかることを実測しており、これが本当なら毎秒50ノード程度が構造的上限になる。
だが「メインスレッドで直列化する」こと自体は当時まだ実測されていなかった。

まず `crates/pcv-core/examples/open_bench.rs` を拡張し、点予算を埋めるまでの逐次読み出し
コストを測った（`pcv-core`単体、`cargo run --release`）。

| | autzen-classified.copc.laz | sofi.copc.laz |
|---|---|---|
| 総点数 | 10,653,336 | 364,384,576 |
| hierarchyノード | 278 | 13,163 |
| 開く時間 | 0.4 ms | 16.0 ms |
| 点予算3Mを埋めるまで読んだノード数 | 91 | 140 |
| 同・所要時間 | 6.29 秒 | 8.40 秒 |
| 同・最も遅い1ノード | 146.4 ms | 125.0 ms |
| **ノード/秒** | **14.5** | **16.7** |
| 点/秒 | 482,984 | 362,231 |
| MiB/秒 | 9.2 | 6.9 |

この開発機（20論理コア）でもADR-0003と同オーダーの値が出た。ノード1つが数十〜百数十ms
かかるCPU律速の処理であることを確認した。

次に、`pcv://`経由の**並行**リクエストのスループットを測った。M0-3
（`src/state/useIpcBench.ts`）と同じ考え方で計測ハーネス
（`src/state/useNodeConcurrencyBench.ts`）を追加し、`report_diagnostic`経由でRust側
stdoutに結果を出す。並行数1・4・8のそれぞれについて、**互いに重ならない64ノードの集合**
を読ませて所要時間を測る（同じノードを2回目以降に読むとOSのページキャッシュが効いて
速くなり、「並行数を上げたから」なのか「2回目だから」なのか区別できなくなるため、
levelの浅い順の一覧を並行数で割った剰余で振り分け、各集合が同じくらいの深さの混在に
なるようにした）。計測は `npm run tauri dev --release --no-watch`（リリースビルド、
ファイル監視オフ）で行った。

**改修前**（`register_uri_scheme_protocol`、`CopcState`は`Mutex<Option<CopcFile>>`）
autzen-classified.copc.laz、64ノード/ラウンド:

| 並行数 | 所要時間 | ノード/秒 | MiB/秒 |
|---|---|---|---|
| 1 | 8,993 ms | 7.1 | 5.5 |
| 4 | 5,677 ms | 11.3 | 9.1 |
| 8 | 5,568 ms | 11.5 | 8.9 |

`npm run tauri dev --release --no-watch` の実測行:

```
[frontend] [M2] pcv:// node concurrency bench (autzen-classified.copc.laz, 64 nodes/round, disjoint node sets per round): concurrency=1: 64nodes/8993ms = 7.1nodes/s 5.5MiB/s | concurrency=4: 64nodes/5677ms = 11.3nodes/s 9.1MiB/s | concurrency=8: 64nodes/5568ms = 11.5nodes/s 8.9MiB/s
```

**並行数4→8でほぼ頭打ちになっている。これが「直列化している」ことの数値上の証拠である。**

ただし1点、仮説を額面通りには裏付けなかった観測がある。**並行数1→4では11.3/7.1≈1.6倍の
向上が見えている。** 完全に単一スレッドで直列化しているなら並行数を上げても速くならない
はずである。実際にはWebView2のfetchディスパッチやIPCのメッセージ処理など、CPU律速でない
オーバーヘッド部分には並行数を上げることで多少の重なりが生まれ、そこだけ速くなったと
考えられる。一方でLAZ伸長そのもの（CPU律速の本体）は`CopcState`のロックを読み出し中
ずっと持つ実装だったため直列のままで、並行数4→8で頭打ちになる形で現れている。
**「Rustのメインスレッドで直列化する」という当初の説明は正確ではなかったが、
「並行数を上げてもスループットが頭打ちになる」という結論自体は実測で裏付けられた。**

### `read_node`の`&mut self`という制約

`CopcFile::read_node`は`&mut self`を取る（`copc-reader`が内部のシーク位置を進めながら
読むため、共有参照では呼べない）。非同期ハンドラに切り替えるだけでは、`CopcState`が
`Mutex<Option<CopcFile>>`のままである限り、結局「1本のreaderを複数スレッドが奪い合う」
形になり、ロックを読み出し中ずっと持つ実装をつい書いてしまう。**非同期化と、
`&mut self`制約の解決はセットで考える必要がある。**

## 採った対処

1. `src-tauri/src/lib.rs`: `register_asynchronous_uri_scheme_protocol`に切り替え、
   ノード読み出しを`tauri::async_runtime::spawn_blocking`に包む。
2. `src-tauri/src/copc_state.rs`: `CopcState`の中身を`Mutex<Option<CopcFile>>`から
   `Mutex<Option<Arc<CopcPool>>>`に変える。`CopcPool`は同じファイルを独立に8回
   (`POOL_SIZE`) `CopcFile::open`し、専用の`File`ハンドルを持つ`CopcFile`をプールする。
   読み出しは`Condvar`でプールから1本借り、使い終わったら返す。`CopcState`のロックは
   `Arc`を複製する一瞬だけ持ち、実際のディスクI/O・LAZ伸長はロックの外で行う。

コードの詳しいコメントは`src-tauri/src/copc_state.rs`冒頭のモジュールドキュメントと
`CopcPool`の定義を参照（「賢いコードより退屈で読めるコードを」という方針に沿って、
プールの仕組み自体は`Vec`+`Mutex`+`Condvar`だけで書いてあり、外部クレートは増やしていない）。

`POOL_SIZE`は8に決め打ちした。この開発機の論理コア数20よりだいぶ少ないが、
`pcv://`の1リクエストはCPU律速（LAZ伸長）なので、コア数まで増やしてもディスクI/Oとの
兼ね合いで頭打ちになると考えた。実測で妥当性を確認した数値であり、変えるときは
本ADRと同じ方法で測り直すべき値としてコード側にもコメントを残した。

## 実測（直した後）

同じ方法・同じautzenファイルで測り直した。

| 並行数 | 所要時間 | ノード/秒 | MiB/秒 |
|---|---|---|---|
| 1 | 9,031 ms | 7.1 | 5.4 |
| 4 | 1,748 ms | 36.6 | 29.6 |
| 8 | 1,076 ms | 59.5 | 46.0 |

```
[frontend] [M2] pcv:// node concurrency bench (autzen-classified.copc.laz, 64 nodes/round, disjoint node sets per round): concurrency=1: 64nodes/9031ms = 7.1nodes/s 5.4MiB/s | concurrency=4: 64nodes/1748ms = 36.6nodes/s 29.6MiB/s | concurrency=8: 64nodes/1076ms = 59.5nodes/s 46.0MiB/s
```

並行数1のスループットは改修前とほぼ同じ（7.1 nodes/s、誤差の範囲）。これは想定通り
であり、**「並行時にだけ速くなった」ことは、キャッシュや測定条件の変化ではなく
並行実行そのものの効果であることを裏付ける**（並行数1では並行実行する余地が無いので、
プールを8個に増やしても1本しか使われない）。

並行数4・8では明確に伸び続けている。

- 並行数4: 改修前11.3 → 改修後36.6（**+224%**）
- 並行数8: 改修前11.5 → 改修後59.5（**+417%**）。改修前は4→8でほぼ頭打ちだったのに対し、
  改修後は4→8でも59.5/36.6≈1.6倍伸びている。**「並行数を上げるとスループットが上がる」
  という受け入れ条件を、直列化していた区間（並行数4→8）で満たしている。**

### `sofi.copc.laz`での確認

TEST-DATA.mdが「受け入れ判定」と位置づける本命ファイル（13,163ノード、2.03GB）でも
改修後の値を確認した（改修前のsofiでの計測は行っていない。理由は下記「時間の都合で
やらなかったこと」を参照。ノード1つあたりのコストがautzenと同オーダーであることは
上記のpcv-core単体計測で確認済みなので、改修の効果がファイルサイズに依存しないことの
傍証として十分と判断した）。

| 並行数 | 所要時間 | ノード/秒 | MiB/秒 |
|---|---|---|---|
| 1 | 7,239 ms | 8.8 | 3.9 |
| 4 | 1,213 ms | 52.7 | 22.8 |
| 8 | 728 ms | 88.0 | 38.1 |

```
[frontend] [M2] pcv:// node concurrency bench (sofi.copc.laz, 64 nodes/round, disjoint node sets per round): concurrency=1: 64nodes/7239ms = 8.8nodes/s 3.9MiB/s | concurrency=4: 64nodes/1213ms = 52.7nodes/s 22.8MiB/s | concurrency=8: 64nodes/728ms = 88.0nodes/s 38.1MiB/s
```

並行数8で並行数1の10.0倍。hierarchyが47倍大きいファイルでも、改修の効果は同じ形で
（むしろautzenよりよい比率で）出ている。

## 帰結

**得たもの**
- 並行数を上げるとスループットが上がることを実測で確認した（直列化の解消）。並行数8で
  改修前の4.2〜10倍のノード/秒が出ている。
- `sofi.copc.laz`（3.6億点、hierarchy 13,163ノード）でも改修の効果が同じ形で再現することを
  確認した。M1完了の定義が課した「これを先に潰す」条件を数値で満たした。
- 「Rustのメインスレッドで直列化する」という当初の仮説は、原因の説明としては不正確
  だったが、「直列化していてスループットが頭打ちになる」という現象自体は正しかった。
  実際の原因は「`CopcState`のロックを読み出し（LAZ伸長込み）の間じゅう持ち続けていた」
  ことであり、非同期ハンドラへの切り替えだけでは直らず、`CopcPool`によるロック粒度の
  見直しとセットで初めて効いた。**推測で「メインスレッドが原因」と決めつけて非同期化
  だけ行っていたら、効果が出ずに原因を見誤っていた可能性が高い。**
- `CopcFile::read_node`の`&mut self`制約への対処（同じファイルを独立に複数回開いて
  プールする）は、`pcv-core`のAPIを一切変更せずに済んだ。`pcv-core`は今回のADRの対象
  である並行化・スレッドプールを一切知らない（規約1: wasm32でビルドできる状態を維持）。

**払うもの**
- `CopcPool`はhierarchyのコピーを`POOL_SIZE`(8)個保持する。sofiで13,163ノード×8プール分
  なので数MB程度だが、`open_copc`のたびに同じファイルを8回開き直す分だけ、開く処理の
  所要時間は伸びる（1回あたり数〜16ms程度なので8回でも100ms未満。体感できるほどでは
  ないが、無視できるコストではないので明記する）。
- `POOL_SIZE`は決め打ちの定数であり、実行時にCPUコア数などから動的に決めていない。
  将来別の開発機やCI環境で挙動が変わる可能性はある。変えるときの計測手順は本ADRに
  残したので、次に触る人はゼロから測り直さずに済むはず。

**時間の都合でやらなかったこと（正直に書く）**
- sofiでの「改修前」計測はしていない。sofiは2.03GBあり、改修前・改修後・
  それぞれのリリースビルド待ち時間を含めると計測サイクルが長く、autzenで直列化の
  発生と解消を明確な数値で示せた時点で、sofiは「改修後の効果がファイルサイズに
  依存しないことの確認」に絞った。もし所有者がsofiでの改修前後の直接比較を必要と
  するなら、`src/state/useNodeConcurrencyBench.ts`の`BENCH_FILE`を`"sofi.copc.laz"`
  に変えて同じ手順で測れる（このADRの計測方法をそのまま再現できる）。
- GUI（実際のカメラ操作でのfps・見た目）は目視できない環境のため未検証。この改修は
  `pcv://`の配信層だけを変えており、`src/renderer`・LOD選択・レンダリングは触っていない
  ため、既存のM1受け入れ条件（描画点数・fps等）への影響は無いはずだが、所有者による
  目視確認が必要な項目として残す。

## 却下した案

| 案 | 却下理由 |
|---|---|
| 非同期ハンドラに切り替えるだけ（`CopcState`は`Mutex<CopcFile>`のまま） | 本ADRの計測方法そのもの。ロックを読み出し中ずっと持つ実装のままだと、非同期化してもディスクI/O・LAZ伸長は1本のreaderに直列化されたままで、効果が出ない（実際に最初この構成で書きかけ、`ADR`の「背景」節にある通りの推論で気づいて`CopcPool`に切り替えた） |
| `RwLock<CopcFile>` | `read_node`が`&mut self`を要求するので共有参照(`read()`)では呼べない。書き込みロック(`write()`)を使うなら`Mutex`と実質同じで、解決にならない |
| `CopcFile`を1個のまま、ノードを読むたびに新しい`CopcReader`を使い捨てで開く | ファイルを開き直すたびにヘッダとVLRを読み直すコストを払う。プールで使い回すほうが単純かつ安い（ADR-0003の実測で開く処理は1〜16ms程度あり、リクエストのたびに払うには大きすぎる） |
| `pcv-core`側に並行読み出し用のAPI（内部でロック・プール管理）を足す | `pcv-core`はTauriや非同期ランタイムを知らない（規約1）。並行化の実装はTauri固有の関心事であり、`src-tauri`に閉じ込めるほうが規約に沿う。`pcv-core`は「`CopcFile::open`を複数回呼べる」という素朴な性質だけを提供すれば足り、実際その性質だけで`CopcPool`は書けた |
| `POOL_SIZE`をCPUコア数から動的に決める | 「1リクエストがCPU律速なのでコア数まで増やしても頭打ちになる」という前提を検証していない状態で複雑さを足すことになる。まず固定値で効果を確認し、必要になったら測り直して動的化を検討する方が、実装を追える状態を保てる |

## 追記（2026-09-23）: 頭打ちの正体は「1ノードあたりの読み出しコスト」だった

**このADRが当初「並行数を上げればスループットが上がる」と結論したのは、
1ノードあたりの読み出しコストそのものを疑っていなかったからである。**
計測の対象の選び方に穴があった。

### 所有者の報告

`POOL_SIZE`を動的化し、フロントの同時リクエスト数もコア数に揃えた後も、
所有者から「早くなったかもしれないが、まだ遅い」という報告があった
（点群が精細になっていくのに時間がかかる）。

### webview / IPC の無実を実測で確認した

`crates/pcv-core/examples/parallel_bench.rs`を新設し、webviewもIPCも通さず
`CopcPool`と同じ構成（スレッドごとに独立した`CopcFile`を開く）で、
Rust側だけの上限を測った。

`sofi.copc.laz`、160ノード、20論理コア（**直す前**）:

| スレッド数 | ノード/秒 | 1コアあたり |
|---|---|---|
| 1 | 11.3 | 1.00x |
| 4 | 36.3 | 0.80x |
| 8 | 71.3 | 0.79x |
| 16 | 71.9 | 0.40x |
| 20 | 71.1 | 0.31x |

**8スレッドで完全に頭打ちで、16でも20でも増えない。** そして本ADR本文が
`pcv://`経由で測った**88 nodes/s**（並行数8）が、このRust単体の上限71と
ほぼ同じだった。**つまりwebviewの同時リクエスト制限もIPCも、ボトルネックでは
なかった。** 1ノードあたりの読み出しコスト（単スレッドで88ms）そのものが
問題だった。

### 真の原因: 1ノードを読むのに、そのレベル全体への空間クエリを投げていた

`crates/pcv-core/src/copc.rs`の`read_node`（直す前）は、`copc-reader`の
`points(LodSelection::Level(key.level), BoundsSelection::Within(bounds))`を
呼んでいた。これは「そのレベル全体」を対象に、ノードのbboxで絞り込むという
汎用の空間クエリである。**bboxが交差する全ノードのLAZチャンクを伸長してから、
自分のノードに属さない点を`point_belongs_to_key`というフィルタで大半捨てて
いた。** 深いレベルほど交差するノードが増えるので、コストが膨らむ。

COPCのhierarchy entryは、ノード1つぶんの点データがファイルの**どこから
どこまで連続したLAZチャンクとして書かれているか**を`offset`/`byte_size`として
直接持っている（`copc-core-0.9.0/src/hierarchy.rs`の`Entry`）。**本来はここへ
直接seekして、そのチャンクだけを伸長すべきだった。**

また、`TaskSheets/ADR-0003-copc-crate.md`に記録されているM1-1のバグ
（「1ノードだけ読み出すと隣接ノードの点が1点混入する」）も**同じ根**である。
`point_belongs_to_key`というフィルタ自体が、間違った読み方への対症療法
だった。直接読みにすればこのフィルタは不要になった。

### 対処

`vendor/copc-reader`（hierarchy offsetの件で既にベンダリング済み）に
`CopcReader::read_node(key: VoxelKey) -> Result<Vec<Point>>`を追加した
（詳細は`vendor/copc-reader/PATCH.md`）。`Entry::offset`/`byte_size`へ直接
seekし、そのノード自身のLAZチャンクだけを伸長する。空間クエリもbboxによる
絞り込みも行わない。読んだ点は無条件に全てそのノードに属する（COPCの構造上、
1チャンク＝1ノードとして書かれているため）。

`pcv-core`の`read_node`をこれを使う形に変え、`point_belongs_to_key`と
それを使っていたコードは削除した。

### 実測（直した後）

同じ`parallel_bench`、同じ`sofi.copc.laz`、同じ開発機（20論理コア）で
測り直した。

| スレッド数 | ノード/秒 | MiB/秒 | 1コアあたり |
|---|---|---|---|
| 1 | 114.6 | 47.8 | 1.00x |
| 2 | 221.9 | 92.6 | 0.97x |
| 4 | 428.7 | 178.9 | 0.94x |
| 8 | 668.2〜694.5 | 278.8〜289.8 | 0.73〜0.76x |
| 16 | 957.0〜1008.0 | 399.3〜420.6 | 0.52〜0.55x |
| 20 | 1025.4〜1123.6 | 427.9〜468.8 | 0.46〜0.49x |
| 24 | 1146.1 | 478.2 | 0.42x |
| 32 | 1033.6 | 431.3 | 0.28x |
| 40 | 1053.1 | 439.4 | 0.23x |

（20・24スレッドは複数回実行し、幅を記載した。他は1回のみ実行。）

**1ノードあたりの時間**: 直す前は単スレッドで1000/11.3 ≈ 88ms。直した後は
1000/114.6 ≈ 8.7ms。**約10分の1になった。**

**頭打ちの位置**: 直す前は8スレッドで完全に頭打ち（16・20でむしろ横ばい〜
微減）。直した後は**8スレッドの頭打ちが消え、論理コア数（20）まで素直に
スループットが伸びる**。論理コア数を超えて24〜40まで振ると、24でわずかに
伸びた後32・40では頭打ちになった（1030〜1150 nodes/sの範囲で横ばい）。
つまり**論理コア数が「これ以上増やしても本質的には伸びない」境目に
ほぼ一致する**。

### この直しで得られた教訓

**当初「並行数を上げればスループットが上がる」と結論したとき、1ノードあたりの
読み出しコスト自体を検証していなかった。** 並行数1→4→8でスループットが
伸びるのを見て「並行化が効いている」と判断したが、それ自体は事実として
正しかった一方、**「8で頭打ちになるのが構造的な上限なのか、たまたま
プールサイズやロック粒度の問題なのかを、1ノードあたりのコストを疑うことで
切り分けていなかった**。今回`parallel_bench`でwebview/IPCを完全に外して
測ったことで初めて、「並行数を上げても8で頭打ち」という現象が
「並行化の実装が悪い」のではなく「1回の読み出しが遅すぎる」ことに
起因すると分かった。**計測の対象の選び方（並行数だけを振り、1リクエストの
コスト自体は疑わなかったこと）に穴があった。**

### 追加実測: 逐次読み（初回の点予算充填）の前後比較

上の`parallel_bench`は「並列化の上限」を測るために、レベルの浅い順に160ノードを
読む。一方、**利用者が実際に最初に待つのは「点予算3Mを埋めるまで」の時間**なので、
`open_bench`（単スレッド）でも前後を比べた。前の値はこのADRの冒頭の表、
後の値は直した後に測り直したもの。

| | autzen 前 | autzen 後 | sofi 前 | sofi 後 |
|---|---|---|---|---|
| 点予算3Mを埋めるまでのノード数 | 91 | 91 | 140 | 140 |
| 同・所要時間 | 6.29 秒 | **1.21 秒** | 8.40 秒 | **1.22 秒** |
| ノード/秒 | 14.5 | **75.4** | 16.7 | **115.1** |
| 最も遅い1ノード | 146.4 ms | **26.5 ms** | 125.0 ms | **20.1 ms** |

**単スレッドだけで 5.2〜6.9倍**になった。`parallel_bench`で見えた「約10分の1」
との差は、読むノード集合が違うためである。`open_bench`は点予算を埋める浅い
ノードを読み、`parallel_bench`はレベル順に深いノードまで読む。直す前の実装は
**レベルが深いほど交差ノードが増えて遅くなる**ので、深い集合ほど改善幅が大きい。
所有者の「点群が精細になっていくのに時間がかかる」という報告はまさに深い
レベルの話なので、体感の改善はこの大きい側に効くはずである。

この単スレッドの改善に、8スレッド頭打ちの解消（20スレッドまで素直に伸びる）が
掛かる。

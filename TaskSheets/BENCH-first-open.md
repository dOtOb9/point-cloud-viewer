# BENCH: 初めて開くときの時間とメモリ（PF-0）

- 日付: 2026-11-16（作業エージェント、PF-0）
- 目的: [PF-first-open.md](./PF-first-open.md) の AC-1・AC-2。「ファイルを選んでから最初の点が見えるまで」と「全部見えるまで」を測る
- コードは変えていない。変換の example `crates/pcv-convert/examples/convert_timings.rs`（本番の `convert_and_timings` を呼び、段階別の時間と読み込みの経過を出す）だけ足した

## 環境と測り方

- 機械: i5-14600K、RAM 31.8 GiB、NVMe SSD（BENCH-conversion-profile と同じ機械）。測定時の C: の空き 約 279 GB
- 時間を測るプロセスは**すべて P コアに固定**（`ProcessorAffinity = 0xFFF`）。Web は node（Playwright）を固定してから Chromium を起こし、子の Chromium が継承した（`Get-Process` の ProcessorAffinity が 4095 であることを実行ごとに確認）
- ピークメモリは **private**（`PrivateMemorySize64`）。ネイティブは 0.2 秒ごと、Web は Chromium の全プロセス（ブラウザ・GPU・renderer・Worker）の private の合計を 0.5 秒ごと（別の PowerShell を E コアに固定して取る）
- Web: `GITHUB_PAGES_BUILD=true npm run build` → `vite preview --port 5311`、画面ありの Chromium（Playwright 同梱）に `--enable-unsafe-webgpu` と HANDOFF の 3 つのフラグ。
  `adapter.info` は `vendor: nvidia, architecture: lovelace, isFallbackAdapter: false`（SwiftShader ではない。実行ごとに確認し、違えば中止する作り）
- Web の時刻: ページ内の `performance.now()`。ファイルを渡す直前を 0 とする（数 ms の誤差）。次の印を renderer にかぶせて取った（`?pcvDebug` の `window.__pcvRenderer` に、setter でインスタンスのメソッドを差し替える）:
  - `addLayer` が呼ばれた時刻（ファイルが開けた）
  - 最初のノードの `readNode` が返った時刻と所要 ms
  - 最初の `handleNodeLoaded`（パースと GPU への転送）の所要 ms
  - 最初に `drawnPoints > 0` になった統計の時刻（**統計は 500 ms ごとにしか出ない**ので、この時刻は最大 0.5 秒遅れて見える。最初のノードが来た時刻のほうが真に近い）
  - 「全部見えた」= `drawnPoints>0 && loading==0 && queued==0` が 2 回続いた最初の統計
- 変換の「全部見える」は、変換が終わって `[M1] opened` が出たあと
- 測り方のスクリプトはリポジトリの外（`C:\pcv-bench-pf0\scripts`、消した後は残らない）。再現の骨組みは上の説明のとおり

## 結果1: COPC をそのまま開く（AC-1 の COPC 行）

### デスクトップと同じ Rust（`pcv-core/examples/open_bench`、点予算 300 万点、3 回）

`open_bench` はヘッダーと階層を読む時間と、点予算を埋めるまでノードを**直列に**読む時間を測る（GPU は含まない）。プロセス全体の private ピークは 9〜22 MiB。

| ファイル | 点数 | 階層のノード数 | 開く（ヘッダー＋階層） | 300 万点を埋めるまで（直列・1 スレッド） |
|---|---|---|---|---|
| autzen-classified.copc.laz | 10,653,336 | 278 | 26.6〜29.5 ms | 91 ノード、1.19〜1.21 秒 |
| sofi.copc.laz | 364,384,576 | 13,163 | 5.9〜13.7 ms | 140 ノード、1.24〜1.30 秒 |
| tokyo-shibuya-merged-v2.copc.laz | 347,797,138 | 6,462 | 50.4〜55.2 ms | 31 ノード、1.43〜1.47 秒 |

3 回の差が小さいので、ファイルはキャッシュに乗っていたと思われる（OS のキャッシュを落とした測定はしていない）。
アプリは `pcv://` を複数スレッドで呼ぶ（ADR-0007）ので、実際の「300 万点が揃うまで」はこれより短いはず（未測定）。

### Web（実 GPU の Chromium、ローカルファイルを開くボタンから）

ファイルを渡してからの秒数。autzen は 3 回、shibuya は 2 回、sofi は 1 回。

| ファイル | 開けた（addLayer） | 最初のノードを GPU に載せた | 最初の描画（統計・500ms 粒度） | 全部見えた | 全部見えた時の描画点数 | ブラウザ全体の private ピーク |
|---|---|---|---|---|---|---|
| autzen COPC | 0.113〜0.129 | 0.177〜0.183 | 0.205〜0.574 | 0.722〜1.075 | 790,853（25 ノード） | 522 MiB |
| shibuya-merged COPC（4.2 GB） | 0.174〜0.182 | 0.255〜0.284 | 0.574〜0.591 | 2.09〜2.11 | 2,015,668 | 616〜622 MiB |
| sofi COPC（2.0 GB） | 0.166 | 0.219 | 0.591 | 1.59 | 1,320,242 | 605 MiB |

最初のノードの読み出しは 32〜40 ms、パースと GPU への転送（`handleNodeLoaded`）は 1.1〜1.2 ms。
**COPC はファイルの大きさ（80 MB〜4.2 GB）にほとんど依らず、0.2〜0.3 秒で最初のノードが載り、1〜2 秒で落ち着く。**
ブラウザの何も開いていない状態の private が約 480 MiB（サンプラーの 0.6 秒目）なので、COPC を開く増分は 40〜140 MiB 程度。

2・3 回目の「ヘッダー・階層」が 3.1・1.5 秒に伸びたのは、直前の出力ファイルを消した直後だったためと思われる（原因は調べていない）。出力は 75.2 MB。

入力が LAZ の場合の読み込みと展開: `beer.laz`（LAZ、66,848,096 点、470 MB、LAS 1.2 点形式 2）、1 回:

空きの読み取りは解放が遅れることがある、と HANDOFF 6 章にある）。

### Web（ブラウザの中の変換。ローカルファイルを開くボタンから）

| 入力 | 開けた（addLayer。＝変換が終わった） | 最初の描画（統計） | 全部見えた | 内訳（アプリの「変換の内訳」の値） | ブラウザ全体の private ピーク |
|---|---|---|---|---|---|
| 渋谷 1 枚（6,199,414 点）×3 | 4.43 / 4.57 / 4.43 | 4.62 / 5.14 / 4.67 | 5.64 / 6.16 / 5.67 | 読み込み 0.142、一時ファイル書き込み 0.573、LOD 0.560、圧縮 2.276、書き出し 0.023、合計 3.575（1 回目） | 688〜974 MiB |
| 渋谷 先頭 10 枚（67,233,981 点、2.13 GiB）×1 | 73.83 | 74.11 | 75.64 | 読み込み 1.877、書き込み 7.708、LOD 16.442、圧縮 44.665、書き出し 0.113、合計 70.806（OPFS の読み書き合計 9.539） | 1,696 MiB |
| 渋谷 55 枚（12 GB） | **変換が始まらなかった**（0.5 秒後に「空き容量が足りません」） | | | | |

- 55 枚: このプロファイルでは `navigator.storage.estimate()` の quota が **10 GiB**（実測。空き 279 GB の C: なのに、永続化していないブラウザの一時領域は 10 GiB まで）。
  アプリが事前に断ったので落ちてはいない（UX としては良い）が、**Web では 55 枚は開けない**。代わりに 10 枚（約 6,700 万点）を測った
- 1 枚の変換の内訳の合計（3.575 秒）と、ファイルを渡してから開けるまで（4.43 秒）の差 約 0.86 秒は、内訳に入っていない（wasm・Worker の起動と、ファイルを渡す部分と思われる。分けて測っていない）
- 点数あたりの時間: 1 枚 約 140 万点/秒、10 枚 約 91 万点/秒（大きいほど遅くなる。圧縮が 63% を占める）

## 結果3: 変換の途中の様子（AC-2 の読み）

1. COPC は開くのにほぼ何もかからない（ヘッダーと階層だけ。ネイティブ 6〜55 ms、Web で最初のノードが載るまで 0.18〜0.28 秒）。**AC-3 の (c) は、今のところ急ぐ理由が無い**
2. LAS/LAZ は、変換が全部終わるまで何も出ない。ネイティブの 55 枚で 220 秒、Web の 10 枚で 74 秒
3. 読み込み（点が入ってくる速さ）は、ネイティブで LAS 約 500 万点/秒（6.2M 点が 1.25 秒）、55 枚で約 430 万点/秒（81 秒で 3.48 億点）、LAZ 約 300 万点/秒。最初の 1% は 0.07〜0.21 秒で入ってくる
4. 時間の大半は読み込みではなく、**LOD の索引（55 枚で 49%）と、Web では圧縮（63%）**。最初の点を出すのに変換を待つ必要は構造上無い（読んだ時点で手元にある）

## 測っていないこと

- Tauri のアプリ（`TauriSource` と WebView）での時間。ネイティブは example（Rust だけ）で、GPU への転送は含まない。デスクトップの GPU の転送時間は Web の `handleNodeLoaded` 1.1〜1.2 ms から推すしかない（推定）
- キャッシュを落とした（コールドな）ディスクでの時間
- Web の 55 枚、Android、10 億点
- 変換の途中で点を取り出す（案 (a)）の実コスト。まだコードが無い
- 変換が走っている間の描画の fps への影響

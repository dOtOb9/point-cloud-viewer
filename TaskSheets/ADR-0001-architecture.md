# ADR-0001: 全体アーキテクチャの選定

- 状態: 採択
- 日付: 2026-09-22

## 決定

点群解析ビューアを **Tauri v2 + React + Tailwind** で構築する。3D描画は webview 内の
`<canvas>` で行い、**Bevy は使わない**。点群の保存・配信形式には **COPC** を採用する。

## 背景

当初案は「Tauri の中で Bevy を動かす」ことで、リッチな UI（React）と高性能な描画（Bevy）を
両立しつつ、全プラットフォーム対応のポテンシャルを持たせるというものだった。
この案を検討した結果、前提が成立しないことが判明した。

### Tauri + Bevy が成立しない理由

Tauri のウィンドウは WebView2（ブラウザ）であり、Bevy の描画先は wgpu のネイティブ
サーフェスである。**両者は互いに合成されない。** 取りうる手段は3つしかなく、いずれも
代償が大きい。

1. **ネイティブ子ウィンドウを重ねる**（`bevy_wry` 等）— Windows では動作するが、透過が
   効かない既知の問題があり（[tauri#12450](https://github.com/tauri-apps/tauri/issues/12450)）、
   z-order・入力イベント・リサイズ・DPI を自前で捌く必要がある。さらに決定的な問題として、
   Web には子ウィンドウという概念が無く、Web 対応が完全な別実装になる。
   加えて **HTML を 3D ビューの上に重ねられない** ため、計測ラベルやコンテキストメニューを
   レンダラ側で自前描画することになる。
2. **Bevy を wasm 化して canvas に載せる** — Web は解決するが、それは「ブラウザで Bevy」で
   あって「Tauri 内で Bevy」ではない。Tauri のバックエンドは描画に一切関与しない。
3. **フレームをテクスチャ転送して webview に流す** — 対話的な3Dナビゲーションには遅延が乗る。

つまり当初案は、移植性を高めるどころか、プラットフォームごとに統合方式を書き直す構成だった。
**移植性を担っていたのは Bevy ではなく、その下の wgpu / WebGPU である。**

### Bevy 単体も採らなかった理由

統合層を捨てて Bevy 単体にすれば、クロスプラットフォーム性はむしろ Tauri+Bevy より高くなる
（ネイティブ・wasm・モバイルが同一コードベース）。実際この案は有力候補として検討した。
採らなかった理由は3つ。

- **点群固有部は結局すべて自作になる。** point sprite シェーダ、EDL シェーディング、
  octree LOD ストリーミング、点予算制御、GPU カリング — どれも Bevy の標準パイプラインには
  乗らず、`RenderApp` に自前ノードを挿すことになる。Bevy から実際に受け取れるのはカメラ
  コントローラと gizmo 程度で、これは自作しても数百行に収まる。
- **ECS が噛み合わない。** ECS が効くのは「数万エンティティを個別に更新する」構造だが、
  点群は「1本の巨大バッファ」であり、恩恵がほぼ無い。
- **出荷の受け皿が無い。** Bevy にはインストーラ・コード署名・自動更新の仕組みが無く、
  全て自作になる。Tauri はこれらを組み込みで持つ。egui で節約した工数はここで消える。

対価として Bevy は 3〜4ヶ月ごとの破壊的変更への追従を要求する。割に合わない。

### 決め手

これはゲームではなく**解析ツール**である。価値が乗るのは属性テーブル、ヒストグラム、
分類の編集、計測の読み値、断面、レイヤーツリー、undo 履歴であり、**表面積の8割は UI** で、
3Dビューはその中の1ペインにすぎない。人が何時間も触る道具を作るなら UI 側に賭けるべきである。

## 付随する決定

### レンダラは TypeScript で書く（Rust→wasm にしない）

Tauri 単体に決めた時点で「同じレンダラをネイティブでも動かす」という選択肢は無くなったため、
レンダラを Rust で書く主な利点（コード共有）が消える。TypeScript で書けば、wasm-bindgen と
二段階ビルドが不要になり、WebGPU API に直接触れ、devtools でそのままデバッグでき、React との
統合も自明になる。**実装を追えることを優先する方針**とも一致する。

Rust は本来強い領域 — COPC のパース、octree 走査、解析アルゴリズム、並列処理 — に集中させる。

### 保存形式は COPC を採用する（自前 octree を作らない）

[COPC](https://copc.io/) は LAZ の内部に octree を埋め込んだ形式で、**HTTP Range リクエストに
よる部分取得を前提に設計されている**。これにより:

- ネイティブでは同じファイルを mmap して読む
- Web では**同じファイル**を静的ホスティングし Range で引く（サーバロジック不要、S3 で足りる）
- リーダーは Rust 1本で、ネイティブと wasm の両方で共有できる
- PDAL / QGIS / lastools とそのまま相互運用できる

自前 octree 形式を切ると、Web 対応時に読み込み層を丸ごと書き直すことになり、かつ既存の
エコシステムから孤立する。

### データ転送はカスタムプロトコルを使う（`invoke` を使わない）

Tauri の `invoke` による IPC は Windows でボトルネックになる。ベンチマークでは 10MB の転送が
macOS で約 5ms に対し **Windows で約 200ms**（≒50MB/s）という報告がある
（[tauri discussion#11915](https://github.com/orgs/tauri-apps/discussions/11915)）。

LOD ノードを移動中に継続的に流し込む用途では、これは直接効く。そのため **ノードデータの転送は
カスタムプロトコル（`pcv://`）で行い、`invoke` は制御メッセージ専用とする**。カスタム
プロトコルは webview のネットワークスタックを通るため JSON 直列化を挟まない。
この規約は M0 で計測して裏付ける。

### Tauri 依存を1ファイルに閉じ込める

Web 版を出せる状態を維持するため、`DataSource` インターフェースを設け、Tauri の API を
import してよいファイルを `TauriSource` の実装1つに限定する。レンダラと UI は `DataSource`
しか知らない。Web 版は `HttpSource` を差し替えるだけで動く。

```
DataSource (interface)
 ├─ TauriSource : pcv:// カスタムプロトコル   ← Tauri API はここだけ
 └─ HttpSource  : fetch + Range              ← Web版はこれを差す
      ↑
   Renderer / UI は DataSource しか知らない
```

## 帰結

**得たもの**
- UI に React / Tailwind / shadcn / Radix / TanStack Table のエコシステムがそのまま使える
- HTML を 3D の上に自由に重ねられる（計測ラベル、ツールチップ、コンテキストメニュー）
- インストーラ・コード署名・自動更新が Tauri 組み込みで手に入る
- Web 版はフロントとレンダラをそのまま流用でき、差し替えは `DataSource` とファイル選択のみ

**払うもの**
- Rust と TypeScript の2言語構成になり、IPC の型契約を維持する必要がある
- データ経路に IPC が挟まる（カスタムプロトコルで緩和するが、ゼロにはならない）
- 描画能力が webview の WebGPU / WebGL2 対応状況に依存する

**引き受けたリスクと対処**
1. **WebView2 で WebGPU が使えるか未確定。** M0 で実測して確定させる。使えない場合は WebGL2 に
   確定させて進む。Potree は WebGL2 のみで数十億点を捌いているため、これは死因にならない
   （compute shader による GPU カリングを諦め、CPU カリングにする）。
2. **IPC 帯域。** 最初からカスタムプロトコルで実装し、スループットを計測するベンチを CI に入れる。

## 却下した案

| 案 | 却下理由 |
|---|---|
| Tauri + Bevy 子ウィンドウ重ね | webview とネイティブサーフェスが合成されない。Web が別実装になり、HTML を 3D 上に重ねられない |
| Bevy 単体 + egui | 点群固有部は結局自作、ECS が噛み合わない、出荷の受け皿が無い、破壊的変更への追従コスト |
| Tauri + ネイティブ子ウィンドウ wgpu（Bevy なし） | 子ウィンドウ方式の問題（Web 別実装・HTML を重ねられない）が Bevy 案と同じ |
| 自前 octree 形式 | Web 対応時に読み込み層を全書き直し。エコシステムから孤立 |

## 1. 点群レイヤーは今どう持たれているか（新しいツールの土台）

レイヤーは **「COPC ファイル1つ」＋「小さな記録」** である。点そのものは、JS にも Rust にも、全部がメモリに載ることは無い。

| 場所 | 何があるか | コード |
|---|---|---|
| ファイル | 点群レイヤーはどれも COPC ファイル1つ。デスクトップ: 利用者のファイル、またはツールの出力 `<一時フォルダ>/pcv-tools/*.copc.laz`。Web: OPFS 上のファイルで、`file:3` のようなキーで開く | `src-tauri/src/conversion.rs` の `tool_output_path`、`src/datasource/opfs.ts` |
| 開いたリーダー | `DataSource.open(path)` が `cloudId`、点群全体の `CloudInfo`（範囲・scale/offset・CRS）、octree のノードの一覧を返す。リーダーは Rust（デスクトップ）か Worker の wasm（Web）にある | `src/datasource/DataSource.ts` |
| GPU | renderer が点の予算の範囲でノードを必要なときに読み（`readNode`）、要らなくなったら捨てる | `src/renderer/node-loader.ts`、`node-cache.ts` |
| 記録 | React の状態にある `ViewerLayer`: id・名前・`info`・表示の設定・`cloudId`・`sourcePath`（`open` に渡した文字列） | `src/state/layers.ts` |

点群ツール（選択・断面・結合）は、GPU にも JS 側の点にも触らない。`sourcePath` を Rust に渡し、Rust が COPC を
**ノード単位で**読み（`pcv_core::extract::ExtractPoints`。一度に持つのは1ノード分の点だけ）、`vendor/copc-writer` で
**新しい** COPC を書き（ディスクに spill する）、`addOpenedLayer` がそのファイルを新しいレイヤーとして開く。
例外は計測レイヤーだけで、ファイルを持たず（`cloudId = -1`）、SVG の重ね描きで表示している。

**この計画にとっての帰結:** ラスタ化も CSF も同じ形に乗る。Rust が元の COPC を1回か2回流し読みし、メモリには
**グリッド**だけを持ち（大きさは面積とセルの大きさで決まり、点数には比例しない）、結果を新しいファイルに書く。

## 2. 作るもの

```
点群レイヤー ──[ラスタ化]──▶ GeoTIFF（成果物）＋ 表示用のレイヤー（1セル1点）
点群レイヤー ──[地表（CSF）]──▶ 新しい点群レイヤー（地表の点を分類 2 にしたもの。元は変えない）
地表を分類したレイヤー ──[ラスタ化：地表のみ・穴埋め]──▶ DTM の GeoTIFF ＋ 表示用のレイヤー
```

**利用者から見た DTM は、ボタン1つ**（所有者の回答 Q5 を受けて整理）。「DTM」ボタンは内部で CSF（地表の分類）→ 地表面を作る
（間引いた地表の点の TIN。9.2）→ 設定の形式（GeoTIFF の格子 / LandXML の TIN / 両方。9.3 Q18）で出す、までを続けて行う。
利用者が「ラスタ化」ツールを別に使う必要は無い。内部で格子を作る部品（グリッド・GeoTIFF の書き出し）をラスタ化ツールと共有するだけ。
「ラスタ化」ツールは、DTM とは別に、任意の点群から DSM・強度・RGB・密度の画像を作るために残す。
出力: 地表を分類した点群レイヤー（ADR-0018 の新しいレイヤー）、DTM の表示用レイヤー（1セル1点）、DTM のファイル。

### 2.1 ラスタ化（G1-R）

- 入力: 選んだ点群レイヤー。パラメータ: セルの大きさ（レイヤーの水平の単位。計測と同じく m / ft で表示）、
  値の種類、分類の絞り込み（全部 / 地表のみ / 選んだ分類）、空のセル（NoData のまま / 埋める）
- 値（最初の版）: Z の最小・最大・平均、点数（密度）、強度の平均、**RGB の平均**（所有者の回答 Q8。オルソ画像のような絵になる）。
  RGB だけは3バンド（u16。LAS の色と同じ幅）の GeoTIFF にし、表示用レイヤーの点にもその色を付ける。「最も多い分類」は要望があれば後で
- グリッド: ファイルの座標軸に沿わせ、原点をセルの大きさの倍数にそろえる（隣り合うレイヤーのラスタが重なるように）。
  セルごとの集計: `min f32`・`max f32`・`sum f64`・`count u32`（選んだ値に要るものだけ持つ）
- 出力1 **GeoTIFF**: 1バンドの float32（RGB は3バンドの u16）。NoData の値は `GDAL_NODATA` に書く。`ModelPixelScale`＋`ModelTiepoint`。
  レイヤーが EPSG コードを持つとき（`CrsId::Epsg`）は CRS を GeoKey で書く。WKT だけ・CRS 無しのときは CRS 無しで書き、
  エラーログに警告を出す（ADR-0011）。デスクトップ: 保存ダイアログで保存するボタン（`@tauri-apps/plugin-dialog` は
  依存に入っている。使うのは `src/datasource/tauri.ts` だけ）。Web: 変換した COPC と同じくダウンロードリンク
- 出力2 **表示用のレイヤー**: 空でないセルの中心に1点ずつ置いた COPC。高さの値なら Z ＝ 値。それ以外の値は
  Z ＝ セルの Z の平均とし、値を強度（u16 に縮めて）に入れる。既存の「強度」の着色でそのまま見える。
  renderer とレイヤーの仕組みを全部そのまま使え、新しいパイプラインが要らない
- 表示用レイヤーの `ViewerLayer` に任意の `raster` 欄（セルの大きさ、値の種類、幅×高さ、GeoTIFF のパス／ダウンロード）
  を足し、レイヤーの情報に変換の内訳と同じように出す

最初の版で採らない案: renderer に高さ場のメッシュ・テクスチャを描かせる。見た目は良いが、2つ目のパイプライン・
独自のピック・独自の GPU エラー処理が要る。ROADMAP の TIN でもメッシュのパイプラインが要るので、そのときにやる（G1-9）。

### 2.2 CSF による地表の分類（G1-C）

アルゴリズムは論文（2節）と参照実装の通り:

1. 高さを反転する（`z' = -z`）。地表が、布が落ちて乗る「上の面」になる
2. 布: `cloth_resolution` 間隔の粒子の格子。レイヤーの XY の範囲＋余白を覆い、反転した点の最も高いところより上から始める。
   粒子は**鉛直方向にだけ動く**（参照実装と同じ）。1粒子は `高さ f32・前の高さ f32・動けるか bool`
3. 粒子ごとの **IHV（intersection height value）**: XY で粒子に最も近い点の反転した高さ（点を1回目に流し読みするとき、
   セルごとに最も近い点の高さと距離を残す）。点の無い粒子は、同じ行・列で最も近い値のある粒子から値をもらう
   （参照実装のスキャンラインの埋め方）
4. 反復: 重力による変位（`time_step` の Verlet）→ 隣どうしの内部の拘束を `rigidness` 回 → 衝突の判定
   （IHV 以下に来た粒子は IHV に置き、動けなくする）。高さの変化の最大がしきい値を下回るか、`iterations` 回で止める
5. 斜面の後処理（`slope_smooth`）: 動けない粒子の隣の動ける粒子は、差が小さければ IHV に寄せる（論文 2.4 節）
6. 分類（点の2回目の流し読み）: 元の向きの高さで `d = 点の z − その XY での布の高さ`（粒子の間は双線形補間）を求め、
   `−class_threshold_lower ≤ d ≤ class_threshold_upper` なら地表（分類 2）、そうでなければ地表以外。
   **論文・参照実装は上下同じしきい値（`|d| < class_threshold`）。上下を分けるのは所有者の経験による変更**（2026-10-21。12節）

2回目は、抽出ツールと同じく点をそのまま `copc-writer` に流すので、**点をメモリに抱えない**。メモリに持つのは布だけで、
1粒子あたり約 12 B（IHV を作るあいだはさらに約 8 B）。ファイルのヘッダーから見積もった値
（2026-10-21 にヘッダーの範囲を node の1行スクリプトで読んだ。セル数は計算で、メモリは**測っていない**）:

| データ | 範囲 | 0.5 間隔の粒子数 | 1.0 間隔の粒子数 |
|---|---|---|---|
| `tokyo-shibuya-merged-v2.copc.laz`（3.48億点） | 3,200 × 2,400 m | 3,070万（約 0.6 GB と推定） | 770万 |
| `tokyo-23ku-1b.copc.laz`（10.6億点） | 4,400 × 4,500 m | 7,920万（約 1.6 GB と推定） | 1,980万 |
| `autzen-classified.copc.laz`（1,070万点） | 3,426 × 4,656（ft と思われる。未確認） | 6,380万 | 1,590万 |

そこで最初の版は**セル数に上限**を設け、超えたら「解像度を粗くするか、先に選択ツールで範囲を切り出してください」と断る。
上限の値は G1-6 で測ってから、デスクトップと Web で別々に決める。上限を外したくなったら、タイル分割（G1-9）で外す。

パラメータ（所有者の回答 2026-10-21。参照実装の既定値をもとに、所有者の経験で変えたもの）:

| パラメータ | 標準 | 急勾配 | 出典 |
|---|---|---|---|
| `cloth_resolution` | 0.5 | **0.25** | 標準は参照実装。急勾配は所有者（2026-10-21。8.6） |
| `rigidness` | 3 | **1** | 急勾配は所有者 |
| `iterations` | 500 | **1500** | 急勾配は所有者 |
| `time_step` | 0.65 | 0.65 | 参照実装 |
| `class_threshold_upper`（布より上） | **0.1** | **0.1** | 所有者 |
| `class_threshold_lower`（布より下） | **1.0** | **1.0** | 所有者 |
| `slope_smooth` | オン | オン | 参照実装 |
| `hdiff`（後処理の高さの差） | 0.3 | 0.3 | PDAL の既定 |

**ダイアログ**: 上に「標準 / 急勾配」のプリセットを選ぶ欄。その下に「詳細設定」のトグル（既定は閉じる）を置き、開くと
全部のパラメータを数値で直せる。数値を直したらプリセットの表示は「カスタム」にする。プリセットを選び直すと数値は
プリセットの値に戻る。プリセットと数値の対応は `src/app/` の1つの表（定数）に置き、ダイアログはそれを表示するだけにする。

実行時間は**測っていない**。大まかな見込み: 770万粒子 × 数百回 × 数十演算 ≈ 10^10〜10^11 回の単純な演算で、
ネイティブの1スレッドで数十秒〜数分、wasm ではそれより遅い（推定）。動けなくなった粒子はほとんど手間がかからないので、
実際はもっと速い見込み（未検証）。G1-6 で測り、必要なときだけデスクトップで `rayon`（`Cargo.lock` に既にある）を使う。

### 2.3 DTM（G1-D）

「地表のみ」「空のセルを埋める」でラスタ化する。渋谷では空のセルが肝心で、建物の下には地表の点が無い。
埋め方（Q4）: (a) CSF の布の高さ（布は穴の上にも張られている）、(b) 近くの地表のセルからの逆距離補間、(c) NoData のまま。
(a) は G1-C の布をラスタ化まで運ぶ必要があり、(b) は CSF と独立している。
**9.2 で、これらの代わりに「間引いた地表の点の TIN を格子に落とす」方法を提案した**（一般的な作り方に合わせるため）。

鉛直座標系（ADR-0008 は「DTM の前に」と書いている）: CSF は高さの差しか使わないので影響を受けない。DTM は**元の点群の高さの基準を
そのまま引き継ぐ**（所有者の回答 Q6）。PDAL・LAStools も入力の高さを変えずに DEM を作り、基準の変換は別の工程にしている
（両者の文書から読んだ範囲での理解。業界の規程として確かめたものではない）。元の点群が CRS に鉛直の基準を持っていれば、出力にも同じものを書く。
注意: 国土地理院は 2025-04-01 に標高の基準を「ジオイド2024日本とその周辺」に基づく体系へ改定した。それより前の点群と後の点群では
同じ地点でも標高が数 cm 程度違いうる（富士山の三角点で +5 cm の例）。古いデータと新しいデータを合成・比較するときの注意として
設計書に書く。換算（基準面補正パラメータ）は今回作らない。

## 3. コードを置く場所

| 部分 | 場所 | 理由 |
|---|---|---|
| グリッド・集計・CSF の布と反復・GeoTIFF のバイト列 | `crates/pcv-core/src/raster/`（`grid.rs`・`geotiff.rs`・`csf.rs`） | 純粋で Tauri に依存せず、wasm32 でビルドできる（規約1）。ファイル無しで単体テストできる |
| COPC の全点を読む（条件なし） | `pcv_core::extract`（`All` の場合を足すか、小さな兄弟のイテレータ） | 既存のツールと同じ、ノード単位の読み方 |
| デスクトップでの実行（流し読み、GeoTIFF と COPC を書く） | `crates/pcv-convert/src/raster.rs`・`csf.rs`。コマンドは `src-tauri/src/conversion.rs` | `extract.rs` / `extract_copc` と同じ分け方 |
| Web での実行 | `crates/pcv-wasm/src/raster.rs`・`csf.rs`（`feed` / `finish`。バッチの合間でキャンセル）、Worker のメッセージ、`WebSource` のメソッド | `crates/pcv-wasm/src/extract.rs` と同じ |
| 手順（ツールを走らせる・進捗・レイヤーを足す） | `src/app/point-cloud-tools.ts`（普通の関数。ADR-0021） | 新しいロジックをフックに足さない |
| ダイアログ・リボンのボタン | `src/ui/tools/RasterDialog.tsx`・`GroundDialog.tsx`、`src/ui/toolbar/buttons/` | 表示だけ |

GeoTIFF の書き出しは**手書き・無圧縮・ストリップ**にする（約150行。タグが全部見える）。採らない案: `tiff` クレートを
実行時の依存にする（GeoTIFF のタグは結局汎用のタグ書き込みで書くことになり隠れる。wasm でのビルドも未確認）。
`tiff` はテストで読み戻すための **dev-dependency** としてだけ使う。渋谷を 1 m で無圧縮にすると 770万 × 4 B ≈ 31 MB（計算）。

エラー処理（ADR-0015）: 新しいコードで `unwrap` / `panic!` を使わない。`pcv-core` / `pcv-wasm` で `Instant::now` を使わない
（`extract.rs` と同じく `web_time`）。コマンド・Worker の入口で panic を受け止め、既存のエラーのバナーとログに出す。

## 5. 起こりうる失敗（このプロジェクトで既に知っているもの）

- **テストは緑で、画面は壊れている。** UI を足す手順は、実ブラウザのスクリーンショットと所有者の確認で終える
- **メモリが点数に比例する。** 大きいのはグリッド・布（上限で抑える）と writer の spill だけ。リーダーのバッファが点数で
  増えないことをテストで確かめる
- **COPC の粗いレベル。** 「全点」は全レベルの全ノード（COPC のレベルは互いに重ならない点を持つ）。最も細かいレベル
  だけ読むと、黙って点が落ちる。読んだ点数をヘッダーの点数と比べるテストを置く
- **単位。** セルの大きさと `class_threshold_upper` / `lower` はファイルの単位。ft のファイルで 0.5 は 0.5 ft。ダイアログに単位を出し、
  CRS から係数が分かるときは m から換算する（計測と同じ）
- **Web での長い処理。** CSF は反復のバッチの合間で処理を返し、キャンセルが効くようにする。`finish` で長いループを持たない

### 8.2 今の断面ツール（変えるところ）

`src/state/useLayerTool.ts` で3Dの2点 A・B を選ぶ → `SectionDialog` で厚さと高さの範囲を入れる →
`sectionBox`（`tool-math.ts`）で向きのある箱を作る → `extractFromLayer` が箱の中の点を新しい COPC のレイヤーにする →
カメラを断面に正対させる。**2Dの画面は無く**、断面は3Dの中で横から見ているだけ。

変えるのは「レイヤーを作ったあと」だけで、抽出はそのまま使う。ADR-0018 の形（元を変えず、新しいレイヤーを作る）も保つ。
元のレイヤーは「非表示にする」だけで、書き換えない。

### 8.3 設計

**座標**: 断面図の横軸は A からの水平距離 `s`（A→B の水平方向への射影）、縦軸は高さ `z`。どちらもファイルの単位で持ち、
表示は計測と同じく m / ft にする。

**断面の点（2D）**: 断面のレイヤーの COPC を Rust が流し読みし、各点を `(s, z)` と色（RGB、無ければ分類か標高）に直して返す。
厚い断面を長く引くと点が数百万になりうるので、**点数に上限**を置く（例: 200万点。`(s, z)` の細かい格子で1マス1点に間引き、
それでも超えたら一定間隔で間引く）。200万点 × 12 B ≈ 24 MB（計算）。CLAUDE.md の「メモリが点数に比例しない」を、
この上限のテストで確かめる。

**断面線（元の点群から、内部で局所的に DTM を作る。Q10 の回答）**: 利用者からは「元の点群から断面線ができる」ように見せる。
DTM のレイヤーを先に作っておく必要は無い。内部の流れ:

1. 断面の線 A→B を中心にした細長い帯（回廊）の点を、元の COPC から読む（既存の `ExtractPoints` に向きのある箱を渡す）。
   帯の幅は断面の厚さより広くとる（CSF の布が周りの地形を見られるように。幅の既定値は G2-4 で決める。例: 片側 20 m）
2. 帯の点に CSF（G1-5 の `pcv-core::csf`）をかけて地表の点を選ぶ。メモリは帯の面積に比例し、点数には比例しない
3. 地表の点から局所の地表面を作り（9節の結論に合わせる。TIN か格子）、A→B に沿って一定の間隔で高さを読み、`(s, z)` の折れ線にする。
   地表の点が無い区間（建物の下など）は、面の補間で埋めるか線を切る（9.3 の Q16）

これで G2-4 は G1-8（DTM のラスタ化）を待たず、G1-5（CSF の中身）だけを待てばよい。

**描画**: Canvas 2D の `ImageData` に、点をピクセルとして直接書く（200万点で1回 10〜20 ms 程度と推定。未計測）。
断面線・GL の印・文字は、その上に Canvas 2D の線で描く。
採らない案: WebGPU の2つ目の画面（renderer に正射影のパイプラインを足す）。速いが、renderer が大きくなり、
GPU のエラー処理も2つ目が要る。Canvas 2D で遅いと測れたときに考える。
採らない案: SVG で点を描く。数万点を超えると重い。

## 9. 調査: DTM は一般にどう作るか（2026-10-21）

所有者の問い: 「分類？ グリッド化・補間・平滑化した点群を足す？ TIN に変える？」。
Web 検索と、取得できた公開資料の本文から調べた。国土地理院の「作業規程の準則」の本文（PDF）は、こちらの環境では
読めなかった（PDF からテキストを取り出す道具が無い）。準則の細かい規定は**未確認**。

### 9.1 分かったこと

一般的な流れは **「分類（フィルタリング）→ 地表の点から面を作る（TIN が主流）→ 用途に合わせて格子か TIN で出す」**。
平滑化は、見つけた資料の標準的な工程には出てこなかった。

1. **地表の点の分類（フィルタリング）**: 地表以外（建物・植生）を除いた「グラウンドデータ」を作る。手法には CSF、SMRF、
   TIN を少しずつ太らせる方法（Axelsson）などがある。PDAL は SMRF や CSF で分類し、分類 2（地表）を取り出す例を出している。
   PDAL の `filters.csf` の既定値は `resolution 1.0`、`rigidness 3`、`step 0.65`、`threshold 0.5`、`iterations 500`、
   `smooth true`、`hdiff 0.3`。全地連の資料は、グラウンドデータを作るには**手作業のフィルタリング**も含まれ、高い技術力が要る、
   と課題に挙げている
2. **面の作り方**:
   - **TIN（主流）**: 地表の点を Delaunay で三角形に結ぶ。LAStools の `blast2dem` は「地表の点から継ぎ目の無い TIN を作り、
     それを格子に落として DEM にする」。既定では**辺が 100 m より長い三角形は格子に落とさない**（大きな穴を引き伸ばした
     三角形で埋めないため）。日本の用語解説（国総研）でも、グリッドの各点の高さは「グラウンドデータから作った TIN に、
     格子の隅から下ろした垂線との交点」で求める、と説明されている
   - **格子に直接集計＋穴埋め**: PDAL の `writers.gdal` は、セルの中心から半径内の点の min / max / mean / IDW（逆距離重み）/
     点数を値にし、空のセルは近くのセルからの IDW で埋められる（`window_size`。既定は埋めない）
3. **出し方**:
   - **格子（グリッドデータ、GeoTIFF など）**: 解析（勾配・微地形）や GIS 向け。鹿児島県の仕様書の例では格子間隔 0.5 m 以内
     （国の準則の数値そのものではない）
   - **TIN（LandXML）**: i-Construction の起工測量・出来形では、点群から TIN の面を作り、**LandXML** で受け渡すのが標準的
     （福井コンピュータのマニュアル、国交省の資料）。設計データの交換には国交省の **J-LandXML** がある
   - 「格子の点群」として出すこともある（`blast2dem` の XYZ 出力など）。この計画の表示用レイヤー（1セル1点）はこれに当たる

### 9.2 この計画への当てはめ（提案）

所有者の3つの案は、どれか1つを選ぶのではなく、**順につながる工程**になっている。

| 工程 | この計画での形 | 状態 |
|---|---|---|
| 分類 | CSF で地表を分類 2 にした新しい点群レイヤー（G1-C） | 計画のまま |
| 面を作る | **地表の点を間引いて（1セル1点）TIN を作り、格子に落とす**（代表点はセルの中心に最も近い地表の点。辺の長さの上限は設けない。9.3） | 2.3 の「穴埋め」の案 (a)〜(c) を**これに置き換える**ことを提案 |
| 格子で出す | DTM の GeoTIFF ＋ 表示用レイヤー（1セル1点）（G1-8） | 計画のまま |
| TIN で出す | LandXML の TIN の面。建設会社の受け渡しに合う | **新しい候補（G1-10）**。所有者の判断待ち（Q18） |
| 平滑化 | 標準の工程ではないので、最初の版では作らない | 提案 |

TIN を間引いた点（1セル1点）で作る理由: 地表の点を全部結ぶと、三角形の数が点数に比例する（CLAUDE.md の決まりに反する）。
1セル1点に間引けば、三角形の数はセル数で抑えられる。間引くときの代表点（セルの最も低い点 / セル中心に最も近い点）は Q16 で決める。
Delaunay の実装は、純 Rust で wasm にもビルドできるクレートがあるか、G1-8 の前に調べる（**未調査**）。

断面線（G2-4）も同じ作り方にする: 帯の地表の点から TIN を作り、A→B に沿って高さを読む。建物の下は TIN の三角形がつなぐ
（辺の長さの上限は設けない。9.3）。

## 11. G3: 間引きとフィルタリング（所有者の要望 2026-10-21）

ADR-0018 の形: 選んだ点群レイヤーから、残した点だけの新しいレイヤーを作り、元は非表示にする（G0-2）。
元の点の属性（RGB・強度・分類など）はそのまま運ぶ（新しい点を作らず、元の点から選ぶ）。

| 機能 | 何をするか | パラメータ（案） |
|---|---|---|
| グリッド化（2D） | XY の格子の1セルに1点だけ残す | セルの大きさ、残す点（セル中心に最も近い / 最も低い / 最も高い） |
| ボクセル化（3D） | 立方体のボクセル1つに1点だけ残す | ボクセルの大きさ、残す点（ボクセル中心に最も近い点） |
| SOR（統計的外れ値除去） | 各点の k 近傍までの平均距離を求め、全体の平均＋n×標準偏差を超える点を除く | k（例 8〜16）、n（例 1.0〜3.0） |
| ROR（半径外れ値除去） | 半径 r の中の近傍が m 点未満の点を除く | r、m |

ボクセル化の「残す点」を重心にしない理由: 重心は新しい点になり、RGB や分類を混ぜることになる。元の点を残せば属性がそのまま。

### 11.1 メモリを点数に比例させない作り方: タイルに分ける

4つとも「近くの点」を見る（同じセルの点、近傍の点）。全点を一度に持たずに済ませるため、**XY のタイルごと**に処理する。

1. レイヤーの範囲を XY のタイルに分ける
2. タイルごとに、タイル＋**縁の余白**（SOR・ROR は近傍を探す距離。グリッド・ボクセルは 0）の点を、既存の `ExtractPoints` に
   軸に沿った箱を渡して読む（COPC はその範囲に掛かるノードだけを読む）
3. タイルの中で近傍を探し、残す点を決める。**出すのはタイルの内側の点だけ**（余白の点は、隣のタイルで出す）
4. 残した点をそのまま `copc-writer` に流す（抽出と同じ。出力の点も抱えない）

メモリはタイル1枚分の点で決まる。タイルの大きさは、COPC の階層の点数（ノードごとの点数が分かる）から、1枚の点数が上限
（例: 200万点。G3 の測定で決める）を超えないように選ぶ。密な所は小さいタイルにする。
上限を超えないことを、`buffer_is_bounded_by_largest_node` と同じ形のテストで確かめる。

近傍の探し方: タイルの中で**一様な格子（バケツ）**に点を入れて探す（手書き。読めるようにするため）。
採らない案: kd-tree のクレート。速いが、中身を追いにくい。格子で遅いと測れたときに考える。

SOR は全体の平均と標準偏差が要るので、**2回流し読みする**（1回目: 各点の平均距離から、全体の平均と標準偏差を足し上げる
（Welford の方法）。2回目: 同じ計算をもう一度して、しきい値で選ぶ）。点ごとの平均距離を保存しない（保存すると点数に比例する）。
代わりに近傍の計算を2回する（時間を払ってメモリを守る）。

知っている落とし穴:
- **粗いレベルのノードを何度も読む**: COPC の上のレベルのノードは範囲が広く、どのタイルにも掛かるので、タイルの数だけ読み直す。
  時間がどれだけ増えるかは G3 で測る（未計測）
- **同じ点を二度出す・出し忘れる**: タイルの境界ちょうどの点の扱いを「左と下を含み、右と上を含まない」に決め、
  全タイルで出した点の数を確かめるテストを置く
- **単位**: セル・ボクセルの大きさと半径はファイルの単位。ダイアログに単位を出す（計測と同じく m / ft）

## 13. ラスタ化をウィンドウとプレビューに作り直す（所有者の要望 2026-10-21）

### 13.1 要望（所有者の言葉をまとめたもの）

- ラスタ化は点群ではなく画像を作る機能なので、ウィンドウの中にプレビューを出すのが筋
- 書き出した TIFF を Windows のフォトで開いたら白黒で、意味が分からなかった（float32 の1バンドを濃淡で見せているため）
- 書き出しは TIFF。RGB か標高かなどは、**ウィンドウの中のボタンで設定し、手軽にプレビューで確かめられる**ようにする
- 表示用の点群（空でないセルの中心に1点ずつ置いた COPC。G1-T6）は**要らない**
- 陰影（hillshade）は要らない（コーディネーターの提案に対し、所有者が「要る？」と問い、入れないことにした）

### 13.2 形

ラスタ化のボタンで、選んだ点群レイヤーに対するウィンドウ（中央の大きめのガラスのダイアログ）を開く。

- **左（狭い画面では上）: 設定のボタン**（どれもトグルのボタンの列。数値はセルの大きさだけ）
  - 値: RGB / 標高（Z の平均・最小・最大）/ 点数 / 強度
  - 分類: すべて / 地表のみ
  - セルの大きさ（表示単位 m / ft。今のダイアログと同じ換算）
  - 書き出す TIFF: **色付き（見たとおりの画像）** / **値のまま（解析用の float32）**。既定は色付き
- **右（狭い画面では下）: プレビュー**。Canvas 2D の `ImageData`。設定を変えるとすぐ描き直す。凡例（標高・点数・強度のとき、
  色と値の対応と単位）。空のセルは透明（市松模様の背景）
- **下: 「書き出す」ボタン**。全点を指定のセルの大きさで読み、TIFF を作る。進捗とキャンセルは今のツールの進捗と同じ。
  デスクトップは保存ダイアログ、Web はダウンロード
- 結果は**レイヤーにしない**（点群ではなくファイルが成果物のため）。ウィンドウを閉じれば終わり。元のレイヤーも隠さない

### 13.3 「手軽に」のためのプレビューの作り方

全点を読むと渋谷で約 3 分かかる（G1-T6 の測定）。設定を変えるたびに全点は読めない。

- プレビューは COPC の**上のほうのレベル（粗い点）だけ**を読み、長い辺が最大 1024 セル程度の格子に足す
  （読むレベルは、点の数が数百万を超えない深さまで。数値は測って決める）
- 粗い点は1回読んだら、ウィンドウを開いているあいだ Worker / Rust 側に持っておき、値・分類・色の切り替えは
  それを足し直すだけにする（点の上限があるので、メモリは点数に比例しない。上限はテストで確かめる）
- プレビューは目安であることを画面に書く（「プレビューは間引いた点から作っています」）。最小・最大は粗い点では外れうる

時間は**測っていない**。数秒で出る見込み（推定）。渋谷で、開いてから最初のプレビューまでと、切り替えにかかる時間を測る。

### 13.4 色の付け方

- 標高・点数・強度: 色の範囲は値の最小〜最大（プレビューの値から決め、書き出しも同じ範囲を使う）。
  配色は表示の標高と同じ（CloudCompare の既定、青＞緑＞黄＞赤。`src/renderer/colormap.ts` と同じ段）
- RGB: そのままの色（u16 → u8）
- 空のセル: アルファ 0
- 色付きの TIFF は RGBA の 8bit。GeoTIFF のタグ（`ModelPixelScale`・`ModelTiepoint`・EPSG）はそのまま付ける。
  Windows のフォトでは見たとおりの絵になり、QGIS では位置の合った図として重なる
- 色を付ける関数は Rust の1か所に置き、プレビューと書き出しで同じものを使う（プレビューと書き出しで色がずれないように）。
  `colormap.ts` の段を写したことをコメントに書き、両方に同じ値の対応のテストを置く

### 13.5 消すもの

表示用の COPC（`DisplayPoints`・`DisplayCursor`・`display_z_at` の Z の合計・`filled_cells` の表示用の使い方）、
`ViewerLayer.raster`・`RasterInfoSection`・`initialColorModeForRaster`、ラスタ化で新しいレイヤーを作る流れ。
値のままの TIFF（今の float32 / u16 の GeoTIFF の書き出し）は残す。

# 再開時の引き継ぎ

中断して時間をおいてから作業を再開するとき、または新しいセッションで続きをするときに、最初に読むファイル。
「いま何がどこまで終わっていて、どこから読めば全体が分かり、次に何をすればいいか」を書く。
判断の理由や経緯は各 ADR・タスクシートにあるので、ここからは参照するだけにする。

**最終更新: 2026-10-14**（セッションを切り替える前にコーディネーターが更新）

---

## 0. 新しいセッションのコーディネーターへ

- まず `CLAUDE.md`（全エージェント共通の決まり）を読み、次にこのファイルを読む
- **役割分担**: 計画・診断・測定結果の解釈・判断は上位モデル（コーディネーター）が持ち、
  受け入れ基準を書いたうえで実装は Sonnet のサブエージェント（`model: sonnet`、`isolation: worktree`、バックグラウンド）に任せる。
  原因が分からない不具合の診断はコーディネーターの仕事。診断が終わったら、修正は委譲する
- 互いに独立した作業は並行で走らせる。所有者の確認を待って次を止めない
- **サブエージェントの報告は鵜呑みにしない。** スクリーンショットは自分でも見る、数値は自分でも測り直す。
  このセッションでも、合成データでの計測（ノード選択の時間）とデータの解析（密度図・黒い点の有無）を自分で行い、
  エージェントの報告の解釈を2回直した
- **測定を伴う指示には「長く待つ処理は run_in_background で走らせ、結果をファイルから読む」と必ず書く。**
  1回のコマンドで10分出力が無いと、エージェントが止められる（このセッションで1回起きた。worktree も壊れて再開できなかった）
- GPU を使う測定と、CPU を食う変換（`merge_las_to_copc`）を同時に走らせない。測定の指示に「変換プロセスが無いことを確かめてから測る」と書く
- 所有者は日本語で話す。返答も日本語

## 4. 次にやる作業（コーディネーターが順番を決める）

- **LOD 改善 B（内蔵 GPU 向けの設定）**: 上の 1 が決まって ThinkBook で測れるようになってから。
  `adapter.info` で見分け、点予算の上限・開始値・描く解像度を下げる。HQ-2 の効き目もそこで測る
- **ステータスバーの「最大まで読み込み中」**: 読み込みが終わっても表示が変わらない。「最大の細かさ」などに直す（小さい）
- **10億点の変換が点数比以上に遅い**（点数3.03倍で時間5.8倍）。一時ファイル約60GB が RAM（32GB）に収まらず I/O 律速になった **[推定]**。
  数十億点（段階2: 約40億点、外付けディスクが要る）に進む前に、切り分けて速くする。M4-16 の +41% の改善案（子の列の振り分けを次のレベルの partition と同じ読み込みで済ませる）も合わせて
- **数十億〜100億点**: 所有者の方針は「まず10億点（済み）。超える場合は23区の実データ」。
  42.9億点を超えるには copc-writer の点番号を u32 → u64 にする改修と約1TBのディスクが要る（`BENCH-1b-points.md`）
- **Web 版の読み込みの速さ**: 10億点の街区で上限まで40〜50秒（デスクトップは5秒前後）。計測に使った自作の配信サーバーが律速の疑いがあり、
  まず GitHub Pages など普通のサーバーで測り直して切り分ける
- 10億点の計測中に「カメラがひとりでに動いたように見えた」回があった（原因不明。再現したら調べる）
- アプリ側の結合（M4-14）で CRS の無いファイルをどう扱うか（23区のタイルで止まる）
- 以前からの残り: 紹介動画の撮り直し（**後回しでよいと所有者**）、Android で複数ファイルの選択（`content://`）、
  設計書（mdBook）と ADR を最新にする、Web で OPFS が異常な値を返す本当の原因

## 6. 繰り返し踏んだ落とし穴

**すべて緑なのに壊れている**（このプロジェクトで最も多い）。**緑は「確かめた」の代わりにならない。** 画面で見る

**データの作り方の不具合が、表示の不具合に見える**（M4-16）。渋谷の「表示されにくい列」は描画ではなく変換の偏りだった。
LOD の不具合を疑う前に、ファイルの各レベルの点の分布を数える（`BENCH-1b-points.md` にある lodscan の考え方）

**点の数ではなくノードの数に比例する処理**（ノード選択）。数億点では見えず、10億点で初めて fps に出た。大きなデータで測る

**コーディネーターの仮説が外れる**。仮説は「推定」と書き、計測で確かめてから直させる。
エージェントには「仮説が外れたら直さずに止まって報告」と指示しておく（このセッションの LOD A 1回目はこれで無駄が出なかった）

**一方向にしか動けず、回復経路を持たない設計**（ADR-0007、0010）。制御ループや推定を書くときは「下がったあと戻れるか」を確かめる

**測り方の誤り**。ピークメモリは private memory で測る。Playwright のブラウザが SwiftShader でないか `adapter.info` で確かめる。
画面ありの Chromium は `--disable-background-timer-throttling --disable-renderer-backgrounding --disable-backgrounding-occluded-windows`
を付けないと、ウィンドウが後ろに回ったとき rAF が絞られて fps が 0 になる

**エージェント同士がぶつかる**。ポートは `PCV_E2E_PORT` で分ける。自分が起動したプロセスだけ止める。
同じ時刻に同じ道具（scratchpad の解析プログラムなど）を書き換えると、別のエージェントの結果が狂う

## 7. 守り続けている制約

- 秘密鍵・キーストア・パスワード、点群データ（`*.laz`・`*.copc.laz`・`*.pcd`・`/data`）はコミットしない。
  ThinkBook 用の SSH 秘密鍵は開発機の `~/.ssh/thinkbook_ed25519`（リポジトリの外）
- コミットの著者は GitHub の noreply アドレス
- 規約1〜3（CLAUDE.md・ARCHITECTURE.md）は CI の `invariants` ジョブが検査する。コメントに Tauri のパッケージ名を書いても落ちる
- CI の Rust ジョブは `vendor/copc-writer` の `cargo fmt` も別に検査する
- 外部リポジトリへの提案・Issue・PR はしない

# 再開時の引き継ぎ

中断して時間をおいてから作業を再開するときに、最初に読むファイル。
「いま何がどこまで終わっていて、次に何をすればいいか」だけを書く。
判断の理由や経緯は各 ADR にあるので、ここからは参照するだけにする。

**最終更新: 2026-09-23**

---

## 1. 再開したら最初にやること

**`npm run tauri dev` で `data/sofi.copc.laz` を開き、目視で4点を確認する。**

2026-09-23 に入れた変更のうち4つは、GUI を持たない環境で実装したため
**画面での確認が一度も行われていない**。コードとテストと CI はすべて通っている
（テスト105件・CI 全ジョブ緑）が、それは今回の不具合（後述）を一つも
検出できなかったので、緑であることは確認の代わりにならない。

| 確認すること | 見るところ | 関連 |
|---|---|---|
| 画面が表示されるか | 起動直後 | 2026-09-23 に一度、真っ黒になる不具合があった |
| EDL で sofi の形が読めるか | 左パネルの「EDL」チェック | `M2-shading-and-ui.md` M2-1 |
| 点予算が上限付近から始まるか | 右パネルの点予算（約2,680万点のはず） | `ADR-0010` |
| 赤いエラーバナーが出ていないか | 画面最前面 | `ADR-0011` |

赤いバナーが出ていたら、**そこに WebGPU のエラー本文がそのまま書かれている**。
2026-09-23 以前はこれが無く、不具合が「画面が真っ黒」という情報だけになっていた。

## 2. 次の作業の入り口（どれから始めてもよい）

目視確認で問題が無かった場合の候補を、着手しやすい順に並べる。

### M2-2 カラーマップ

標高・強度・分類による着色。`M2-shading-and-ui.md` の M2-2。
sofi のような RGB を持たない点群を読むための手段として、EDL と補完関係にある。

### M2-4 ガラス面と2パス構成の描画コスト計測

**未計測の項目が2つ溜まっている。**

1. UI のガラス面（`backdrop-filter`）の fps への影響。`ADR-0005` がリスクとして
   挙げたまま、一度も測っていない
2. **EDL をオフにしても、オフスクリーンへ描いてから合成する2パス構成が常に通る。**
   M1 の頃の1パス構成には戻らない。この差も未計測

所有者は速度に敏感なので、体感で重くなっていればここが最優先になる。

### M3 リリースとアップデート

**署名鍵の生成で止まっている。** 秘密鍵は所有者が自分で生成し、GitHub Secrets に
入れる必要がある（このリポジトリには絶対にコミットしない）。`M3-release-and-update.md`。
Android 実機（OPPO Pad Air）での動作確認もここ。

### M4 変換パイプライン

`beer.laz` を使った変換コストの見積もりから。`M4-import-and-conversion.md`。

### 小さい残務

- UI シェルのレイアウトが粗い（所有者の 2026-09-23 のコメント）。`ADR-0005`
- EDL の半径（`setEdlRadiusPx`）にレンダラ API はあるが UI のスライダーが無い
- EDL の強度 1.0・半径 1.4px は Potree から借りた未検証の初期値で、
  このプロジェクトの深度レンジに合わせた調整をしていない
- 点予算まわりの調整値（世代30秒、下限4ms、変化率10%/20% など）はすべて
  未検証の初期値。実機でのチューニングが未実施

## 3. 2026-09-23 に入った変更

詳細は各 ADR にある。ここでは「何が直ったか」と「誰が確認したか」だけ。

| 変更 | 効果 | 確認の状況 |
|---|---|---|
| COPC ノードを hierarchy の offset へ直接 seek | 単スレッド5〜7倍、並列の頭打ちが8→20コア | **実測済み**（`parallel_bench` / `open_bench` を再実行して確認） |

| EDL（M2-1） | 色の無い点群の形が読める（はず） | **未確認** |
| UI シェル（M2-3） | `ADR-0005` の5面 | **未確認** |
| WebGPU エラーの可視化（ADR-0011） | バリデーションエラーを画面に出す | **未確認** |

## 4. この日に繰り返し踏んだ落とし穴

同じ形の不具合を1日に3回踏んだ。**一方向にしか動けず、回復経路を持たない設計。**

1. **ノードの読み出し** — レベル全体を空間クエリして大半を捨てる読み方から
   抜け出せず、深いレベルほど遅くなっていた（`ADR-0007` 追記）
2. **点予算** — vsync では「増やす」条件が原理的に成立せず、下がる一方だった
   （`ADR-0010`）
3. **リフレッシュ周期の推定** — 全期間の最小値を使っており、異常に短い値を
   一度拾うと永久に固定されていた（`ADR-0010` 追記3）

いずれも、**動いている間は誰も疑わない**という共通点がある。
新しく制御ループや推定を書くときは、「この値は下がったあと戻れるか」を
必ず確認すること。

もう一つ。**テストも CI も、今回の不具合を一つも検出しなかった。**
EDL の `depthStencil` 欠落は WebGPU のバリデーションエラーで、
typecheck・lint・vitest・build・CI のどこにも現れない。この穴を塞ぐために
`ADR-0011` の仕組みを入れたが、**それ自体もまだ目視確認されていない。**

## 5. 守り続けている制約

- **秘密鍵・キーストア・パスワードは絶対にコミットしない。** GitHub Secrets のみ
- **点群データ（`*.laz`, `*.copc.laz`, `/data`）はコミットしない。** gitignore 済み
- コミットの著者は GitHub の noreply アドレスを使う
- 規約1〜4（`ARCHITECTURE.md`）は CI の `invariants` ジョブが機械的に検査する
- 実装は Sonnet に委譲し、計画・診断・検証を上位モデルが持つ
- **測っていないことを「実測した」と書かない。** 過去に一度、未実施の計測結果が
  コードコメントに書かれて訂正した

# ADR-0015: エラー処理の方針（触ったところから少しずつ）

- 状態: 採択
- 日付: 2026-10-07

## 決定

**本番で panic しないこと、どんな小さなエラーも画面側で取れることを目指す。ただし一度に全体を直さず、
これから触るコードとその周りに少しずつ入れていく。**

全体を書き直す大きな作業は行わない。機能の追加や不具合の修正で触ったファイル・関数に、下の3つを当てはめる。

### 1. 自分たちのコードでは panic を書かない（予防）

- 触った関数では `unwrap`・`expect`・`panic!`・添字の範囲外アクセスなど、panic しうる書き方を `Result` を返す形に直す
- `wasm32-unknown-unknown` で使われるクレート（`crates/pcv-core`・`crates/pcv-wasm`・`vendor/copc-writer` など）では、
  ブラウザで panic する標準ライブラリの機能（`std::time::Instant::now`・`SystemTime::now` など）を使わない。
  検査できるものは clippy の `disallowed_methods` などで CI に止めさせる
- テストのコードは対象外

### 2. 境界で受け止める（安全網）

他人のクレートの中の panic や、メモリ確保の失敗は、自分たちのコードからは無くせない。そこで、Rust を呼ぶ入口で受け止める。

- デスクトップ・Android: Rust を呼ぶ入口（`pcv://`、Tauri のコマンド）で panic をエラーに変える（`pcv://` は [ADR-0013](./ADR-0013-crash-visibility.md) で済）。
  触った入口から広げる
- Web: panic のメッセージを Worker から画面へ送る。panic した wasm のインスタンスは使えなくなるので、その Worker は作り直す
- メモリ確保の失敗は捕まえられない。「メモリ不足で止まった」と分かる表示までにとどめる

### 3. エラーは画面で取れるようにする（見える化）

- 触った処理のエラーは、黙って捨てず、既存のエラー表示（[ADR-0011](./ADR-0011-gpu-error-visibility.md) のバナーとログ）に流す
- 本文はそのまま出す（要約しない）。どこで起きたかが分かる見出しを付ける
- 重大なものはバナー、軽いものはログに分け、画面を埋め尽くさない

## 背景

2026-10 に、Web 版の変換が `unreachable` とだけ表示されて止まった。原因は `vendor/copc-writer` の通常の経路が
`Instant::now()` を呼んでいたことで、wasm では panic する。**本当の原因は開発者ツールの Console にしか出ておらず**、
所有者に Console を開いてもらって初めて分かった。それまでコーディネーターはメモリ不足と誤って見立てていた。

同じ時期に、テストも CI もすべて緑のまま、v0.1.3 のデスクトップ版・Android 版でノードが1つも読めない不具合も出ている。
**緑であることは、実際に動くことを保証しない。** 動かしたときに出たエラーが画面で見えることが、原因を突き止める一番の近道になる。

所有者はこの方向に賛成したうえで、「規模が大きすぎるので、これから触るコードと周辺に入れていく」形を選んだ。

## 帰結

- 古いコードには panic しうる書き方が残る。触ったときに直す
- エージェントへの依頼では、この ADR を読ませ、触った範囲に当てはめさせる
- 一度に全部を直さないので、どこまで当てはめ済みかは揃わない。それで構わないとする

## 却下した案

- **全体を一度に直す**: 規模が大きく、他の作業と衝突しやすい。所有者が退けた
- **何もしない**: 原因が Console にしか出ない状態が続き、不具合の調査に所有者の手間がかかる

## 文脈

所有者の依頼（2026-11-16）: 初回の読み込みが遅い。メモリに余裕があるなら、先にメモリに乗せて描き、あとから変換（ディスクへの書き出し）が追いついてメモリが減るようにしたい。
ただし、アプリが落ちるなど UX を損なう挙動は避ける。

### 測ったこと（[BENCH-first-open.md](./BENCH-first-open.md)。i5-14600K、P コア固定、実 GPU）

| 場面 | 結果 |
|---|---|
| COPC を開く（Web、80 MB〜4.2 GB の 3 ファイル） | 開けるまで 0.11〜0.18 秒、最初のノードが GPU に載るまで 0.18〜0.28 秒、全部見えるまで 0.7〜2.1 秒。ファイルの大きさにほぼ依らない |
| COPC を開く（Rust、ヘッダーと階層） | 6〜55 ms |
| LAS 1 枚（620 万点）の変換 | ネイティブ 約 2〜6 秒、Web 約 4.4 秒（そのあと 1 秒ほどで全部見える） |
| LAS 55 枚（3.48 億点）の変換 | **ネイティブ 220 秒**（読み込み 81、LOD 107、圧縮 8）。何も出ない。private ピーク 309 MiB |
| LAS 10 枚（6,700 万点）の変換（Web） | **73.8 秒**。何も出ない。ブラウザ全体の private ピーク 1.7 GiB |
| LAS 55 枚（Web） | 開始前に「空き容量が足りません」（一時領域の quota 10 GiB） |
| 点が入ってくる速さ（ネイティブ） | LAS 約 430〜500 万点/秒、LAZ 約 300 万点/秒。最初の 1% は 0.07〜0.21 秒 |
| COPC を開いたあとに実際に描く点 | 79 万〜200 万点（autzen・sofi・shibuya） |

読み取れること:

1. **遅いのは COPC ではなく、変換が終わるまで何も出ないこと。** COPC は既に十分速い。変換される入力（LAS/LAZ/PLY/PCD/E57）が問題
2. 変換の時間の多くは LOD の索引（ネイティブ 49%）と圧縮（Web 63%）で、読み込みではない。点は変換の最初の 0.1 秒から手元に流れてきている
3. 画面が 1 度に描く点は 100〜200 万点で足りている。**下見として全点を持つ必要は無く、数百万点で十分**
4. メモリは今も余裕がある側にある: 変換のピークはネイティブ 309〜492 MiB（1 枚は回によって約 370〜480 MiB）、レンダラのキャッシュ予算は 1 GiB（デスクトップ）。Web は変換中に 1.7 GiB（10 枚）まで増える

## 決定（提案）

**案 (a) を採る。** 変換と並行して、読み込んだ点から一様に間引いた「下見の点」を持ち、仮のレイヤーとして描く。変換が終わって COPC のレイヤーが描けたら、下見を捨てる。
そのために**レンダラに「レイヤーの階層の差し替えとノードの無効化」の口を足す**（下の「レンダラに足す口」。コーディネーターの判断 2026-11-16、PF-0 監査 F-2）。
案 (c)（COPC の初回表示の改善）は、PF-0 の計測では不要。案 (b) は採らない（理由は下）。

### 全体の流れ

```
ファイルを選ぶ
  ├─ すぐ: ヘッダーから範囲（bounds）が分かる（55 枚でも 0.03 秒）。カメラを範囲に合わせ、各タイルの範囲の枠と「変換中」を出す
  ├─ 変換を始める（今と同じ。copc-writer の out-of-core。ADR-0019 は変えない）
  │    └─ 読み込みの途中で、一様に間引いた点を「下見の保管庫」にためる
  ├─ 最初の数万点がたまったら、仮のレイヤー（下見）を足して描く。以後は階層の差し替えで細かくなる（レイヤー ID は変えない）
  └─ 変換が終わる
       ├─ COPC のレイヤーを足す（今の addOpenedLayer）。カメラは動かさない。このとき**下見はまだ消さない**
       ├─ COPC 側が「下見と同じくらい描けた」と判断できたら下見を消し、保管庫を捨てる（メモリを返す）
       │    条件（どちらか早いほう）: COPC のレイヤーの描画点数 c が、**今の点予算 B の 1/2 以上**になる（下見の上限が B の 1/2 以下なので、c ≥ B/2 なら下見より疎にならない）／COPC のレイヤーの loading==0 && queued==0。
       │    どちらもレイヤーごとの統計で判定する（下の「レンダラに足す口」の `getLayerStats`）
       └─ 失敗・中止なら: 下見は残す。エラーは既存の表示（ADR-0011）に出す。「下見のみ・変換は失敗」と表示する
```

切り替えを「COPC の最初のノードが描かれたら」にしない理由（F-3）: 実測で COPC の最初の描画は 8.4〜11.8 万点、下見は最大で数百万点なので、その瞬間に点が 1/30 ほどにまばらになる。
**点予算 B は全レイヤーで共有**（`selectNodesForLayers` が全レイヤーの候補を 1 つの予算で選ぶ）なので、COPC の描画点数 c と下見の描画点数 p は c + p ≤ B。
したがって「c が p 以上」は p ≤ B/2 のときしか起きない。そこで**下見の上限を `pointBudgetMax` の 1/2 にし**（下の「メモリ」）、比べる相手は**今の点予算 B の 1/2**にする（B は自動調整で上下する。`getPointBudget()` で読める）。
loading==0 && queued==0（そのレイヤーの読み込みが尽きた）が先に来る場合は、COPC のレイヤーがそれ以上細かくならないので、そこで切り替える。
両方を描いている間も GPU のメモリは増えない: `NodeCache` は全レイヤーで共有で、点予算の中に収まる（下見のノードも COPC のノードも同じ予算から追い出される）。
下見の点は COPC の点の部分集合で座標が同じなので、重ねて描いても見た目は変わらない。

### レンダラに足す口（F-2。今のレンダラのままでは下見が細かくならない）

今のレンダラは、`addLayer` の `LayerInput.hierarchy` を固定で持つ（`Layer.hierarchy`・`hierarchyByKey`・`sceneBounds` はそのとき一度だけ作る）。
`NodeCache` はキーで GPU バッファを持ち続け、キーを指定して捨てる口が無い（`removeByPrefix` はレイヤーを消すときだけ）。ノード選択は階層の `pointCount` に頼る。
つまり、そのままでは下見は**最初の 1 回の中身から細かくならない**（以前の草稿の「レンダラは変えずに」は誤りだった）。

案（コーディネーターが (ii) を採った。(i) は、下見を消して新しいレイヤーを足し直す案。レイヤー ID が変わり、ADR-0023 のプラグインが持つレイヤーへの参照が壊れるので採らない）:

```ts
// src/renderer/point-cloud-renderer.ts に足す（形の案）
interface NodeReplacement { oldKey: string; newKey: string }
replaceLayerHierarchy(layerId: string, hierarchy: HierarchyNodeInfo[], replacements: readonly NodeReplacement[]): void;
getLayerStats(layerId: string): { drawnPoints: number; drawnNodes: number; loadingNodes: number; queuedNodes: number } | null;
```

- **規則: 中身が変わるノードは、新しいキーにする**。同じキーの中身は変えない。
  古いキャッシュを誤って使う・古い読み込みの結果が新しい中身に化ける、が構造上起きない
- **キーの形（F-12 の 2）**: `parentKey`（`node-selection.ts`）は `key.split("-")` を 4 つの整数として読むので、`3-1-2-0@g5` のような接尾辞は `NaN` になり親が `null` になる。
  ただし今のコードでは、`d-x-y-z` の形でないキーは「先祖の無いノード」として **roots に入る**（`HierarchyTree` のコメントと実装を読んだ。実行して確かめてはいない）ので、
  世代つきのキーを混ぜると、親子が切れて、粗い根と細かい子が**二重に描かれる**。
  そこで**逆にする**（最小の変更。F-19）: `HierarchyNodeInfo.key` は今までどおり**唯一の読み込み・キャッシュのキー**で、世代つきの形（`3-1-2-0@g5`）にする。
  今のコードは `key` 1 つを、選択の候補・キャッシュの検索・読み込みの要求（`keyPrefix + node.key`、`selectNodesForLayers`）、`readNode` の引数（`parseLayerNodeKey(...).nodeKey`）、
  `hierarchyByKey` の作成と検索（ダブルクリックで寄る処理など）の全部に使っているので、これらは**変えずに**済む。新しい世代と古い世代は `key` が違うので、`hierarchyByKey` の Map で片方が消えることも無い。
  足すのは、**木だけが読む欄 `positionKey?: string`**（`3-1-2-0`。世代の無い位置のキー）。`treeOf`（`node-selection.ts`）は親子を探すとき `n.positionKey ?? n.key` を使い、`parentKey()` はその値に対して呼ぶ（`parentKey` 自体は変えない）。
  `positionKey` が無いノード（COPC の通常のノード）は今までどおり `key` で探すので、既存の挙動は変わらない。
  新旧の世代が**同時に**階層にあるとき（後継が載るまでの間）は、同じ `positionKey` が重複する。`treeOf` の `indexByKey`（位置のキー → 配列の添字）は**新しい世代を優先**して登録し、子は新しい世代につなぐ
  （古い世代は、後継が載るまで描くだけの葉として扱い、後継が `NodeCache` にあれば選ばない。下の「点滅させない」）。
  `handleNodeLoaded` の「今の階層に無いキーを捨てる」確認は、`hierarchyByKey`（`key` が索引）で引くので、そのまま正しく働く（古い世代のキーが階層から外れたら、届いた結果は捨てられる）。
  `selectNodesForLayers` が候補に付ける `keyPrefix + node.key` も `key` のままなので、世代の付け方は「下見の側が、置き換えるノードに新しい `key`（`<位置のキー>@g<世代>`）と `positionKey` を付けて渡す」だけで、レンダラの選択のコードは `treeOf` のほかに変わらない。
  テストで、世代つきのノードを混ぜた階層で、親子が切れず、二重に描かれないこと、新旧が同時にあるとき子が新しい世代につながること、`hierarchyByKey` から両方引けることを確かめる
- **点滅させない（F-12 の 1）**: 新しい世代のキーはまだ GPU に無いので、古いキーをすぐ捨てると、そのセルが空になり、さらに AN-1 のフェードイン（`firstDrawnAtMs === null` から 250 ms のディザ、`animation.ts` の `nodeFadeFactor`）で 0 から出直す。
  2 回/秒の差し替えごとに下見が点滅する。そのため:
  1. 階層には、古いキーと新しいキーを**両方**入れて渡す（`replacements` で対にする）。古いキーは、新しいキーの GPU バッファが `NodeCache` に入るまで**描き続ける**（古いキーを外すのは、後継が載った時点で階層から外す側だけで足りる。選択側に「後継があれば古いほうを選ばない」という特別扱いは足さない。監査 F-23）
  2. 後継のノードが載るとき（`handleNodeLoaded`）、古いキーの `firstDrawnAtMs` を**引き継ぐ**（0 からのフェードにしない）。そのあとで古いキーを `NodeCache.remove(key)`（頂点・uniform のバッファを `destroy`、`totalPoints` を減らす）で捨て、階層からも外す
  3. 後継がなかなか載らない（読み込みが失敗した）ときは、古いキーを残したまま（見えなくならない）
- `replaceLayerHierarchy` がすること:
  1. `Layer.hierarchy`・`hierarchyByKey`・`sceneBounds` を差し替える（`elevationRange` はヘッダーの範囲から決まるので変わらない）。**`intensityRange` は広げるだけで、狭めない・`null` に戻さない**（F-17。残るノードは読み直されないので、範囲を変えると色が跳ぶ）。カメラは動かさない。グリッドは `updateGridFromVisibleLayers` で合わせ直す
  2. `replacements` の古いキーの読み込み中・待ちを取り消す（新しい口 `NodeLoader.cancel(key)`）
  3. **新しく足す確認（F-16）**: `handleNodeLoaded` は、今は通し番号で消えたレイヤーかどうかだけを見る（`point-cloud-renderer.ts` の `handleNodeLoaded`）。ここに「キーが今の階層に無ければ捨てる」を足す。取り消しに間に合わず届いた古い結果をこれで捨てる（今のコードにある確認ではない）
- **レイヤーごとの統計（F-13）**: `RenderStats` は全レイヤーの合計しか持たない。`getLayerStats(layerId)` で、そのレイヤーの描画点数・描画ノード数・読み込み中・待ちを返す（`updateStats` の集計でレイヤーごとにも数える）。切り替えの条件の判定に使う
- 無効になるもの: ノード選択の結果（次のフレームで階層から作り直す。キャッシュしていない）、統計（次の更新で正しくなる。最大 500 ms の遅れ）、古いキーの GPU バッファ（上の手順で）。
  idle-boost・点予算の自動調整・他のレイヤーには触らない
- 呼ぶ頻度は 1 秒に数回まで（下の「状態の流れ」）。数百〜数千ノードの配列を渡すだけ（ノード数に比例する処理は既にフレームごとにある）
- テスト（vitest、GPU なし）: 差し替え後に、後継が載るまで古いキーが選ばれ続ける／後継が載ったら古いキーが選ばれず `destroy` される／後継が `firstDrawnAtMs` を引き継ぐ（フェードが 0 に戻らない）／
  世代つきのノード（`key` は `…@g5`、`positionKey` は `d-x-y-z`）が混ざっても木の親子が切れず、二重に描かれない／新旧が同時にあるとき子が新しい世代につながる／`hierarchyByKey` から新旧の両方が引ける／取り消しに間に合わなかった古い結果が捨てられる／`intensityRange` が狭まらない／`getLayerStats` がレイヤーごとの値を返す／既存の `addLayer`・`removeLayer` が変わらない。実 GPU での確認は別（未確認）

ADR-0023 の `LayerApi` での見え方: プラグインには `layers.addProvisional(options)` が `ProvisionalLayerHandle`（`id`・`grow(nodes, replacements)`・`finish(finalLayerId)`・`discard()`）を返す形にし、`replaceLayerHierarchy` はホストの中にしまう。
下見は「開く」の中核の一部でプラグインではないが、同じ口を ADR-0023 の将来のプラグイン（途中経過を出すツール、表示範囲で中身が変わるレイヤー）が使える。
一覧には `provisional: true` を持たせ、「下見」の印を出す（下の「ADR-0022/0023 との整合」）。

### 下見の持ち方

- **平らな 16×16 の問題（F-21）**: 下見を平らなセルの集まりにすると、見下ろした画面でも、下見が最大 1,342 万点（cap）の**全部**を描こうとする（点予算の半分まで。COPC は同じ画面を 79 万〜200 万点で描いている）。
  LOD が無いので、画面の大きさに合わせて減らせない。PF-1 で、下見あり・なしの fps を見る（AC に入れる）か、**最初から 2 段の階層（根＝粗い間引き、子＝細かい点）にして**レンダラの LOD で画面に必要な分だけ描かせる。後者を勧める（根と子の点は同じ入れ子の間引きから作れる）

- 保管庫は **ノード形式（`node-format`、1 点 20 B）のバッファそのもの**で持つ。`readNode(key)` は保管庫のバッファを返すだけの小さなリーダー
- 間引きは、**点の通し番号のハッシュの下位ビット**で決める（`hash(i) % 2^k == 0` なら残す）。k が大きいほど粗い。
  粗くするときは、残っている点から `hash(i) % 2^(k+1) != 0` の点を捨てるだけで、点が全体に一様に残る（入れ子）。走査順に並んだ入力でも、読んだ範囲では一様
- 空間への割り振りは、ヘッダーの bounds を一定の格子（例: 水平 16×16）に切り、セルごとに 1 ノードにする。
  セルの点が増えたら新しい世代のキーで置き換える（`replacements` に古いキーと新しいキーを対にして渡す。上の「点滅させない」の手順）。1 回の差し替えで置き換えるセルは、変わったものだけ
- k の初期値は、ヘッダーの総点数から決める: 最終的な下見の点数が目標（下の「メモリ」）になるように `k = ceil(log2(総点数 ÷ 目標))`。
  総点数が 100 万点以下の入力は下見を出さない（変換が数秒で終わる。BENCH の 6.2M 点でも 2〜6 秒）
- 複数ファイル（55 枚）は、ファイルを順に読むので、下見は**読み終えたタイルから**広がる（最初は 1 枚ぶんだけ）。範囲の枠は最初から全部出す。
  全体を最初から粗く見せたい場合は、LAS（非圧縮）に限り各ファイルから間引いて読む「下見だけの先読み」が考えられるが、
  読み取り量が入力のほぼ全部（12 GB）になりうるので、PF-1 で測ってから決める（未測定）
- 読み込みの終わり（55 枚で 81 秒）から変換の完了（220 秒）までの約 140 秒は、下見が変わらない（F-10）。
  この間は、各タイルの範囲の枠（ヘッダーの確認 `summarize_headers` の結果で最初から出せる）と「細部を準備中（経過 xx 秒）」を出す。
  変換の後半は割合が取れない（`PostProcessing` の通知だけ。`streaming.rs` のドキュメント参照）ので、割合は出さず経過時間だけにする（割合を出すには変換側にフックが要り、PF-1 の範囲外）

### 変換のどこに足すか（F-4）

デスクトップの変換の入口は**4 つに分かれている**。下見の点を取る口は、それぞれの読み込みの出口に要る:

| 経路 | 関数 | 口を足す場所 | 補足 |
|---|---|---|---|
| 単一の LAS/LAZ | `pcv_convert::streaming::convert_and_timings` | `BatchedLasPoints`（64Ki 点ごとのバッチ） | 本番の単一ファイル。`on_progress` は件数しか渡さない |
| 複数の LAS/LAZ（渋谷 55 枚はここ） | `pcv_convert::merge::merge_paths_and_timings` | `MultiFileLasPoints` の読み出し | 別の読み手。入力ごとに CRS・スケールの合わせ直しがある |
| 形式が混在 | `pcv_convert::import::merge::convert_paths_to_copc_and_timings` | 形式ごとの読み手の出口 | |
| PLY/PCD/E57 | `pcv_convert::import::convert_to_copc_and_timings` | `import::convert` の読み込みループ（このクレート側にある） | |
| Web（全形式） | `crates/pcv-wasm`（`convert`・`point_file_import`・`point_merge` など） | TypeScript が回すバッチの出口（Worker から取り出す） | `pcv-wasm` は `pcv-convert` に依存できず、読み手が別（ADR-0020） |

どの経路も「読み込んだ点（座標・色などを含む 1 バッチ）を、変換とは別に 1 回だけ見るコールバック」を足す形で、ADR-0019 の分割・LOD・圧縮には触れない。
ただし、口が **5 か所**に要り、点の座標系（スケール・オフセット、複数ファイルでの合わせ）を下見のバッファに直す処理が経路ごとに要る。
このため実装の大きさは **中〜大**（以前の草稿の「小〜中」は過小だった）。**範囲の分け方（コーディネーターの判断）**: PF-1 は**単一 LAS/LAZ（デスクトップと Web）に絞る**。PF-1 で、下見の点を受ける型（例 `PreviewSink`）を `pcv-convert` に 1 つ定義し、
複数 LAS（10 枚・55 枚。`merge_paths_and_timings`）は直後の PF-2 で同じ型を使って足す。形式が混在する経路と PLY/PCD/E57 は、入口を統合するリファクタリングと一緒にやる。

**構成の負債**: 変換の入口がデスクトップで 4 経路、Web で別の読み手と、計 5 つに分かれていて、同じ「読み込みの出口」が 5 回要る。
下見を足すと 5 つの口が増えて負債が広がる。経路を 1 つの「点の源（`PointSource`）」に寄せるリファクタリングを、PF-1 の前に別タスクとして起こすことを勧める
（ADR-0020 が言う「重複する読み手を減らす」と同じ方向）。寄せずに進める場合の分け方は、上のとおり（PF-1 は単一 LAS/LAZ、PF-2 で複数 LAS）。

### メモリ（AC-4。F-5: 固定の上限ではなく、空きに応じて増やし、逼迫したら手放す）

所有者の依頼は「メモリに余裕があれば先に使う」。そこで下見の上限は固定にせず、空きメモリに応じて決める。メモリを使うものは下見だけではない:

| 使うもの | 大きさ | 出どころ |
|---|---|---|
| 下見の保管庫 | 点数 × 20 B（下の目標で決まる） | この ADR |
| `NodeCache`（GPU に載せた点） | デスクトップ最大 1 GiB（`pointBudgetMax` 約 2,684 万点 × 20 B × 2）。モバイルは deviceMemory ÷ 64 | `device-profile.ts` |
| 変換の中のメモリ | ADR-0019 の既定で、小さな部分木をメモリで仕上げる予算が約 1 GiB。実測の private ピークは 309〜492 MiB（1 枚は回によって約 370〜480 MiB。上は監査役の再計測値） | ADR-0019、BENCH-first-open |
| Web の変換 | ブラウザ全体の private で 1 枚 974〜1,040 MiB、10 枚 1,696 MiB（wasm32 の 4 GiB の上限が別にある） | BENCH-first-open |

**デスクトップ（空きメモリが取れる）**:

- 空きメモリ A（利用可能な物理メモリ）を、`GlobalMemoryStatusEx` の `ullAvailPhys` で取る。Windows は `pcv-convert` が既に依存する `windows-sys` に `Win32_System_SystemInformation` の feature を足すだけ（新しい依存は無い）。
  Linux/Android は `/proc/meminfo` の `MemAvailable`（Android でも読める）。macOS は対象外（今のところ出していない）
- 下見の目標点数 `cap = clamp(A × 4% ÷ 20 B, 50 万点, pointBudgetMax ÷ 2)`。例: A = 25 GiB なら 1 GiB ÷ 20 B で 5,300 万点だが、`pointBudgetMax` の 1/2、約 1,342 万点（268 MB）で止める（推定の例。実機で確かめていない）。A = 4 GiB なら 約 860 万点
- **上限を `pointBudgetMax` の 1/2 にする理由**: レンダラは点予算（最大でも `pointBudgetMax`）を超えて描かない。それを超えて下見を持っても画面には出ない。さらに点予算は全レイヤーで共有なので、切り替えの間に COPC と下見が同時に描かれると、下見は予算の半分までしか描けない（上の「切り替え」）。
  さらに、最初の画面で実際に描く点は 79 万〜200 万点（BENCH）。カメラを寄せて点予算を使い切るまで細かく見る（idle-boost）ときだけ、2,000 万点台が効く。
  よって「余裕があるほど増やす」効果は、空きが数 GiB を超えたあたりで頭打ち（上の例のとおり。1,342 万点まで）。それ以上の余裕は、変換とキャッシュに残すのが正しい
- **変換の中のメモリ予算は、変換を始めるときに決める（F-14。コーディネーターの判断）**: ADR-0019 の「メモリで仕上げる部分木の予算」は、writer に開始時の `u64`（`memory_budget_bytes`）で渡され、一度だけ割って使う（`vendor/copc-writer/src/writer.rs`）ので、変換の途中では変えられない。
  vendor は変えず、**変換を始めるときの空きメモリ A から予算を決める**（A が小さければ既定の約 1 GiB より小さい値を渡す。式の案: `min(1 GiB, A × 10%)`。推定）。途中の逼迫には、下の 1・2（下見と `NodeCache`）だけで応える
- 手放す順（A を 5 秒ごとに見る。閾値は推定で、PF-1 で実機に合わせる。`total` は物理メモリの合計）:
  1. A < max(2 GiB, total の 10%): **下見を 1/2 に**（k+1。入れ子なので捨てるだけ）
  2. A < max(1 GiB, total の 5%): **`NodeCache` を縮める**（`setPointBudget` で点予算を下げる。これは既存の口）。下見はさらに 1/2。
     A < 512 MiB: 下見は捨てて、仮のレイヤーを消し、進捗の表示だけに戻る（変換は続ける。変換のメモリは開始時に小さめに決めてあるので、途中で減らせなくても落ちない見込み。未検証）
  A が戻ったら、下見は増やさない（一度捨てた点は取り戻せない。変換が終われば COPC が出る）。`NodeCache` の点予算は、既存の自動調整（ADR-0010）が戻す
- 下見が増やすメモリは、最大でも A の 4%（上の式）。他の使い手（キャッシュ、変換）が先に足りなくなる前に下見が手放す順になっている

**Web/Android**: 空きメモリは取れない（`performance.measureUserAgentSpecificMemory` はクロスオリジン分離が要り、GitHub Pages では使えない）。`navigator.deviceMemory`（丸めた値）しか無い。
Web は**変換のメモリ（ブラウザ全体で 1.0〜1.7 GiB、wasm32 の 4 GiB の上限）が先に問題になる**。下見は wasm のヒープの外（Worker の外の JS ヒープ）に置き、
点数を `min(400 万点, pointBudgetMax の 1/2)`（`pointBudgetMax` の 1/2 は、切り替えの条件のためでもある。400 万点 × 20 B = 80 MB。ブラウザ全体の 1.0〜1.7 GiB に対して約 5〜8%。モバイルは約 84 万点で 17 MB）に固定して、
**変換のメモリを悪化させない**。Web の変換は一時領域の quota（実測 10 GiB）が先に尽きるので、下見のために断るケースは増えない。メモリの少ない端末での確認は未実施。

### ADR-0022/0023 との整合（F-6）

- **下見のレイヤーの扱い**: 下見のレイヤーは `provisional: true`（一覧に「下見」の印）。レイヤーを元にするツール（計測・土量・断面・ラスタ・間引き・フィルタ・DTM・結合）は、
  **下見には走らせない（ボタンをグレーアウトし「変換が終わるまで使えません」と出す）**。理由: 下見は点の一部なので結果が全点と食い違い、ADR-0018 の「選んだレイヤーから新しいレイヤーを作る」の元になれない。
  警告つきで走らせる案は、間違った土量が保存されうるので採らない。表示の設定（着色・EDL・点の大きさ）は下見にも効かせる
- **レイヤー ID は差し替えで変えない**（F-2 の (ii)）。COPC が描けたあと、下見のレイヤーを消して COPC のレイヤーを残す（COPC のレイヤーの ID は新しい）。
  プラグインが持つ下見の ID は `finish(finalLayerId)` で COPC の ID に付け替える通知を受ける
- **変換の途中で利用者が下見のレイヤーを消したら、変換を中止する**（`cancelConversion`）。消す前に「変換も中止します」と確認を出す（変換が止まるのを知らずに消さないように。ダイアログの形は HANDOFF 5 章に従う）。変換の ID を持ち、中止後に届く `conversionFinished` は、その ID の下見が無ければ**捨てる**
  （R11 の `prepareToOpen` は `cancelled` で返る。完了が先に届いた場合の競合は、`update` が「その ID の下見が一覧に無ければ COPC を足さない」とするだけで済む）
- **状態の流れ**（ADR-0022）: Model は `{ conversionId, phase, previewPoints, previewLayerId | null }`、Msg は `previewStarted`・`previewGrew`・`conversionFinished`・`conversionFailed`・`previewDiscarded`、
  Effect は保管庫への追加・`replaceLayerHierarchy`・`cancelConversion`。
  `previewGrew` は**間引く**: 保管庫への追加は毎バッチ（約 66 回/秒＝430 万点/秒 ÷ 64Ki）でよいが、Msg を `dispatch` するのは最大 2 回/秒（統計の更新と同じ 500 ms）。
  差し替え（`replaceLayerHierarchy`）も同じ頻度で、最後の 1 回だけが効く（間のものは畳む）。遷移（失敗しても下見が残る、中止後の完了を捨てる）は `update` の純粋な関数として vitest で確かめられる

### PF-1 の受け入れ基準の案（F-7。変えられる数値の線）

PF-1（単一 LAS/LAZ。デスクトップと Web）の AC の案。入力は `data` にある大きな単一ファイルから選ぶ: `beer.laz`（LAZ、66,848,096 点、470 MB。LAS 1.2 点形式 2）が最大の単一 LAS/LAZ（`data/` を確認した）。
渋谷の 1 枚（620 万点、LAS）も測るが、変換が 2〜6 秒で終わるので効果は小さい（下見を出さない閾値 100 万点より上だが、利用者にとっては待ちが短い）。意味のある確認は `beer.laz` 級のファイルで行う。

1. 最初の点まで（ファイルを渡してから、最初の下見の点が描かれるまで）: **ネイティブ ≤ 1 秒、Web ≤ 2 秒**。`beer.laz`（Web は quota と時間で開けるか PF-1 の最初に確かめる。開けなければ渋谷 1 枚と、先頭 数枚を 1 枚に結合した LAS で代える）と渋谷 1 枚、P コア固定、各 3 回の最大値。「最初のノードが載った時刻」で測る（統計の 500 ms の粗さを避ける）
2. 下見ありの変換時間は、下見なしの **+5% 以内**（同じ入力・同じ日・P コア固定、3 回の中央値。BENCH の `beer.laz` 30.3 秒なら +1.5 秒）
3. 下見の CPU 側の private の増分: 目標点数 × 20 B の **1.2 倍以内**（デスクトップの cap は最大 1,342 万点＝268 MB なので上限は約 322 MB。Web の 400 万点なら 96 MB。測り方は BENCH と同じ private）
4. 切り替え: COPC への切り替えの前後で、描画点数が点予算 B の 1/2 を**下回らない**か、COPC の読み込みが尽きている（レイヤーごとの統計の記録で。画面の確認も）
5. 中止・失敗: 失敗すると下見が残り、エラーが既存の表示に出る。下見を消す前に確認が出て、消すと変換が中止される。後から届いた完了は捨てられる（`update` の遷移として vitest）
6. メモリ: 空きを人工的に減らした状態（大きなダミーの確保）で、下見が手放す順（1 → 2）に従い、アプリが落ちない（`update` の遷移の vitest と、実機での確認）。変換のメモリ予算が開始時の空きから決まる（関数の vitest）
7. 下見あり・なしで、見下ろした画面の fps を比べる（F-21。平らな階層なら必須。2 段の階層にした場合も確認する）
8. レンダラの口（`replaceLayerHierarchy`・`getLayerStats`・`NodeCache.remove`・`NodeLoader.cancel`）の vitest（上の「テスト」。点滅しない・二重に描かない・フェードを引き継ぐ・`intensityRange` が狭まらない）が緑。実 GPU の確認は未確認として手順を残す

PF-2（複数 LAS。`PreviewSink` を `merge_paths_and_timings` に足す）の AC の案:

1. 渋谷 10 枚・55 枚（デスクトップ）で、最初の点まで ≤ 1 秒、各 3 回の最大値。Web の 10 枚は ≤ 2 秒（Web の 55 枚は quota で開けない）
2. 最初の 1 秒以内に、各タイルの範囲の枠と「全体の x%（読み終えたタイルの割合）」が出る
3. 変換時間 +5% 以内（55 枚 220 秒なら +11 秒）、private の増分の上限は PF-1 と同じ式

### 案の比較（AC-3）

### 壊れやすい所（未検証）

1. **平らな階層と、中身が変わるノード**: (1) レンダラが、点を持たない根の無い平らなノードの集まりを階層として受けるか。コードを読むと、`d-x-y-z` 形でないキーや先祖の無いノードは roots に入る作りなので受けられそうだが、実行して確かめていない（未確認）。
   受けなければ、下見は「根 1 つ＋ 8 の子」の 2 段にする。(2) 中身が変わるノードは新しいキー（世代つき。位置のキーとは別に持つ）にする規則と、`replaceLayerHierarchy`・`NodeCache.remove`・`NodeLoader.cancel`、後継が載るまで古いキーを描く手順、フェードの引き継ぎを守って、
   点滅・二重描画・古い GPU バッファ・古い読み込みの結果が残らないこと。どちらも PF-1 の最初に小さな試作と vitest で確かめる
2. 下見から COPC へ**途切れずに**切り替わること（切り替えの条件は上。画面での確認が要る。未確認）
3. 複数ファイルで、下見が最初は 1 枚ぶんしか出ない（上記）。「変換中、全体の x% が見えています」の UX
4. 変換中に下見を描くことで CPU/GPU を取り合い、変換が遅くなる可能性（AC 2 で測る。未測定）
5. 入力の点の順序が偏っていると、密度は一様でも見える範囲が偏る
6. Tauri のアプリそのものでの時間（PF-0 はネイティブを example で、Web を実ブラウザで測った）
7. 空きメモリの閾値は推定。`GlobalMemoryStatusEx` の値が、OS のキャッシュ（ファイルキャッシュ）を空きに含める点が実際の逼迫とずれる可能性

## 採らなかった案

- **全点をメモリに読んでから描く**: 数億点で点数に比例して落ちる（CLAUDE.md「メモリが点数に比例しないこと」）
- **変換を速くするだけ**: 55 枚で 220 秒、Web 10 枚で 74 秒の待ちは、LOD の索引と圧縮が主で、1/10 にするのは別の大きな仕事。待ちの間に何も見えないこと自体は変わらない
- **案 (b)**: 上の表
- **下見を消して COPC を足し直すだけの案 (i)（レンダラを変えずに、ID を変える）**: 下見が最初の中身から細かくならず（階層が固定）、ID が変わるのでプラグインの参照が壊れる。
  (ii)（階層の差し替え）は汎用の口になり、他の用途にも使える

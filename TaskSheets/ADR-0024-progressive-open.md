## 文脈

所有者の依頼（2026-11-16）: 初回の読み込みが遅い。メモリに余裕があるなら、先にメモリに乗せて描き、あとから変換（ディスクへの書き出し）が追いついてメモリが減るようにしたい。
ただし、アプリが落ちるなど UX を損なう挙動は避ける。

### 測ったこと（[BENCH-first-open.md](./BENCH-first-open.md)。i5-14600K、P コア固定、実 GPU）

| 場面 | 結果 |
|---|---|
| COPC を開く（Web、80 MB〜4.2 GB の 3 ファイル） | 開けるまで 0.11〜0.18 秒、最初のノードが GPU に載るまで 0.18〜0.28 秒、全部見えるまで 0.7〜2.1 秒。ファイルの大きさにほぼ依らない |
| COPC を開く（Rust、ヘッダーと階層） | 6〜55 ms |
| LAS 1 枚（620 万点）の変換 | ネイティブ 約 2〜6 秒、Web 約 4.4 秒（そのあと 1 秒ほどで全部見える） |
| LAS 55 枚（3.48 億点）の変換 | **ネイティブ 220 秒**（読み込み 81、LOD 107、圧縮 8）。何も出ない。private ピーク 309 MiB |
| LAS 10 枚（6,700 万点）の変換（Web） | **73.8 秒**。何も出ない。ブラウザ全体の private ピーク 1.7 GiB |
| LAS 55 枚（Web） | 開始前に「空き容量が足りません」（一時領域の quota 10 GiB） |
| 点が入ってくる速さ（ネイティブ） | LAS 約 430〜500 万点/秒、LAZ 約 300 万点/秒。最初の 1% は 0.07〜0.21 秒 |
| COPC を開いたあとに実際に描く点 | 79 万〜200 万点（autzen・sofi・shibuya） |

読み取れること:

1. **遅いのは COPC ではなく、変換が終わるまで何も出ないこと。** COPC は既に十分速い。変換される入力（LAS/LAZ/PLY/PCD/E57）が問題
2. 変換の時間の多くは LOD の索引（ネイティブ 49%）と圧縮（Web 63%）で、読み込みではない。点は変換の最初の 0.1 秒から手元に流れてきている
3. 画面が 1 度に描く点は 100〜200 万点で足りている。**下見として全点を持つ必要は無く、数百万点で十分**
4. メモリは今も余裕がある側にある: 変換のピークはネイティブ 309〜492 MiB、レンダラのキャッシュ予算は 1 GiB（デスクトップ）。Web は変換中に 1.7 GiB（10 枚）まで増える

## 決定（提案）

**案 (a) を採る。** 変換と並行して、読み込んだ点から一様に間引いた「下見の点」を持ち、仮のレイヤーとして描く。変換が終わって COPC のレイヤーが描けたら、下見を捨てる。
案 (c)（COPC の初回表示の改善）は、PF-0 の計測では不要。案 (b) は採らない（理由は下）。

### 全体の流れ

```
ファイルを選ぶ
  ├─ すぐ: ヘッダーから範囲（bounds）が分かる（55 枚でも 0.03 秒）→ カメラを範囲に合わせ、「変換中」の表示
  ├─ 変換を始める（今と同じ。copc-writer の out-of-core。ADR-0019 は変えない）
  │    └─ 読み込みの途中で、一様に間引いた点を「下見の保管庫」にためる（上限つき）
  ├─ 下見の保管庫が最初の数万点たまったら、仮のレイヤー（下見）を足して描く
  │    └─ 変換が進むほど、描ける範囲・密度が増える（再配置はしない。追加だけ）
  └─ 変換が終わる
       ├─ COPC のレイヤーを足す（今の addOpenedLayer）。カメラは動かさない
       ├─ COPC の最初のノードが描かれたら、下見のレイヤーを消し、保管庫を捨てる（メモリを返す）
       └─ 失敗・中止なら: 下見は残す。エラーは既存の表示（ADR-0011）に出す。「下見のみ・変換は失敗」と表示する
```

### 下見の持ち方

- 保管庫は **ノード形式（`node-format`、1 点 20 B）のバッファそのもの**で持つ。レンダラは `LayerInput`（階層と `readNode`）しか見ないので、
  保管庫から `readNode` を返す小さなリーダーを渡せば、レンダラは変えずに仮のレイヤーを描ける（未検証: 下の「壊れやすい所」の 1）
- 間引きは、**点の通し番号のハッシュの下位ビット**で決める（全点について `hash(i) % 2^k == 0` なら残す）。k が大きいほど粗い。
  こうすると「粗くする」は、残っている点から `hash(i) % 2^(k+1) != 0` の点を捨てるだけで済み、点が全体に一様に残る（入れ子になる）。
  入力が LAS/LAZ のように走査順に並んでいても、番号で間引くので、読んだ範囲では一様
- 空間への割り振りは、ヘッダーの bounds を一定の格子（例: 水平 16×16、高さは 1 層の 1 段）に切り、セルごとに 1 ノード（最大 5 万点程度）にする。
  ノードがいっぱいになったらそのセルだけ粗くする（セルの中で k を上げる）
- 複数ファイル（55 枚）は、ファイルを順に読むので、下見は**読み終えたタイルから**広がる（最初は 1 枚ぶんだけ）。
  範囲の枠だけは最初から出す。全体を最初から粗く見せたい場合は、LAS（非圧縮）なら各ファイルから間引いて読む「下見だけの先読み」が考えられるが、
  読み取り量が入力のほぼ全部（12 GB）になりうるので、PF-1 で測ってから決める（未測定）

### 上限と落ちないための仕組み（AC-4）

| 項目 | 値 | 根拠 |
|---|---|---|
| 下見の最大点数 | `min(400 万点, レンダラの pointBudgetMax の 1/2)` | 実際に描く点は 79 万〜200 万点（BENCH）。デスクトップの `pointBudgetMax` は約 2,684 万点（1 GiB ÷ 20 B ÷ 2、device-profile.ts）なので 400 万点。モバイル（deviceMemory 4 GiB）は 4 GiB÷64÷20 B÷2 で約 168 万点 → 下見は約 84 万点 |
| 下見のメモリ | 最大 400 万点 × 20 B = **80 MB**（モバイル 約 17 MB） | 上の点数から。GPU のキャッシュにも同じ点が載るので、合計は最大でこの約 2 倍（推定。レンダラが CPU 側のバッファを残すかは未確認） |
| 追加の保管庫の置き場所 | デスクトップ: Rust 側（`pcv://` が返す。IPC で 80 MB を渡さない）。Web: Worker の外の JS ヒープ（wasm32 の 4 GiB に入れない） | ADR-0007・ADR-0012 |
| 粗くする（k を 1 上げる）条件 | 下見が最大点数に達したとき（全体を 1/2 にして続ける。ためた点は一様に残る） | 入れ子の間引き |
| メモリが逼迫したときの手放し方 | デスクトップ: 起動時と変換中 5 秒ごとに OS の空きメモリを見る。**空き < 1.5 GiB で下見を 1/2 に**、**< 0.75 GiB で下見を捨て**、仮のレイヤーを消して進捗の表示だけに戻る（変換は続ける）。Web: 空きは取れないので、固定の上限だけ（下の注） | 変換のピークは実測でネイティブ 309〜492 MiB（Web 0.7〜1.7 GiB）。その 1.5 倍の余裕を残す。数値は推定で、PF-1 で実機に合わせて調整する |
| 変換が止まったとき | 下見は残す。保管庫は、そのレイヤーを閉じるまで持つ | R11 の「失敗したら failed を返す」を変えない |

注（Web）: ブラウザは空きメモリを返さない。`navigator.deviceMemory`（丸めた値）と、ブラウザ全体の private の実測（10 枚の変換で 1.7 GiB）から、
下見の上限を上の式の固定値にとどめる。Web の変換はもともと一時領域 10 GiB（実測の quota）が先に尽きるので、下見が増やすメモリが先に問題になる場面は
測った範囲では無い（未確認: メモリの少ない端末）。

### 変換への変更点（最小）

- `pcv_convert::streaming` の `BatchedLasPoints`（64Ki 点ごとのバッチ）に、点を見るコールバックを 1 つ足す。ADR-0019 の分割・LOD・圧縮には触れない
- Web は変換を TypeScript が小さなバッチで進める（ADR-0020）ので、同じ場所で下見の点を Worker から取り出せる
- 状態は ADR-0022 の形（Model: 下見の点数・段階、Msg: `previewGrew`・`conversionFinished`・`conversionFailed`、Effect: 保管庫への追加・仮レイヤーの追加と削除）。
  ADR-0023 の `layers`（足す・消す）と `tools`（進捗）の API で書ける。下見は「開く」の中核の一部で、プラグインではない

### 案の比較（AC-3）

|---|---|---|---|
| 最初の点までの時間 | ネイティブ 約 0.5〜1 秒、Web 約 1〜2 秒（推定。入力の最初の 64Ki 点が 0.07〜0.08 秒で届く実測＋ノードを描くまでの実測 0.2〜0.6 秒＋Web の起動 約 0.9 秒） | 読み込みと spill が終わるまで（55 枚で約 81 秒、Web 10 枚で約 10 秒）＋ 1 回目の分割（未測定）。つまり入力の大きさに比例する | COPC では既に 0.2〜0.6 秒。改善の余地が小さい |
| 入力の大きさへの依存 | 無い（最初の数十万点が届けば描ける） | ある | ほぼ無い |
| メモリの上限の決め方 | 下見の点数の上限（上の表）。変換のメモリとは別に固定 | 変換のメモリはそのまま。追加は不要 | 追加は不要 |
| 落ちないための仕組み | 上限＋粗くする＋空きメモリでの手放し。失敗しても下見は残る | 途中のファイルを開いたまま書き続けるので、壊れた COPC を開く危険がある | ― |
| ADR-0019 との関係 | 触れない（読み込みの出口にコールバックを足すだけ） | **衝突する**。親ノードの点は「ラン全体から均等に」選ぶ（M4-16）ので、上の段はラン全体を 2 回読むまで決まらない。書き出しの順の変更も要る | 無関係 |
| Web と デスクトップの差 | 保管庫の置き場所が違う（Rust 側／JS）。仕組みは同じ | Web の OPFS の途中ファイルを別ハンドルで開く必要（同期アクセスハンドルは 1 つ。ADR-0012） | ― |
| 壊れやすい所 | 下の 1〜4 | COPC の階層が最後に書かれる前提（vendor/copc-writer の書き出しの変更）、途中のファイルの読み取りと書き込みの競合 | ― |
| 実装の大きさ（推定） | 小〜中（ストアとリーダー、仮レイヤー、差し替え） | 大（vendor のライターと LOD の変更） | 小 |

(b) を採らない理由: 最初の点までの時間が入力の大きさに比例したまま残る（所有者の目標 1 を満たさない）うえ、vendor の変換の中を変える必要があり、
過去に何度も直した部分（ADR-0019 の前後の M4-1・M4-6・M4-7・M4-9）にもう一度手を入れることになる。

### 壊れやすい所（未検証）

1. **レンダラが、点を持たない根のない平らなノードの集まりを階層として受けるか**（`node-selection` は親子を前提にしている可能性）。PF-1 の最初に、小さな試作で確かめる。受けなければ、下見は「根 1 つ＋ 8 の子」の 2 段の階層にする
2. 仮のレイヤーから COPC のレイヤーへ**途切れずに**切り替える（下見を消すのは、COPC の最初のノードが描かれたあと。カメラは動かさない）。画面での確認が要る（未確認）
3. 複数ファイルで、下見が最初は 1 枚ぶんしか出ない（上記）。「変換中、全体の x% が見えています」と書く UX が要る
4. 変換中に下見を描くことで CPU/GPU を取り合い、変換が遅くなる可能性。PF-1 で、変換の時間を下見あり・なしで比べる（未測定）
5. 入力の点の順序が偏っている（例: 先頭にノイズの多い走査線）と、ハッシュの間引きでも密度は一様だが、見える範囲が偏る
6. 実測の Tauri アプリでの時間（PF-0 はネイティブを example で、Web を実ブラウザで測った）

## 採らなかった案

- **全点をメモリに読んでから描く**: 数億点で点数に比例して落ちる（CLAUDE.md「メモリが点数に比例しないこと」）
- **変換を速くするだけ**: 55 枚で 220 秒、Web 10 枚で 74 秒の待ちは、LOD の索引と圧縮が主で、1/10 にするのは別の大きな仕事。待ちの間に何も見えないこと自体は変わらない
- **案 (b)**: 上の表

## このマイルストーンの目的

**COPC ファイルを開いて、点が画面に出て、動かしても破綻しない状態**まで持っていく。

M0 の計画では M1 に EDL とカラーマップも含めていたが、**1マイルストーンが大きすぎて差分を
追えなくなるため、そこは M2 に送る**。M1 は「点が正しく見える」だけに絞る。

## M0 から引き継いだ設計予算

M0-3 の実測で `pcv://` のスループットは **92.7MB/s**。後述のノード形式（1点20バイト）では
**毎秒約 4.6M 点**が上限になる。点予算を 3M 点とすると、可視ノードを総入れ替えするのに
約 0.65 秒かかる。したがって M1 の LOD は以下を満たす必要がある。

- ノードは **1〜2MB 単位**に刻む（粗くすると1ノードの到着待ちで画面が固まる）
- **画面空間誤差**でノードに優先度を付け、粗いものから順に埋める
- 一度読んだノードは**キャッシュして再取得しない**

なお Web 版では HTTP 帯域がこれより細くなるため、この予算で設計しておけば Web でも成立する。
**デスクトップ側がボトルネックになることはない。**

## M1-1: COPC を読む（`pcv-core`）

### やること

`crates/pcv-core` に COPC リーダーを実装する。

**クレートを選定する。** 候補は2つ:

| 候補 | 備考 |
|---|---|
| `copc-rs` 0.5.0 | reader + **writer**。writer があるとテスト用の極小 COPC をコードで生成でき、fixture を public リポジトリにコミットせずに済む |
| `copc-core` 0.9.0 | 新しい。hierarchy / streaming point 型を提供 |

**選定の決め手は規約1**（ARCHITECTURE.md）:
**`pcv-core` が `wasm32-unknown-unknown` でビルドできること。** これが Web 版のバックエンドが
成立する条件なので、ここを満たさない候補は落とす。`std::fs` を直接要求せず
`Read + Seek` のジェネリクスで受けている実装が望ましい。

実際に両方を試し、**選んだ理由と落とした理由を ADR-0003 に記録すること。**

### 公開する API の形

```rust
// 中身は選定したクレートに委ねてよいが、pcv-core の外向きAPIはこの形に寄せる
pub struct CopcFile { /* ... */ }

impl CopcFile {
    pub fn open(path: &Path) -> Result<Self>;
    pub fn info(&self) -> &CloudInfo;              // 点数, BBOX, scale/offset, 属性の有無
    pub fn hierarchy(&self) -> &Hierarchy;         // octree ノードキーと各ノードの点数
    pub fn read_node(&mut self, key: NodeKey) -> Result<NodeBuffer>;  // M1-2 の形式で返す
}
```

## M1-2: ノードのバイナリ形式を決めて `pcv://` で配信

### やること

Rust からレンダラへ渡すノードの**バイナリレイアウトを確定させ**、`pcv://` で配信する。
これは Rust と TypeScript の間の唯一の重いインターフェースなので、ここで固める。

### ノードのバイナリ形式（決定）

ヘッダ（固定長）＋インターリーブされた点配列。**GPU の頂点バッファにそのまま流し込める形**にする。

```
[ヘッダ 32 bytes ]
  u32   magic        "PCVN"
  u32   version      1
  u32   point_count
  u32   stride       20
  f32   origin_x     ノードローカル座標の原点（世界座標、f32 で足りる粒度に丸めた値）
  f32   origin_y
  f32   origin_z
  u32   flags        どの属性が有効か（color / intensity / classification）

[ 点配列 point_count × 20 bytes ]
  f32 x3   position       ← ノードローカル相対座標
  u8  x4   color RGBA
  u16      intensity
  u8       classification
  u8       _padding
```

### なぜノードローカル相対座標にするのか（重要）

COPC の座標は f64 の世界座標で、実測データは UTM 系などで **X=500000.123 のような大きな値**を
取る。これを素朴に f32 に落とすと仮数部が足りず、**mm 〜 cm 単位の精度が消えて点群が
グリッド状にガタつく**（点群ビューアの古典的な失敗）。

そこでノードごとに原点を持たせ、点は**その原点からの相対座標**を f32 で持つ。
原点は uniform でシェーダに渡し、ビュー行列側で吸収する。これで f32 のまま精度が保たれる。

f64 を GPU に送る案は採らない。WebGPU に f64 は無い。

### 受け入れ条件

- [x] `pcv://` でノードを要求すると上記形式のバイナリが返る
      （`src-tauri/src/copc_state.rs` のテストに加え、M1-3で実際に `npm run tauri dev` を
      起動し webview から `fetch(convertFileSrc("0-0-0-0", "pcv"))` が動くことを確認した。
      Rust側stdoutに `[pcv] served node 0-0-0-0: 20000 points, 400032 bytes` が出た）
- [x] フロント側にパーサがあり、ヘッダの `magic` / `version` を検証して弾ける
      （`src/datasource/node-format.ts` の `parseNodeBuffer`。`npx tsx` で
      正常系・magic不正・version不正・バイト長不一致の4パターンを手動実行して確認した）
- [x] 読み出した点数がヘッダの `point_count` と一致する
      （Rust側は`read_node_bytes_matches_m1_2_wire_format`でバイト長を検証、
      フロント側は`parseNodeBuffer`が`buffer.byteLength`とヘッダの`point_count`から
      逆算した期待バイト数を突き合わせて検証する）
- [x] `DataSource` インターフェース（M0-3 で作った形）に `readNode(key)` が生えている
      （`src/datasource/DataSource.ts`。`TauriSource`が実装）
- [x] Tauri の API を import しているファイルが `src/datasource/tauri.ts` のままであること（**規約2**）
      （`grep -rl "@tauri-apps/api" src/` で確認）

### M0 で判明している落とし穴（そのまま効く）

- `convertFileSrc` はパス全体を1セグメントとして `encodeURIComponent` するため、
  `/node/<key>` のような**複数セグメントのパスは使えない**。ノードキーは1セグメントに
  エンコードすること（例: `pcv://0-0-0-0`）
- devURL と `pcv://` はオリジンが異なるため `Access-Control-Allow-Origin` ヘッダが要る

## M1-3: 1ノードを WebGPU で描画する

### やること

- WebGPU の point sprite パイプライン（頂点シェーダで四角形を展開、フラグメントで円形に抜く）

## M1-4: octree LOD と点予算

### やること

可視ノードを octree から選び、点予算の範囲で漸進的に精度を上げる。**M1 の本体。**

1. **画面空間誤差でノードに優先度を付ける** — ノードの BBOX を投影し、画面上の大きさ ÷
   そのノードの点密度から誤差を出す。大きいものほど優先
2. **視錐台カリング** — 画面外のノードは候補から外す
3. **点予算** — 合計点数が予算（デフォルト 3M、UI から変更可）を超えたら、優先度の低い
   ノードから捨てる
4. **ノードキャッシュ** — 一度読んだノードは LRU で保持し、再取得しない。
   GPU バッファも合わせて解放する
5. **非同期ロード** — 優先度順にキューイングし、同時リクエスト数を絞る（4本程度）。
   カメラが動いたらキューを組み替える

### 受け入れ条件

- [x] 大きい COPC（1000万点以上）を開いても即座に粗い全体像が出る
      — **所有者が実機確認（2026-09-23）。問題なし。**
- [x] 静止していると精度が段階的に上がり、やがて止まる
      （上記の合成COPCで、drawnNodesが8→28→32→36→40→41と段階的に増え、
      `drawnPoints=200000 drawnNodes=41 loadingNodes=0 queuedNodes=0` で安定することを
      `npm run tauri dev` のRust側stdoutログで確認した）
- [x] 動かしている間もフレームが落ちない（点予算が効いている）
      — **所有者が実機確認（2026-09-23）。問題なし。**
- [x] 点予算を UI から変えると、描画点数が実際に追従する
      （点予算を3,000,000→30,000に変更した直後、`drawnPoints`が200000から29959へ
      即座に減り、以後そこで安定することをログで確認した）
- [x] 同じ場所に戻ったとき再ロードが走らない（キャッシュが効いている）
      — **所有者が実機確認（2026-09-23）。問題なし。**
- [x] 描画点数・ロード中ノード数・fps が画面に出ている（**これが無いと挙動を追えない**）
      `ViewerPanel.tsx` に統計表示を実装し、`useCopcViewer.ts` が
      `report_diagnostic` 経由でRust側stdoutにも同じ内容を出す
      （`[M1] drawnPoints=... drawnNodes=... loadingNodes=... queuedNodes=... cachedNodes=... fps=... pointBudget=...`）。
      所有者が実機確認。画面上のオーバーレイに統計表示が出ていると報告

### 自分で確かめる手順

```bash
npm run tauri dev
# 1. 大きい COPC を開く → 粗い全体像がすぐ出るか
# 2. じっとする → 精度が上がって止まるか
# 3. 速く動かす → fps が落ちないか、点予算を超えないか
# 4. 元の視点に戻る → 再ロードが走らないか（統計表示で確認）
```

### 検証中に気づいた挙動（要注意）

`npm run tauri dev` を開発モードで動かして確認したところ、ノードの読み込みが
**数十秒単位で止まって見えることがある**（`loadingNodes=4` のまま `queuedNodes` も
減らない状態が続き、その後まとめて進む）。fps は常に58〜60を維持しており、
`[pcv] served node ...` のエラーログも出ないため、描画パイプラインやLODの
選択ロジック自体の不具合ではなく、`pcv://` カスタムプロトコルへの並行リクエストが
開発サーバ（Vite）やWebView2のネットワークスタック側で一時的に詰まっている
（devビルド・大量の小さいリクエスト特有の現象）可能性が高いと見ている。
`cargo build --release` でのビルドや、実運用に近いノードサイズ（1〜2MB、
M1-point-rendering.mdの設計予算どおり）ではこの現象が再現するか未確認。
所有者が実機で気になる遅延を感じたら、まずこの点を疑ってほしい。

#### 追記: 原因の候補を特定した（レビュー時）

上記は「devモード特有のネットワーク挙動」と結論づけられていたが、**その結論は手元の
証拠では裏付けられていない**。

**fps が 58〜60 を維持していたことは根拠にならない。** 描画は既にキャッシュ済みの
ノードを描き続けるだけなので、転送が止まっていても fps は落ちない。むしろ落ちないのが
当然の挙動であり、転送層を免責する材料にはならない。

**M0-3 の実測値はこのケースをカバーしていない。** M0-3 で測ったのは単発・逐次の
大きな転送（1/10/100 MiB を1本ずつ）であり、M1-4 が行う4本の並行リクエストは
一度も計測していない。

`src-tauri/src/lib.rs` を確認したところ、`register_uri_scheme_protocol`（**同期版**）を
使っている。同期版のハンドラは Rust 側のメインスレッドで実行されるため、
**ノード読み出し（ディスク I/O + LAZ 伸長 + 20 バイト stride への詰め替え）が
すべて直列化する**。LAZ 伸長は CPU を食う処理なので、4本の並行リクエストは互いの
完了を待つことになる。観測された「`loadingNodes=4` のまま止まり、その後まとめて進む」
という挙動はこれと一致する。

fps が落ちなかったことも矛盾しない。JS の requestAnimationFrame は webview の
レンダラプロセスで回っており、Rust のメインスレッドとは別だからである。

**対処の方針:** `register_asynchronous_uri_scheme_protocol` に切り替え、ノード読み出しを
ブロッキング用スレッドプールに逃がす。これは LOD ストリーミング設計の土台にあたるため、
M2 の先頭で潰す。

**ただしこれは仮説であり、まだ実測していない。** 切り替える前に、並行リクエスト時の
スループットを M0-3 と同じ方法で測り、直列化しているかどうかを数値で確認すること。
直した後も同じ計測を行い、改善したことを数値で示すこと。推測で直して「直った気になる」
ことを避ける。

## M1-5: 見たいところに寄れるようにする

### なぜ M1 に入れるのか

**この項目は当初どのマイルストーンにも入っていなかった。** ROADMAP には「ピッキング」を
土台として挙げ、それを必要とする機能（マーカー配置・計測・選択・歩行時の接地）を並べたが、
**カメラのナビゲーションを消費者として挙げ忘れていた**ため、誰も所有しない項目になっていた。

後送りできない理由は、M1 の未確認項目がすべて「自由に動き回れること」を前提にしているため。

- 「カメラを回しても、遠くから寄ってもガタつかない」
- 「静止すると段階的に精細化し、やがて止まる」
- 「見回している間、fps が維持される」
- 「視点を戻したときに再ロードが走らない」

寄るほど身動きが取れない状態では、これらを判定できない。M2 の EDL やカラーマップの評価も
同じ前提に乗っている。**カメラ操作は機能ではなく、他のすべての目視検証の前提条件である。**

M1 の目的は「点が正しく見える」であり、**見たいところに寄れないなら「見える」を満たしていない。**

### 現状の問題（所有者の実機報告から）

所有者から「ズームすると速度が遅くなる」という報告があり、当初は性能問題として調査したが、
統計表示が `drawn` は減り `loading` は 0、fps も維持という値を示しており、
**計算量は増えていなかった**。原因はカメラの設計だった。

`src/renderer/orbit-camera.ts`:

```ts
zoom(factor) {
  this.distance = clamp(this.distance * factor, MIN_DISTANCE, MAX_DISTANCE);
}
```

1. **注視点に漸近するだけで到達しない。** 距離を掛け算で縮めるため、1ティックあたりの
   実移動量が近づくほど小さくなる
2. **カーソル位置ではなく固定の注視点に向かって寄る。** `target` は初期化時に決まり
   パンでしか動かないため、点群の端にある物を見たくても中心へ寄っていく
3. **パン速度も距離に比例する**（`speed = this.distance * 0.0015`）ため、
   寄るほどパンも鈍る

結果、**寄れば寄るほどズームもパンも同時に鈍り、身動きが取れなくなる。**

### やること（初版。1・2回目の実装方針。3回目で方式を変えた — 下記参照）

カーソル位置に向かってズームする（Potree / CloudCompare / Blender / Google Earth と同じ挙動）。

**正確なピッキングは使わない。** ROADMAP で土台として挙げた「ピッキング」は深度バッファの
読み出しを伴うが、ここではそこまで要らない。**octree のノード AABB への粗いレイキャスト**で
十分実用になり、hierarchy は既に JS 側にあるので新しい土台を作らずに書ける。
正確なピッキングはマーカー配置や計測が必要になる M5 まで待つ。

1. カーソルのスクリーン座標から、逆 viewProj でワールド空間のレイを作る
2. hierarchy のノード AABB とレイの交差を取り、最も近い交点を求める
   - 交差が無い場合（空を指しているなど）は従来どおり `target` に向かって寄る
3. ズーム時に `target` をその点へ向けて寄せながら距離を縮める
4. パン速度が寄るほど潰れる件も見直す

**この方針（手順2・3、「AABBとの交点という『点』を求めてtargetをそこへ寄せる」）は
方式そのものが構造的に成立しないことが後で判明した。** 詳細と、代わりに採用した方式
（方向だけを使う）は次項「方式を変更した（3回目）」を参照。手順1（レイを作る）と
手順4（パン速度の下限）は今の実装でもそのまま使っている。

**規約3 を守ること:** `src/renderer/` は React を知らない。canvas と `DataSource` だけを受け取る。

### 方式を変更した（3回目）: 「点」ではなく「方向」だけを使う

1・2回目の実装（上の「やること」）は、実機確認のたびに退行報告が続いた。1回目は
固定の注視点に寄るだけでカーソル位置を無視していた。2回目はカーソル下の「点」を
octreeのAABBへのレイキャストで求めてtargetをそこへ寄せる方式にし、レイキャスト自体の
バグ2件（後述「実機確認で見つかった不具合」参照）を直したが、直した後も所有者から
「スクロールするほどズームが利かなくなる」という報告が続いた。

**原因は実装のバグではなく、方式そのものが構造的に成立しないことだった。**

2回目の方式は `target += (towardPoint - target) * (1 - factor)` という式で、1ティックの
移動量は `(1 - factor) * D`（`D` = targetからtowardPointまでの距離）になる。ところが
`towardPoint` はAABBとレイの交点、つまり**octreeノードの箱の面（境界）**でしかなく、
点群の点があるところではない。カメラがその面に近づくほど `D` は0に近づき、移動量も
一緒に0へ潰れる。つまり毎ティック「残り距離の何%」ずつ進むだけで、**箱の面という
何もない境界に漸近して止まる。** 点群の点そのものへ到達することは、この式の形である
限りありえない。レイキャストのバグを直しても、「正しい面」に漸近して止まるようになる
だけで、症状（寄るほど効かなくなる）は解消しない。

3回目（今回。`src/renderer/orbit-camera.ts` の `zoom()`）は、AABB・ピッキング・
深度バッファのどれにも依存せず、**カーソル位置を通るレイの方向ベクトルだけ**を使う。
`step = distance * (1 - factor)` は `distance`（自分がまさに縮めている量そのもの）に
比例して決まり、target が実際にどこにあるか・カーソルの下に何があるかとは無関係。
`distance` は自分自身の縮小と一緒に動くので、「独立した何か」に漸近して止まることが
構造的に起こりえない。止まるとしたら `MIN_DISTANCE` に当たったときだけ。

**次に「カーソル位置にズームしたい」と考えたとき、AABBの面や深度バッファの値など
「点」を求めてそこへ寄せる方式を選ばないこと。** 箱の内部は空洞で、面は点群の点では
ないため、代理として原理的に間違っている。方向だけを使えば、間違いうる代理が一つも無い。

### ズームすると読み込みが遅くなる → 修正した

**原因（実測で確認）:** `src/renderer/screen-space-error.ts` の
`projectedBoundsDiagonalPixels` は、ノードのBBOXの8頂点をクリップ空間に投影する際、
1頂点でもニアプレーンの後ろ（`cw <= 1e-6`）に回ると、残りの頂点を見ずに即座に
「画面いっぱい」相当の固定値（`canvasWidth + canvasHeight`）を返していた。ズームインして
カメラがノードのBBOXに近づく・入り込むと、この条件に該当するノードが急増し、優先度が
軒並み同じ最大値に潰れる。その結果、優先度によるノードの選別（`point-cloud-renderer.ts`
の `selectNodesForThisFrame` が候補を優先度順に並べて点予算内に絞る処理）が効かなくなり、
ローダーが本来後回しでよいノードまで大量に「最優先」として要求していた。

**対処:** AABBをニアプレーンでクリップしてから画面上の大きさを求めるようにした。
`transformPoint` が返すクリップ空間の `w` はワールド座標のアフィン関数（行列との内積）
なので、ニアプレーンの後ろに回った頂点と手前に残った頂点をワールド座標のまま線形補間
すれば、`w` がちょうど閾値を跨ぐ点（＝ニアプレーン上の点）を厳密に求められる。AABBの
12本の辺すべてについてこれを行い、「手前に残った元の頂点」と「辺がニアプレーンを跨ぐ
箇所にできる新しい頂点」を集めて画面座標に変換し、そのbounding boxの対角線を返す。
8頂点すべてが後ろに回ったときだけ、従来どおり最大値を返すフォールバックを残した
（本来は視錐台カリングで弾かれているはずのケース）。

「カメラの至近にあるノードを優先したい」という元の意図は変えていない。至近のノードは
相変わらず大きな値になるが、ノードごとに異なる値になるため、優先度による選別が機能する。

**確認方法:** `src/renderer/screen-space-error.test.ts` にテストを追加した。
- ズームイン相当のカメラ（原点近くにカメラを置き、周囲3x3x3個のノード相当のBBOXを
  配置）で `screenSpaceError` を呼び、返る優先度が全ノードで同一の値に潰れていない
  ことを確認（`distinctPriorities.size > 1`）。修正前のコードに戻すとこのテストは
  失敗する（全ノードが `canvasWidth + canvasHeight` に潰れる）
- `projectedBoundsDiagonalPixels` 単体でも、箱がすべて手前・すべて後ろ・ニアプレーンを
  跨ぐ、の3パターンを確認。跨ぐケースでは箱の大きさによって値が変わり、
  `canvasWidth + canvasHeight` という固定値にはならないことを確認した

このバグ修正のためにフロント側にテストランナー（`vitest`）を追加した

### ズームすると逆に近づかなくなった → 修正した

**症状:** 上の「ズームすると読み込みが遅くなる」を修正した後、所有者から
「（修正前より）逆に近づかなくなった」という報告があった。カーソル位置に向かって
寄る機能（M1-5）を入れた直後の実機確認で見つかった退行。

**原因（コードを読んで特定、2つが重なっていた）:**

1. **レイ原点がAABBの内側にあると`intersectRayAabb`が0を返していた。**
   `src/renderer/raycast.ts`の末尾が`return Math.max(tMin, 0);`になっており、
   レイ原点（`screenPointToWorldRay`が作るレイの原点はニアプレーン上の点、つまり
   ほぼカメラ位置）がAABBの内側にあるとき0を返す仕様だった。octreeのルートノードの
   AABBは点群全体を覆うため、**カメラが点群にわずかでも寄るとルートAABBの内側に
   入る。** そうなると`closestHierarchyHit`はどのノードよりも先に「t=0」を最小値
   として拾ってしまい、交点は`origin + direction * 0` = **カメラ位置そのもの**に
   なる。
2. **`closestHierarchyHit`にhierarchy全ノード（内部ノード込み）を渡していた。**
   octreeの内部ノードのAABBは子を入れ子に包んでいる。レイが外から入ってくる場合、
   外側の粗い箱への到達点は内側の細かい箱への到達点より必ず手前になるため、
   **最近傍判定は常に一番粗い外側の箱に勝ってしまい**、カーソル下の実際の表面には
   届かない。

**結果:** `pickPointUnderCursor`が返す`towardPoint`がカメラ位置（またはそれに近い
粗い値）になり、`OrbitCamera.zoom()`の`target += (towardPoint - target) * shrink`で
**注視点がカメラのほうへ引き寄せられる**。カメラと注視点が互いに近づくだけでシーン
に対しては進まなくなり、「逆に近づかなくなった」という体感になっていた。

**対処:**

1. `intersectRayAabb`（`src/renderer/raycast.ts`）を、`tMin`が小さな正の閾値
   （`MIN_HIT_DISTANCE = 0.01`。ニアプレーン距離程度）未満ならnullを返すように
   変更した。レイ原点を含む箱（`tMin`が負）も、原点のごく近くにしか交点が無い箱も
   候補から除外される。カメラ自身を含む箱に「寄る」ことに意味は無いため。
2. `PointCloudRenderer`（`src/renderer/point-cloud-renderer.ts`）に
   `lastDrawnAabbs`を追加し、`selectNodesForThisFrame`が返す`toDraw`（今フレーム
   実際に描画したノード）のAABBだけを保持するようにした。`pickPointUnderCursor`は
   `this.hierarchy`（全ノード）ではなく`this.lastDrawnAabbs`を対象にする。
3. `raycast.ts`に`pickWorldPointUnderCursor`（レイ生成＋交差判定をまとめた関数）を
   追加し、`PointCloudRenderer`はこれに委譲するだけにした。WebGPUデバイスを
   起動しなくても、この関数だけで「カメラ位置を返していないか」を単体テストで
   検証できるようにするため。

**確認方法:** `src/renderer/raycast.test.ts`・`src/renderer/orbit-camera.test.ts`に
テストを追加した。
- `intersectRayAabb`が「レイ原点が箱の内側にある」場合にnullを返すことを確認
  （修正前は`Math.max(tMin, 0)`により0を返し、このテストは失敗する）
- 入れ子のAABB（粗い外側の箱＋細かい内側の箱）を両方`closestHierarchyHit`に渡すと
  常に粗い箱が勝つこと、細かい箱だけ（＝実際に描画中のノードだけ、という想定）を
  渡せば正しい表面に届くことを確認
- **実機で起きた状況そのもの**（カメラが点群のルートAABBの内側にいて、その内側に
  前方の面を表す入れ子ノードがある）を再現し、`pickWorldPointUnderCursor`が
  カメラ位置ではなく前方の面を返すことを確認（修正前のコードに戻すとカメラ位置が
  返り、このテストは失敗する）
- `pickWorldPointUnderCursor`の返り値をそのまま`OrbitCamera.zoom()`に渡しても、
  `target`がカメラ(eye)の近くまで一気に吸い寄せられないことを確認
- 描画中のノードが無い場合・カーソルが空を指している場合はnullを返し、従来どおり
  `target`へ向かうフォールバックに落ちることを確認
- 既存の28件のテストを含め、`npm run test`（34件）・`npm run typecheck`・
  `npm run lint`が全て通ることを確認した

**次に触る人へ（罠になりやすい点）:**
- 「レイとAABBが交差するか」だけをテストしても、「カメラがそのAABBの中にいる」
  という実際の使用状況は再現できない。ズームのピッキングは常にカメラが点群の
  近く・内部にいる前提で動くので、テストも原点をAABBの内側に置いた状態で書く
  必要がある。
- 入れ子になったAABB集合に対して「最近傍のtを取る」という素朴な実装は、
  ノードが親子関係を持つ（octreeやBVHなど）限り、常に一番粗い（外側の）ノードが
  勝つ。対象を「実際に描画中のノード」や「葉ノードだけ」に絞らない限り、
  この種の階層構造とは相性が悪い。

**この時点では未検証だった:** 実際のマウス操作で、点群の端にある物にカーソルを
合わせてホイールを回したときに、見た目としてそこへ近づいていくように感じるか。
→ 次の実機確認で「スクロールするほど効かなくなる」という別の退行が報告され、
下の「ズームが方式ごと成立しないと判明した」で方式そのものを変更することになった。

### ズームが方式ごと成立しないと判明した → 方向ベースに書き直した（3回目）

**症状:** 上の2件のバグ（カメラを含む箱がt=0を返す・内部ノードの入れ子AABBが
最近傍判定で常に勝つ）を直した後の実機確認で、「スクロールするほどズームが
利かなくなる」という報告が続いた。

**原因: 実装のバグではなく、方式そのものが構造的に成立しなかった。** 2回目の方式
（`target += (towardPoint - target) * (1 - factor)`）は、1ティックの移動量が
`(1 - factor) * D`（`D` = targetからtowardPointまでの距離）になる。ところが
`towardPoint` はAABBとレイの交点＝**octreeノードの箱の面**でしかなく、点群の点が
あるところではない。カメラがその面に近づくほど`D`は0に近づき、移動量も一緒に
0へ潰れる。上の2件のバグを直したことで「正しい面」に対して漸近するようにはなったが、
**面そのものが点群の点ではなく、漸近して止まるという構造は変わっていなかった。**
これが「スクロールするほど効かなくなる」の正体で、レイキャストのバグ修正では
直しようがなかった。

**対処:** `OrbitCamera.zoom()` を、AABB・ピッキング・深度バッファのどれにも
依存しない方式に書き直した。カーソル位置を通るレイの**方向ベクトルだけ**を使い、
`step = distance * (1 - factor)` で target を動かす。移動量は`distance`自身に
比例して決まるため、targetの位置や対象までの距離とは無関係に決まり、独立に
0へ潰れることが構造的に起こりえない。`pickWorldPointUnderCursor`（AABBの交点を
求めていた関数）は削除した。詳細な数式と、次に同じ罠を踏まないための注意は
本ファイルの M1-5 節「方式を変更した（3回目）」、および `src/renderer/orbit-camera.ts`
の `zoom()` のコメントを参照。

**確認方法:** `src/renderer/orbit-camera.test.ts` に、100回ズームインを繰り返しても
1ティックの移動量が毎回`previousDistance * (1 - factor)`のまま一定であることを
確認するテストを追加した（`orbit-camera.ts`のコメントで「これがM1-5『3回目』の核心」
と明記している）。2回目の方式（targetの位置に依存する）ならこの比率は徐々に
崩れていくはずだが、方向ベースの実装では毎回ぴったり一致し続けることを確認した。
**所有者が実機で確認し**、「細部まで行っても速度が変わらなくなったのでよくなった」
との報告を得た（ただし「まだ操作性は改善の余地がありそう」というコメントもあり、
未解決として残っている）。

**教訓:** カーソル位置へのズームを「対象までの距離に比例して縮む」式で実装する場合、
縮む対象（ここでは`D`）が「点群の点」ではなく「点群を覆う代理（AABBの面、深度バッファの
値など）」だと、代理に近づくほど代理と本物の点群の点との差は分からないまま、代理へ
漸近して止まる。代理を使う限りこの罠から逃れられないので、代理を経由しない量
（今回で言う`distance`自身）で移動量を決める方式に切り替える必要がある。

### 起動のたびにフリーズする → 修正した

**症状:** アプリを起動するたびに（点群を開く前から）しばらく操作不能になる、という
報告が所有者からあった。

**原因:** 計測用のベンチマークハーネス（`src/state/useIpcBench.ts` /
`src/state/useNodeConcurrencyBench.ts`）が、`useEffect` でマウント時に自動実行される
実装になっていた。`src/App.tsx` はこれらのパネルを `<details>` の中に置いていたが、
**React は `<details>` が閉じていても中身をマウントするため**、パネルを畳んでいても
計測は実行されていた。

起動のたびに実際に走っていた処理:

- `useIpcBench`（M0-3）: 1MiB + 10MiB + 100MiB を `pcv://` と `invoke` の両方で転送。
  ADR-0007 / M0-3 の実測では invoke の 100MiB だけで約9.7秒、10MiB で約7.8秒かかり、
  合計で20秒前後の重い転送になる
- `useNodeConcurrencyBench`（M2）: 64ノード × 並行数1/4/8 = 192回のノード読み出し。
  実測レートから数秒〜十数秒かかる上、`CopcPool`（8本）を占有する

この2つが、ビューア本体が点群ノードを読もうとしているのと同時に走り、リーダープールと
IPC帯域を奪い合っていたことが、起動時フリーズの正体だった。

**対処:** パネルと計測ロジック自体は残した（ADR-0007 / M0-3 の計測手順を再現できる状態を
保つため）。変更したのは自動実行のトリガーだけ:

- `useIpcBench` / `useNodeConcurrencyBench` の内部状態にボタン未押下を表す `runId = 0`
  を導入し、`useEffect` の先頭で `runId === 0` なら何もせず即 return するようにした。
  ボタン（既存の「再計測」を流用）を押すと `runId` がインクリメントされ、そこで初めて
  計測が走る
- 初期状態（`status`）を `"running"` から `"idle"` に変更し、パネルに「未計測」と
  分かる表示を追加した
- 各パネルに、押すとどのくらい時間がかかるか（IPCベンチは20〜30秒程度、並行数ベンチは
  数秒〜十数秒程度）を明記した。押した人が固まったと誤解しないようにするため
- `useWebGpuProbe`（M0-2）は `requestAdapter` と三角形1枚の描画だけで軽く、実測でも
  フリーズの原因になっていないため、従来どおり自動実行のままにした

**確認方法:** `npm run tauri dev` を起動し、Rust側stdoutに `[M0-3]` / `[M2]` の
計測ログが出ないことを確認した（`[M0-2]` のWebGPUプローブと `[M1]` のレンダリング統計は
従来どおり出る）。起動直後から `fps=60.0` で安定しており、フリーズは再現しなかった。
`<details>` を開かない状態で確認しており、開いてボタンを押すと従来どおり計測でき、
結果がRust側stdoutにも出ることも確認した。

**教訓:** 計測用の仕組みを製品の起動経路に置いたままにしない。`<details>` で畳んでも
Reactはマウントを止めてくれないので、「UI上は隠した」は「実行されない」の代わりにはならない。
計測ハーネスは実装した時点でボタン起動にしておくか、実装した直後に自動実行を外し忘れて
いないか確認する必要がある。
（`package.json` の `test` スクリプト、CIの `frontend` ジョブに `npm run test` を追加）。
それまでフロント側には自動テストが1つも無かった。

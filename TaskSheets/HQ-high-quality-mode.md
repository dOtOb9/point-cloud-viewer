# HQ: 高品質モード（PC のメモリと GPU の余裕を使って、もっと細かく表示する）

- 状態: 計画（HQ-0 から順に進める。各段の終わりに判断点がある）
- 日付: 2026-10-10
- 対象: デスクトップ版と、PC のブラウザの Web 版。**スマホ・モバイル Web は対象外**（今の保守的な設定のまま）
- 関連: [ADR-0009](./ADR-0009-adaptive-render-settings.md)・[ADR-0010](./ADR-0010-lod-priority-and-point-budget.md)（点予算と AIMD）・[ADR-0011](./ADR-0011-gpu-error-visibility.md)（GPU の喪失）・[ADR-0017](./ADR-0017-ui-shell-ribbon.md)（設定画面）

## 背景: 今の状態（コードで確かめた事実）

- 点予算の上限（デスクトップ）は、GPU メモリ **1GiB** を前提にした計算で決まる固定値で、約2,684万点。
  計算は `上限 = 1GiB ÷ (1点のバイト数 × 2)`（`device-profile.ts`・`point-budget.ts`）。
  2倍なのは、GPU 上のノードのキャッシュを点予算の2倍まで持つため（`CACHE_BUDGET_MULTIPLIER`）
- 点予算は、上限から始まり、フレームが間に合わなければ下げる（AIMD、ADR-0010）
- 一度読んだノードは GPU メモリにしか置かない。キャッシュから外れたノードは、もう一度ファイルから読み、展開し直す。
  **PC の RAM はほとんど使っていない**
- 動画の撮影時（渋谷 3.48 億点、この開発機の Chromium）の画面では、`pointBudget` が上限 26,843,545 に張り付いたまま fps 60 だった。
  **上限がブレーキになっている可能性が高い。ただし1枚の画面からの読みで、測ったものではない**（HQ-0 で確かめる）

## 引き受けるリスク

1. **GPU の喪失（device lost）が増えるおそれ。** 所有者の Windows でも、ときどき GPU が落ちる件が未解決のまま残っている。
   GPU メモリを多く使えば、落ちやすくなる可能性がある。
   → 段階的に上げて測る。落ちたら標準に戻して、そのことを画面に出す（ADR-0011 の仕組みに乗せる）
2. **WebGPU では GPU メモリの量（VRAM）が分からない。** 自動では決められない。
   → 使ってよい量は、所有者が設定で選ぶ。選べる上限は `adapter.limits` と、HQ-1 の実測で決める
3. **止まったときに最大まで描くと、次に動かした最初のフレームが重くなる。**
   → 入力を受けた時点で、描く前に点予算を戻す（HQ-2）

## 段取り

### HQ-0: 測る（コードは main に入れない）

開発機は所有者の PC と同じ（Core i5-14600K / RTX 4070 / 31.8GB）。Playwright の画面ありの Chromium で、**実際の GPU が使われていることを確かめたうえで**（SwiftShader ではないこと）測る。

- データは `data/tokyo-shibuya-merged.copc.laz`（3.48 億点）。視点は3つ固定する: 全体を見下ろす、街区、通りの高さ
- 上限を 1・2・4・8 GiB 相当に変えて（一時的な改造。コミットしない）、各視点で 10 秒止めたあとの値を記録する:
  `pointBudget`・上限・描いた点数・fps・読み込み待ちのノード数・GPU が落ちたか
- 5分間カメラを回し続けて、GPU が落ちないかも見る

**判断点 A**: 上限を上げると、描く点が増えて fps が保てるか。
- 増えないなら、ブレーキは別の場所にある。HQ-1 はやめて、原因を調べる
- 増えるなら、HQ-1 の選択肢（何 GiB まで選べるようにするか）を、この結果から決める

### HQ-1: 使ってよいメモリの量を選べるようにする

- 設定に「画質: 標準 / 高品質」を加える。高品質にすると、GPU メモリの予算を選べる（選択肢は判断点 A で決める。標準は今の 1GiB）
- 予算を変えたら、点予算の上限とキャッシュの大きさに反映する（再起動なし）
- GPU が落ちたら、標準に戻して、ダイアログで知らせる
- 設定画面は UI の作り直し（ADR-0017）の後に触る。それまでは、レンダラーと状態の側だけを作る

### HQ-2: 止まったら最大の細かさまで読む

- カメラが一定時間（初期値 0.5 秒、要調整）動かなかったら、AIMD による点予算の調整を止め、上限まで点予算を上げて読み込む
- 入力（ドラッグ・ホイール・タッチ）を受けたら、その時点で、描く前に元の点予算に戻す
- 測る: 止めてから最大の細かさになるまでの時間、止めている間の fps、動かし始めた最初のフレームの時間

**判断点 B**: 高品質モードを、デスクトップの既定にするか（所有者が画面で見て決める）。

### HQ-3（判断点 B の後に決める）: 展開済みのノードを RAM に置く

- GPU のキャッシュから外れたノードを、RAM に数 GB まで置いておく。戻ってきたときに、ファイルの読み込みと展開を省ける
- 効くのは細かさではなく、**戻ったときの速さ**。HQ-1 と HQ-2 を体感してから、要るかを決める

### 採らない（今は）: fps の目標を 60 から 30 に下げる

描ける点は増えるが、操作が重くなる。HQ-2（止まったら最大）のほうが、操作感を落とさずに細かさを上げられる。
HQ-2 の結果を見てから考え直す。

### 測り方と前提

- **Web 版**（`vite build` → `vite preview`、GitHub Pages と同じ `base`）を、Playwright の**画面あり Chromium**（同梱の Chromium 1248、フラグは `--enable-unsafe-webgpu` のみ）で動かした。

  「手動」は同じ改造に加えて、起動後に `setPointBudget(上限)` で点予算を上限に固定した（AIMD を止める）。
  カメラは一時改造で `window` に出したレンダラーの `camera` に直接代入した
- **注意（測定の質）**:
  1. この機械では別プロセスが 4173 番ポートを使っていた（他のセッションのプレビューと思われる）。測定中に他のセッションが GPU・画面を使っていた可能性があり、fps は揺れる **[推定]**
  2. `fps=0` や `1` が出た区間が何度かある。描画自体は進んでいた（描いた点数は増えていた）ので、ウィンドウが隠れて `requestAnimationFrame` が絞られたための見かけの値と考えられる **[推定]**。表には使っていない

  4. 途中でスクラッチ用ディレクトリが消え、最初の表の測定のスクリーンショットは取り直した（表の数値は消える前に画面へ出した出力から書いている）

### 内蔵 GPU（Intel UHD 770）**[測れなかった]**

**測れなかった。この PC の Windows には、内蔵 GPU が存在しない。**

- `Win32_VideoController` と `Get-PnpDevice -Class Display` が返すのは `NVIDIA GeForce RTX 4070` だけ。Intel の表示アダプターは「無効」でもなく、**デバイスとして現れていない**（BIOS で内蔵 GPU が無効になっていると思われる **[推定]**）
- Chromium 側の試行は全て NVIDIA に解決された:
  `requestAdapter({ powerPreference: 'low-power' })`、`--force_low_power_gpu`、`--use-webgpu-power-preference=low-power`、`--use-angle=d3d11 --force_low_power_gpu`、`--use-webgpu-adapter=intel`。
  どれも `adapter.info` は `nvidia / lovelace` で、Intel は出なかった
- Windows のグラフィックス設定（`HKCU\Software\Microsoft\DirectX\UserGpuPreferences`）は**変更していない**（対象の GPU が無い）。戻す作業は不要。キーは今も存在しない
- 依頼された「既定設定の 1920x1080、各視点 10 秒の最悪フレーム時間、EDL・ガラス・スケールの切り分け」は、**内蔵 GPU では測っていない**。RTX 4070 での 1920x1080 の測り直しもしていない（上の 1600x900 の表のみ）

内蔵 GPU 向けの考察（**すべて [推定]。実測なし**）:

- 内蔵 GPU は、RTX 4070 より点の処理能力がずっと低いはず。RTX 4070 でさえ 26.8M 点で動かしながら 20〜35fps まで落ちたので、**内蔵 GPU に 26.8M 点の上限をそのまま使うと、AIMD が長く縮み続ける**と考えられる。
  AIMD は点予算を 3 秒に 1 回、約 10% しか戻さない（`growRate` 0.1・`sustainedHitsToGrow` 3）ため、一度縮むと回復が遅い
- 低スペック向けのデスクトップ用の既定を別に持つ価値はあるが、**根拠にする実測が無い**。測れる機械（内蔵 GPU のみの PC か、BIOS で内蔵を有効にした同じ PC）で、HQ-1 の前に測るべき。
  変えるなら、確実そうな順に、点予算の上限（1 GiB から 256〜512 MiB 相当）、描画スケール、EDL 切、ガラス切。ただし RTX 4070 の結果では、スケールや EDL の効果がはっきりしなかったので、**上限を下げるのが最も確実** **[推定]**

### 判断点 A への提言

1. **「上限を上げると、描く点が増えて fps が保てるか」: 増える。ただし fps は保てない。**
   - 増える **[実測]**: 同じ街区で 26.8M → 60M → 142M と描く点が増え、遠景の欠けが埋まった（見た目の差は主に遠景）
   - 保てない **[実測]**: この GPU・1600x900・EDL ありでは、26.8M 付近が回しながら 60fps を保てる境目。40M で約 15〜27fps、60M で約 7fps、142M で約 9fps
   - 近景・真上の全体では、26.8M でほぼ足りていて、増やしても見た目はほとんど変わらない
2. **ブレーキは 3 つある（上限だけではない）** **[実測＋推定]**:
   - **読み込みの速さ**（Web 版で約 120 万点/秒。上限が 1 GiB でも 8 GiB でも、最初の 20 秒に描ける量は同じ）。上限を上げても最初は速くならない
   - **AIMD の回復の遅さ**。一度縮むと、上限が高くても戻らない（1 GiB 全体 4.95M、4 GiB 通り 11.5M）。5 分間の回転では、上限 214M に一度も戻らなかった
   - **動かしている間の描画コスト**（約 27M 点が境目）
3. **HQ-1 の選択肢**: 動かしている間は今の 1 GiB 相当のまま、止まっている間（HQ-2 の「止まったら最大」）だけ高い上限を使う設計にすれば、操作の fps を落とさずに細かくできると考えられる **[推定]**。
   選べる値は **1 GiB（標準）・2 GiB・4 GiB** を勧める。2 GiB（約 5,370 万点）は、60M で fps が 7 に落ちる手前で、止まっているときに使う量として妥当。
   4 GiB 以上（約 1.07 億点）は、`device.limits` と GPU の落ちやすさ（上記 [未確認]）があるので、止まったときだけに限り、動かし始めたら標準に戻す前提でなければ勧めない。8 GiB は選択肢に入れない（手動で最大まで描くと fps が 10 前後、0〜1 の時間帯も出た）
4. **HQ-1 より先に確かめること**:
   1. 現状のブレーキは読み込みの速さと AIMD の回復の遅さにもある。HQ-2 の「止まったら読み込みを進めて上限まで描く」だけで、上限を上げなくても細部が出るか（上限 1 GiB の街区は 30 秒で収束して 26.8M まで描けた）
   2. デスクトップ（Tauri）版で同じ測定をする（読み込み速度が Web 版と違う可能性 **[未確認]**）
   3. 内蔵 GPU の PC での測定

### なぜ効かなかったか **[推定。2 の方は一部実測]**

1. **点間隔の推定が、地表のようなデータでは大きすぎる**。`cbrt(体積/点数)` は点が立方体の中に一様に詰まっている前提。街や地形は薄い面にしか点が無いので、実際の面内の点間隔（`sqrt(面積/点数)`）より何倍も大きく出る（面に 10 万点なら約 7 倍）。
   画面上の本当の点間隔が 1 画素を割っていても、推定は 1 画素を超えたままになり、閾値 1 ではほとんど打ち切られない（見下ろしで約 140 点/画素を描いていたのに、点数がほぼ変わらなかったのと整合する）
2. **閾値を上げて推定の過大さを埋めると、穴が出る**。閾値 4 の見下ろしで描いていたノードを調べた（`lastDrawn`）: ルートと深さ 1 の全 8 ノードは**各 10 万点なのに、画面には塊とすき間で出た**。つまりこのデータでは、浅いノードの点が領域全体を薄く均等に覆っていない（一部の範囲に偏っている）。
   浅いノードで止めると、深いノードが埋めていたすき間が埋まらない。偏りの原因（変換側の間引き方か、元データの結合の仕方か）は**調べていない** **[未確認]**

### 採らなかった案・次の候補

- 閾値だけを上げる: 上のとおり穴が出るので採らない
- 次の候補（未実装）: (a) 誤差の式を面データ向けに直す（`cbrt(V/n)` を、AABB の最も薄い軸を除いた `sqrt(面積/n)` にする等）。ただし ADR-0010 の優先度の式も変わるので、LOD 全体の見直し。(b) 変換側で浅いノードを空間的に均等に間引く（M4 の変換の仕様に関わる）。(c) 判断前に、浅いノードの偏りの原因を調べる

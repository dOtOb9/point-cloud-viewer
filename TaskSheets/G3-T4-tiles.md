# G3-1 タイルの分け方と、タイル＋余白を読むイテレータ（T4）

所有者の依頼で、この文書は日本語で書く。計画は `G1-raster-and-dtm.md` の 11.1・11.3。

## 作ったもの

- `crates/pcv-core/src/tiles.rs`（`lib.rs` に `pub mod tiles;` を1行足しただけ。`extract.rs` は触っていない）
- `crates/pcv-convert/examples/tile_bench.rs`: 実ファイルで計測するだけの小さな例（本体からは使わない）

| 名前 | 役割 |
|---|---|
| `plan_tiles(extent, nodes, total_points, cap, min_tile_size)` | 純粋関数。ファイルなしでテストできる |
| `plan_tiles_for_reader(reader, cap, min)` | COPC のヘッダーの範囲と階層から上を呼ぶ |
| `TileReader::new(open, cap, min, margin)` | タイルごとに「タイル＋余白」の点を読むイテレータ。1回に1タイル分だけ持つ |
| `TileData` | 核の範囲、点（`TilePoint { record, is_core }`）、読んだ点数（`scanned_points`）、推定点数 |

`open` はタイルごとに新しい `CopcReader` を作る関数。`ExtractPoints::new` が `CopcReader` を所有してしまい、
`extract.rs` を変えない約束なので、使い回せない。代わりにヘッダーと階層をタイルごとに読み直す（小さい）。

## 所有のルール（点は必ずちょうど1つのタイルの核になる）

- 核は `[min, max)` の半開区間（X も Y も）。左と下を含み、右と上を含まない
- 例外: 全体の範囲の外側の最大端（X の最大、Y の最大）だけは閉じる（`[min, max]`）。含めないと端の点が消える
- 隣り合うタイルは**同じ f64 の境界値**を共有する（一様格子は境界を1つの式で、4分割は親の中点を子の両方に渡す）。
  だから隣同士で境界が1ulpずれて、点が二重になったり消えたりしない
- 余白 0 のときは核の点だけを返す。余白 > 0 のときは、核の外で「タイル±余白」の閉じた範囲にある点を `is_core = false` で返す
- ヘッダーの範囲の外にある点は、どのタイルの核にもならない（正しい COPC のヘッダーは点を全部含む）

読み出しの箱は、中心と半分の長さで表すと丸めで端の点を落としかねないので、わずかに広げて読み、
そのあと `owns()` と余白の範囲で厳密に選び直す（`ExtractPoints` の判定は両端を含む）。

## 推定の方法と分け方

- タイルの推定点数 ＝ 階層の全ノードについて `ノードの点数 × (ノードとタイルの XY の重なりの面積 ÷ ノードの XY の面積)` の和。
  ノードの中の点が XY で一様と仮定する。**推定であって上限ではない**（ノードの角に偏っていると超える）
- 最初は一様格子。1枚あたり平均 `cap / 2` 点になる枚数（ヘッダーの点数 ÷ 面積 ＝ 平均の密度から）。
  縦横の比は範囲に合わせる。最小の大きさ `min_tile_size` より細かくはしない
- 推定が `cap` を超えるタイルは4分割（四分木）。`min_tile_size` まで、または深さ24まで。
  それ以上分けられないタイルは `cap` を超えたまま残す（呼び出し側は `TileData` の実際の点数を見られる）
- 範囲の幅か高さが 0 の場合（線状）は、0 でない方向だけ分ける

## 計測（この機械、release、`autzen-classified.copc.laz` 10,653,336 点）

コマンド: `cargo run --release -p pcv-convert --example tile_bench -- <ファイル> <cap> <margin> 1`

| cap | 余白 | タイル数 | 核の点の合計 | 読んだ点（展開した点）の合計 | ヘッダー比 | 最大の1枚 | 全体の時間 |
|---|---|---|---|---|---|---|---|
| 2,000,000 | 0 | 12 | 10,653,336 | 20,846,511 | **1.96倍** | 1,053,709 点 | 9.35 秒 |
| 500,000 | 0 | 48 | 10,653,336 | 39,551,754 | 3.71倍 | 346,620 点 | 28.93 秒 |
| 2,000,000 | 20 | 12 | 10,653,336（余白を含めて 11,306,905） | 20,846,511 | 1.96倍 | 1,147,315 点 | 14.66 秒 |

- 計画そのものは 1ms 未満
- 読み直しの増え方: タイルが増えるほど、粗いレベルのノード（どのタイルにも掛かる）を読み直すので、
  上限を 1/4 にすると読む量が約 1.9倍になった。タイル数 12 → 48 で 1.96 → 3.71 倍
- 推定の精度: 1枚の核の実際の点数と推定の差は、最大で 47,355 点（cap 2,000,000）／35,529 点（cap 500,000）
- 最大の1枚（余白 0）は cap より小さい 1,053,709 点。cap が余裕を持って守られた
- 時間は1回ずつの測定（繰り返していない）。ほかのプロセスが動いていた可能性がある

2倍を超えるほどではないが（cap 2,000,000 で 1.96 倍）、cap を小さくすると読み直しはすぐ大きくなる。

## 採らなかった案

- **ノードを1回だけ読み、点を該当するタイルのバケツへ振り分ける**: 読み直しがなくなるが、全タイル分のバケツを同時に
  持つ必要があり、メモリが点数に比例する。計画（11.1）の「1タイル分だけ持つ」に反する。
  読み直しが問題になった場合の次の一手は「粗いレベルのノードだけ、展開した点を小さくして持ち回る」などだが、今回は計画どおり作った
- **`CopcReader` を使い回す**: `ExtractPoints` が所有するため、`extract.rs` を変えずには不可能。変える場合は T2 と調整する
- **推定を上限として扱う**: 一様と仮定した推定は偏りで外れる。上限にするなら最悪値（ノードの全点）になり、タイルが小さくなりすぎる
- **四分木だけ（一様格子なし）**: 平均の密度から始めたほうが、根から分けるより分割の回数が少ない（計画のとおり）

## テスト（`cargo test -p pcv-core tiles`、9件）

純粋関数: 面積の合計が範囲と一致し全位置がちょうど1つのタイルに所有される、密な所が小さいタイルになり推定が cap 以下、
最小の大きさで分けられないタイルは残る、線状の範囲と不正な入力。
ファイル（`copc-writer` の dev-dependency で合成した COPC）: 全点がちょうど1つのタイルの核（余白 0 と 3 の両方、`gps_time` で同定）、
範囲の最大の端と内側の境界、境界ちょうどの点（65×33 の格子で境界が整数になる）、余白の点は核でなく範囲内、
最大のタイルの点数が `cap` と余白から決まる上限以下（全体の半分未満）。

## 未確認・注意

- 渋谷などもっと大きい／偏ったデータでの読み直しの倍率と時間は未測定（autzen だけ）
- Web（wasm）では `open` が Worker の同期 I/O でタイルごとに開き直す形になる。そこでの時間は未測定（wasm32 向けビルドが通ることだけ確認）
- 階層のノード数が非常に多いとき、計画は「タイル数 × ノード数」の計算になる。autzen では 1ms 未満だが、数十万ノードでは未測定
- 計測は1回ずつ。時間の揺れは見ていない

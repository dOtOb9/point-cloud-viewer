# ADR-0009: 描画設定を端末に合わせて自動決定する

- 状態: 採択
- 日付: 2026-09-23
- 前提: [ADR-0002](./ADR-0002-rendering-api.md)（WebGPU 採用）、[M1](./M1-point-rendering.md) の点予算、
  [M3](./M3-release-and-update.md) の対象端末

## 決定

**静的な端末情報は「初期値」と「上限」を決めるためだけに使い、実際の描画設定は
実測したフレーム時間による閉ループで継続的に調整する。**

一度測って決め打ちにはしない。

## 背景

描画設定（点予算など）は現在すべて定数で、**開発機の RTX 4070 を前提に決めた値**である。
[M3](./M3-release-and-update.md) の対象端末（OPPO Pad Air / Snapdragon 680 / Adreno 610 /
RAM 4 GB）では、この値は成立しない。

### なぜ静的な推定では当たらないのか

**① 端末情報がそもそも取れない。**
[M0-2](./M0-feasibility.md) の実測では `adapter.info` から取れたのは
`vendor="nvidia"`, `architecture="lovelace"` だけで、**`device` と `description` は空文字**だった。
WebGPU のアダプタ情報はフィンガープリンティング対策のため意図的に粗い。
**GPU 名から性能表を引く方式は、引くべき名前が手に入らない。**

`navigator.deviceMemory` も 0.25/0.5/1/2/4/8 GB の粗い刻みで、実装されていない環境もある。

**② 性能表は陳腐化する。** 端末は増え続ける。表の保守は終わらない。

**③ 決定的な理由: モバイルはサーマルスロットリングする。**
Snapdragon 680 のようなファンレス端末は、負荷をかけ続ければ必ずクロックが下がる。
**起動直後に測って決めた値は、数分後には過大になる。**
一度測って終わりにする方式は、モバイルでは構造的に破綻する。

同じ理由で、電力モード（省電力設定、充電中かどうか）でも性能は変わる。

### したがって

**実測して追従する以外に、正しくあり続ける方法が無い。**
これはゲームの動的解像度や、Potree 系ビューアの点予算制御と同じ考え方である。

## 静的情報の使いどころ

静的情報は捨てない。**初期値と上限**として使う。閉ループが収束するまでの間、
極端に悪い体験を避けるために要る。

| 情報 | 用途 |
|---|---|
| `adapter.limits.maxBufferSize` 等 | **ハードな上限**。これを超える確保は失敗するので必ず守る |
| `navigator.deviceMemory` | キャッシュ量の上限の目安（取れたときだけ） |
| `navigator.hardwareConcurrency` | 同時ロード数の初期値 |
| `devicePixelRatio` | レンダースケールの初期値。**高 DPR は断片数に直接効く** |
| `adapter.info` の vendor | 初期値の大まかな段階分け程度。**これに依存した分岐を増やさない** |

## 調整対象の設定

| 設定 | 現状 | 効き方 |
|---|---|---|
| 点予算 | 定数 3,000,000 | 最も効く。頂点数とロード量の両方 |
| キャッシュ量 | 点予算 × 2 | メモリ。RAM 4 GB では効く |
| **レンダースケール** | 未実装（常に DPR 等倍） | **断片数に二乗で効く。** 10.36 インチの高 DPR では大きい |
| 点サイズ (px) | 定数 4 | 断片数に二乗で効く。オーバードローに直結 |
| 同時ロード数 | 定数 4 | CPU と IPC。[ADR-0007](./ADR-0007-pcv-protocol-concurrency.md) の実測を踏まえる |
| EDL の有無・半径 | 未実装（M2） | ポストプロセス。近傍サンプル数に比例 |
| ガラスのぼかし | 未実装（M2） | [ADR-0005](./ADR-0005-ui-shell.md) で実測すると決めた項目 |

**下げる順序を決めておくこと。** 画質への影響が小さいものから下げる。
例えば「レンダースケール → 点予算 → EDL の半径 → EDL 無効」のように、
**何を先に諦めるかを設計として決める。** その場しのぎで下げると、
何が効いて何が効かなかったのかが分からなくなる。

## 閉ループの作り方

**素朴に書くと振動する。** 以下を守ること。

- **目標はフレーム時間**（例: 16.6 ms）であって fps ではない。fps は平均で均されて鈍い
- **上げるときはゆっくり、下げるときは速く。** 体験が壊れるのは下げ遅れたときだけ
- **ヒステリシスを入れる。** 目標の前後に不感帯を設け、境界で往復しないようにする
- **判断は数フレームの中央値で行う。** 単発の重いフレーム（ノード到着時など）に反応しない
- **ユーザーの手動設定を常に優先する。** 手で変えたら自動調整は止まる、または手動値を
  上限として扱う。[M1-4](./M1-point-rendering.md) で点予算の手動変更は実装済み
- **現在値を画面に出す。** 勝手に変わる仕組みは、何が起きているか見えないと不信になる

## 帰結

**得たもの**
- 端末を列挙せずに、どの端末でも実用的な設定に落ち着く
- サーマルスロットリング後も追従する
- 新しい端末が出ても表を更新しなくてよい

**払うもの**
- 設定が動的に変わるため、**性能の再現性が下がる**。ベンチマークを取るときは
  自動調整を止められるようにしておくこと
- 閉ループの調整（不感帯、変化率）自体にチューニングが要る
- 「さっきより粗くなった」という見え方が起きうる。現在値の表示で緩和する

## 却下した案

| 案 | 却下理由 |
|---|---|
| GPU 名から性能表を引く | **引くべき GPU 名が取れない**（`adapter.info` は意図的に粗い）。表の保守も終わらない |
| 起動時に1回ベンチマークして決め打ち | **サーマルスロットリングで数分後には過大になる。** モバイルでは構造的に破綻する |
| 手動設定だけにする | 初見のユーザーが適切な値を知る方法が無い。初期値が悪いと「使えない」と判断される |
| 何もしない（定数のまま） | 対象端末で成立しない。開発機の値がそのまま他端末に押し付けられる |
| プラットフォームで分岐（Android なら低め） | 端末差は Android 内部のほうが大きい。Adreno 610 と最新の Adreno を同じ扱いにできない |

# M2: 点群を読めるようにする（陰影・カラーマップ・UI シェル）

- 状態: 未着手
- 前提: [M1](./M1-point-rendering.md) 完了、[ADR-0002](./ADR-0002-rendering-api.md)、[ADR-0005](./ADR-0005-ui-shell.md)

## このマイルストーンの目的

M1 で「点が出る」ようになった。M2 の目的は **「点群が読める」ようにすること**である。

この違いは実データで明確になった。`sofi.copc.laz`（3億6,438万点）は point format 6 で
**RGB を持たない**。現状では真っ白な塊にしか見えず、形状を判読できない。
そして調べた公開データ10件のうち**色を持つのは4件だけ**だった。

> 航空 LiDAR は基本的に強度と分類しか持たず、RGB は写真から後付けした製品にしかない。
> **現場のデータは色を持たないほうが多数派である。**

したがって EDL とカラーマップは「あると良い」ではなく、**無いと道具として使えない**機能である。

## M2-0: レンダラを描画対象の種類で分ける

### なぜ最初にやるのか

[ROADMAP.md](./ROADMAP.md) で、将来の DTM / TIN 表示が現状の構成に乗らないことを記録した。
`src/renderer/` は point sprite 専用に書かれており、三角形メッシュのパイプラインが無い。

**追加自体は難しくないが、「点群を描くもの」として書かれた構造のまま機能を積むと、
後から構造ごと作り直しになる。** 今なら安く、EDL とカラーマップを積んだ後では高い。

M1 では「点が正しく見える」というスコープを守るため意図的に触らなかった。ここで手当てする。

### やること

描画対象を1種類に決め打ちしている箇所を、複数種類を並べられる形にする。
**TIN の実装はしない。** 点群以外を受け入れられる構造にするところまで。

- 描画対象（現状は点群ノードのみ）を、パイプラインとバッファの組として抽象化する
- 1フレームの描画が「対象の集合を順に描く」形になっていること
- ノードのバイナリ形式は既に `magic "PCVN"` と `version` を持つので、
  将来 `"PCVM"`（メッシュ）を足せる。**この形式は変えない**

**やりすぎないこと。** 「将来こう拡張するかもしれない」を根拠に抽象を増やさない。
根拠のある拡張（メッシュ）に必要な分だけにする。所有者が追える構造を保つこと。

### 受け入れ条件

- [ ] 点群の描画が、種類を持つ描画対象の1つとして扱われている
- [ ] 見た目と性能が M1 から変わっていない（リグレッションが無い）
- [ ] 既存のテストが通る

## M2-0b: 上方向（up 軸）を確定させる

### これが先に要る理由

**点群データは Z-up だが、カメラは Y-up を仮定しており、変換する箇所がどこにも無い。**

```
autzen-classified.copc.laz の範囲:  X 3426 m × Y 4656 m × Z 209 m
                                                          ↑ Z だけ極端に薄い = Z が標高
```

LAS / COPC は投影座標系なので Z が標高である。一方 `orbit-camera.ts` は:

```ts
lookAt(this.eye(), this.target, [0, 1, 0]);   // Y を上と仮定
const worldUp: [number, number, number] = [0, 1, 0];  // パンも同じ
```

### 実機で確認した症状（当初の推定を訂正）

当初このファイルには「点群が横倒しで描画されている」と書いたが、**これは不正確だった。**
所有者に実機で確認してもらった結果は「**上から俯瞰したように見える**」であり、
以下が正しい説明である。

初期状態（`pitch = 0.3` rad ≈ 17°、`yaw = 0`）では、カメラはほぼ **+Z の真上**に位置して
−Z 方向を見る。データは Z が薄い（autzen で 209 m）ため、**XY 平面を正面から見る
＝真上からの俯瞰**になる。所有者の観察と一致する。

問題はここから。カメラの「上」は **+Y**、つまりデータ上は**水平方向**（北など）である。

| `pitch` | 本来あるべき見え方 | 実際 |
|---|---|---|
| 0° | **水平。地平線が見える** | **真上からの俯瞰** |
| ±90° | 真上 / 真下 | 真横 |

**つまり「横倒し」ではなく、仰角の軸が 90 度回っている。**

決定的なのは、**地平線を見る姿勢に自然に到達できない**こと。カメラにとっての「水平」が
データの水平と一致していないため、空を入れても地平線が正しい向きに出ない。

**気づかれなかった理由は、画面に上下を判断する手がかりが一つも無いこと。**
空も地平線もグリッドも無いため、真上から見ている間は不一致が現れない。
カメラを傾けると、建物や樹木が画面の横方向に伸びて見えるはずである。

所有者の「形状は大丈夫そう」という当初の判断は正しい（形そのものは正しく出ている）。

### 影響範囲（空だけの問題ではない）

| 機能 | 上方向への依存 |
|---|---|
| パン | 画面の上下方向の算出 |
| ピッチ | 回転する平面 |
| **標高カラーマップ**（M2-2） | どの軸が標高か |
| **EDL**（M2-1） | 陰影の向き |
| **空と地平線**（M2-0c） | 地平線の向きそのもの |
| DTM / TIN（[ROADMAP](./ROADMAP.md)） | 地面の定義そのもの |
| タッチ操作（[M3-6](./M3-release-and-update.md)） | パンと同じ |

### やること

**まず現状を確認すること。** 「横倒しになっている」は本ファイルを書いた時点での推定であり、
実機で確定させてから直す。所有者に見てもらうか、既知の形状のデータ（autzen は
スタジアムと周辺地形）で判断する。

そのうえで、上方向の扱いを1箇所に集約する。

- **点群の上方向は Z** を既定とする（LAS / COPC の投影座標系に従う）
- カメラ・パン・ピッチ・標高・EDL がすべて同じ定義を参照すること。
  **`[0, 1, 0]` をコード中に散らさない**
- 将来 CRS やデータによって上方向が変わりうるので、**定数ではなく設定可能な値**にしておく
  （[ADR-0008](./ADR-0008-formats-and-crs.md) の通り PLY / PCD は座標系を持たないため、
  上方向が Z とは限らない）

### 実装（3段階に分けた。所有者の指示）

上方向を直す前に「空」という計器を先に用意しないと、直ったかどうかを確認する基準が
無いという指摘を受け、次の順で進めた。

1. **段階1（リファクタのみ、挙動不変）**: `src/renderer/up-axis.ts` を新設し、
   `DEFAULT_UP_AXIS`（この時点ではまだ`[0, 1, 0]`）と、上方向に直交する水平基底を作る
   `horizontalBasis()` を集約。`orbit-camera.ts` の `lookAt()` の up、`pan()` の
   `worldUp`、`eye()` の球面座標の式を、すべて `OrbitCamera.upAxis`
   （`setUpAxis()`/`getUpAxis()` で変更可能）経由に統一した。既存テストは無改造のまま
   全通過（`up=[0,1,0]`のとき新旧の式が代数的に一致することを確認済み）。
2. **段階2**: 空の背景（M2-0c）を実装。この時点ではまだ上方向が`[0,1,0]`のままなので、
   地平線が90度ずれて見える状態を意図的に作った（不具合の可視化）。
3. **段階3**: `up-axis.ts` の `DEFAULT_UP_AXIS` を `[0, 0, 1]` に変更（1行）。
   `src/renderer/orbit-camera.ts` の `pitch` 既定値(0.3 rad ≈ 17°)は変更していない
   — 上方向がYのままだったときにこの値が「ほぼ真上からの俯瞰」になっていたのは
   上方向のバグそのものが原因で、上方向を直せば同じ値が意図通り
   「少し見下ろしつつ地平線も見える」角度として機能する。

### 受け入れ条件

- [x] パンの上下方向が画面の上下と一致する — `pan()`が設定した`upAxis`だけを参照する
      ことを数式で確認（`orbit-camera.test.ts`「pan()も設定した上方向を使う」）。
      体感としての確認は下記「実機で、地面が水平に見える」と合わせて所有者の実機待ち
- [x] ピッチが地面に対して正しい平面で回る — `pitch=0`で視線が`upAxis`と直交（水平）に
      なること、`pitch`がクランプ境界付近で`upAxis`とほぼ平行になることをテストで確認
      （`orbit-camera.test.ts`「OrbitCamera 上方向 (M2-0b)」）
- [x] 上方向の定義がコード中で1箇所に集約されている — `src/renderer/up-axis.ts`。
      `[0, 1, 0]`/`[0, 0, 1]`のリテラルはこのファイルの`DEFAULT_UP_AXIS`定義以外に無い
      （`grep -rn "\[0, *1, *0\]\|\[0, *0, *1\]" src/renderer`で確認可能）
- [x] 上方向を変えられる（将来 PLY / PCD 等で Z-up でないデータに備える） —
      `OrbitCamera.setUpAxis()`。任意の軸で`eye()`/`pan()`が追従することをテストで確認
- [x] 実機で、地面が水平に見える（横倒しになっていない） — **確認済み。** M2-0cの
      空/グリッドを実機で確認する過程で、所有者から地面が横倒しに見えるという
      報告は出ておらず、以後のフィードバックは色と既定値のみ（下記M2-0c「既定の
      決定」参照）。`npm run tauri dev`のstdoutに`pitch=... upAxis=[...]
      eye=[...]`を出力する機械的な裏付けも変更なし

## M2-0c: 空の背景

### なぜ装飾ではないのか

**上下を判断する手がかりを画面に与えるため。** 現状は背景が単色で、地平線も空も無いため、
自分がどちらを向いているのか・どれだけ傾いているのかが分からない。
所有者からも「操作性は改善の余地がありそう」という指摘が出ている。

M2-0b で上方向を確定させたうえで空を入れると、**地平線が向きの基準**になる。

### 方式: 手続き的なグラデーション（テクスチャを使わない）

| 案 | 判断 |
|---|---|
| **グラデーション（天頂→地平線）を全画面パスで描く** | **採用。** アセット不要、メモリ増加なし、Adreno 610 でも軽い |
| キューブマップ / スカイボックス画像 | 却下。アセットが要り、RAM 4 GB の端末でメモリを食う |
| 大気散乱シミュレーション（UE 相当） | 却下。解析ツールに対して過剰。コストも高い |

ビューのレイ方向から色を決めるだけなので、テクスチャも頂点も要らない。

### 守ること

- **点より必ず奥に描く。** 深度書き込みを切り、点が常に手前に出るようにする
- **切り替えられること。** 「空 / 単色（暗） / 単色（明）」を選べるようにする。
  策定当時ここには「点群ビューアが伝統的に暗い背景を使うのは点のコントラストが
  最大になるからで、既定で強制せず実データを見て決める」と書いていた。
  実データを見た結果、**最終的な既定は単色(暗)**（策定時の判断通り）。
  グリッドの既定はオン。**判断の経緯（一時「空」を既定にした後に単色(暗)へ
  戻した理由）は本セクション末尾の「既定の決定」を参照。**
- **地平線の下も描く。** 空だけだと下を向いたときに背景が消える

### EDL との相互作用（先に書いておく）

[M2-1](./M2-shading-and-ui.md) の EDL は深度の不連続から陰影を作る。
**点群の輪郭と空の境界は深度差が無限大**になるため、EDL が輪郭に濃い縁取りを描く可能性がある。
良く見えるか汚く見えるかはやってみないと分からないが、**空を入れてから EDL を調整する**
順序にすること。逆だと EDL のパラメータを二度調整することになる。

### ガラス UI との相互作用

[ADR-0005](./ADR-0005-ui-shell.md) で「点群は高周波ノイズがありガラス上の文字が読みにくい」と
記録したが、**空はなめらかなので、ガラスの下が空になる領域はむしろ読みやすい**。
問題になるのは点群が背景の領域だけである。

### 実機報告と補強（段階2の後）

段階2（グラデーションのみ）を所有者が実機で確認した結果:

> 「地平線が分からない状態だ。地面がない？」「単色は機能している」

原因は2つ特定した。

1. **点群が地平線を隠している。** 段階2の時点では上方向がまだ`[0,1,0]`のままで
   ほぼ真上からの俯瞰になっており、点群が画面の大半を覆っていた
2. **グラデーションだけでは境界に見えない。** 色が滑らかに変わるだけで、
   「地面がある」ことを示す手がかりが無かった

対策として2つ補強した（太陽・雲は却下: 太陽は輝点で周辺の点を見えなくし、
雲は解析中の目線を引っ張る。空はこの道具では表現の対象ではなく向きを示す計器）。

**補強A: 地平線をはっきりさせる。** `src/renderer/sky.ts`の`groundColor`を、
`horizonColor`とは明度・色相の両方で明確に区別される中立な暗色に変更し、
`t=0`（地平線）に`fwidth()`基準の細い線を明示的に描くようにした。

**補強B: 地面のグリッド（本命）。** `src/renderer/ground-grid.ts`を新設。
上方向に直交する水平面とレイの交点を求め、アンチエイリアスされた格子線を
アルファブレンドで背景に重ねる全画面パス（sky.tsと同じ手法）。
Blender / CloudCompare / QGIS 3D 等の定番手法で、**向き**（水平面が見える）・
**尺度**（目盛りで距離感がつかめる。測量ツールとして本質的）・**地平線**
（遠方で収束して自然に地平線が現れる）の3つを同時に与える。
グリッド間隔は`niceGridCellSize()`でシーンのバウンディングボックス対角線から
1-2-5系列のキリのいい値を自動選択する（**固定値にしない**。例:
autzenのY幅4656m相当では100m刻み）。策定当時は既定オフだったが、実機フィードバックを
受けて**既定オンに変更**した（背景の既定は単色(暗)に戻ったが、グリッドの既定は
オンのまま。経緯は本セクション末尾の「既定の決定」を参照）。トグルでの
オン/オフ切り替えは変わらず残す。

### 地面グリッド（補強B）の受け入れ条件

- [x] グリッド間隔が点群のスケールに応じて自動で決まる（尺度。固定値ではない） —
      `niceGridCellSize()`をシーン対角線に対してテスト（`ground-grid.test.ts`）
- [x] グリッドの表示/非表示を切り替えられる（切替） — `PointCloudRenderer.setGridEnabled()`、
      `ViewerPanel`のチェックボックス
- [x] グリッドが上方向に直交する水平面上に表示され、向きの手がかりになる（向き） —
      **確認済み。** 所有者が実機でグリッドを確認したうえで「グリッドはありでデフォに
      したほうが良い」と判断しており（下記「既定の決定」参照）、向きの手がかりとして
      機能していることの裏付けになる

### 実機不具合（1回目）: 空にすると地面しか見えない／グリッドが効かない（NaN）

補強A/Bを実装した後、所有者の実機で次の2つが報告された。

> 「背景を『空』にすると地面しか見えない（どこを見ても地面色）」
> 「グリッドにチェックしても表示が変わらない」（点群は正しく見えている）

**原因は1つ。ワールド空間の行列をf32でGPUに渡していたこと。**

`sky.ts`/`ground-grid.ts`は当初、`invert(viewProj)`（ワールド空間のview-projection
逆行列）をuniformバッファ経由でf32のままGPUへ渡し、フラグメントシェーダで
`invViewProj * ndc`からレイ方向を復元していた。`scripts/diag-sky-ray.ts`で
実測すると、この設計には次の問題があった。

- `NEAR = 0.01` / `FAR = 1e7`（`point-cloud-renderer.ts`の実際の値）でダイナミック
  レンジが10^9あり、そこにautzenのような大きなワールド座標（X約637,000）が乗ると、
  `invViewProj`の成分は1.72e-9〜8.55e+7まで開く
- この行列でNDC座標を変換した後のw（同次座標の第4成分）は1.00e-7という小さい値に
  なる。これは1e7規模の成分どうしの引き算（桁落ちを伴う）から作られる値で、
  正しく求めるには14桁程度の精度が要るが、**f32の有効桁は約7桁しかない**
- 結果、f32にキャストした瞬間にwが0に桁落ちし、`farPoint4.xyz / w`がInf、
  `normalize(...)`がNaNになる。**f64では正しく計算できる同じ式が、f32にした
  瞬間に全ピクセルでNaNになる**（`diag-sky-ray.ts`の実行結果を参照）
- WGSLでは`NaN >= 0.0`が`false`と評価されるため、空のシェーダは全ピクセルが
  `else`分岐（`groundColor`）に落ちる。「空にすると地面しか見えない」という
  報告はこれで説明できる。グリッドのシェーダでは、`t = (groundHeight -
  dot(eye, up)) / denom`の`denom`（またはdirそのもの）がNaNになるため、
  すべての交点判定が意味を持たなくなり格子線が一切描かれない。「グリッドに
  チェックしても表示が変わらない」もこれで説明できる。**1つの原因が2つの
  症状として現れていた。**

**これは`mat4.ts`冒頭の既存の規約への違反だった。**同ファイルはこう書いている。

> ワールド座標そのものを行列に持たせず、カメラとノード原点の差分だけを
> 最終行列に残す

点群パイプライン（`multiply(viewProj, translation(origin))`をf64で計算してから
f32にキャストする、M1-2）はこの規約を守っていたので正しく動いていた。空と
グリッドは、ワールド空間の逆行列をそのままf32でGPUに渡してしまい、この規約を
破っていた。**M1-2で点の座標をノードローカル相対にしたのと同じ種類の問題が、
背景パスで再発した形。**

**直し方: 行列をシェーダに渡すのをやめた。** 代わりにJS側(f64)でレイ方向を
計算し、正規化済みの小さいベクトル（大きさ~1。f32で何の問題も起きない）だけを
GPUに渡すようにした。

- `raycast.ts`から`ndcPointToWorldRay(viewProj, ndcX, ndcY)`を新設（カーソル
  ズームが使っていて正しく動くことが確認済みの`screenPointToWorldRay`から、
  NDCを受け取る核の部分を抽出したもの。ndcは`[-1, 1]`の外側も扱える）
- `sky.ts`/`ground-grid.ts`の全画面三角形（頂点バッファ不要の巨大三角形）の
  3頂点それぞれについて、`point-cloud-renderer.ts`がこの関数をf64で呼び、
  得られた3つの方向を頂点シェーダへ`@location`で渡す。頂点シェーダの
  `clipPosition.w`はどの頂点でも1なので、フラグメントシェーダで受け取る
  補間値は単純な線形補間になる。**正規化は補間の後に行う**（先に正規化すると
  頂点ごとに違う縮尺で割ることになり、補間結果が本来の方向からずれるため）
- `sky.ts`のフラグメントシェーダはもう`invViewProj`も`eye`も要らない
  （`t = dot(normalize(補間したdir), up)`にeyeは不要）
- `ground-grid.ts`は交点の位置が要るため、**すべてカメラ相対**にした:
  平面の高さは`groundHeight - eyeHeight`（カメラからの相対値）として渡し、
  グリッドの位相合わせには「カメラ位置をグリッド間隔で割った余り」
  （`floorMod()`、`[0, cellSize)`に収まる小さい値）を渡す。大きい絶対座標は
  一切GPUに渡らない

補間で正規化前後の順序を変えたことによる近似誤差（頂点の方向を先に正規化せず、
線形補間してから正規化する分、画面の隅では真の透視方向とわずかにずれる）は
残るが、フルスクリーン三角形でスカイボックス/地面を描く際の標準的な手法であり、
このプロジェクトのFOV(60°)では実用上問題にならない、と当時は判断した。
**この判断は誤りだった。次項参照。**

当時の`scripts/diag-sky-ray.ts`は旧方式のNaN再現に加えて、新方式（3頂点の方向→
f32キャスト→GPUのラスタライザと同じ重心補間→正規化）をシミュレートし、
**NaNが出ないことだけ**を確認して「修正できた」と判断していた。

### 実機不具合（2回目）: 空やグリッドを入れると画面が真っ黒になる（同じ根本原因が別経路で再発）

1回目の修正をリリースした後、所有者の実機で次が報告された。

> 「空とかグリッド入れると画面が真っ黒になっちゃう」

**1回目の「対策」自体が壊れていた。原因は、正規化済みの方向ベクトルを
広い角度にわたって線形補間したこと。**

全画面三角形の頂点はNDCで`(-1,-1), (3,-1), (-1,3)`である。**NDC=3は画面の
右端の3倍外側**で、FOV60°（アスペクト16:9なら水平の半画角は約46°）でも、
NDC x=3へのレイは画面中心から**70度以上**離れる。正規化済みの単位ベクトル
（球面上の点）をこれだけ広い角度で線形補間すると、球面上の弧ではなく**弦**を
取ることになり、結果のベクトルは向きがずれるだけでなく**長さが縮む**
（実測: 画面中心付近で長さ0.55、隅では最大1.0だが場所によって0.53まで縮む。
角度が開くほど0に近づく設計上の欠陥で、条件によってはほぼゼロベクトルになり
`normalize(0)`がNaNになる）。**1回目と同じNaNが、別の経路（invViewProjの
桁落ち→線形補間による弦の短縮）で戻ってきていた。**

**教訓1（次に踏みやすい罠）: 単位ベクトル（方向）を広い角度にわたって
線形補間してはいけない。** 線形補間は「位置」や「まっすぐ変化する量」には
正しいが、正規化された方向ベクトルは球面上の点であり、補間は弦を取ることに
なる。全画面三角形は頂点が画面の3倍外側まで延びるため、この誤差が致命的な
大きさになる。

**教訓2（検証手法そのものの欠陥。次に踏みやすい罠）: 「NaNが出ないこと」は
「値が正しいこと」の証明にならない。** 1回目の受け入れ条件は
「`scripts/diag-sky-ray.ts`を拡張し、新方式でも同じ検証をしてf32でNaNが出ない
ことを示す」だったが、診断スクリプトはNaNの有無だけを確認しており、
**f64で直接計算した真値と数値的に一致するかを検証していなかった**。実際、
1回目の新方式は真値から最大0.48（3〜4桁大きい誤差）もずれていたが、
NaNにならない限りスクリプトは「成功」と表示していた。
**「NaNが出ない」は必要条件であって十分条件ではない。以後、レイ方向の
検証は必ず真値との数値比較（許容誤差つきのassert）で行うこと。**

**直し方（2回目）: レイ方向の補間そのものをやめた。** 頂点シェーダで補間する
のはNDC座標（位置）だけにする（位置の線形補間はアフィンな量なので正しい）。
フラグメントシェーダで、画素ごとに

```wgsl
let dir = normalize(u.forward.xyz + ndc.x * u.rightScaled.xyz + ndc.y * u.upScaled.xyz);
```

としてレイ方向を直接組み立てる。JS側(f64)で用意する値は次の3つ
（`mat4.ts`の`cameraBasis()`、および`point-cloud-renderer.ts`のFOV/アスペクト比から
求める）。

```
forward     = normalize(target - eye)                    // カメラの視線方向
right       = normalize(cross(forward, upAxis))
camUp       = normalize(cross(right, forward))
rightScaled = right * tan(fovY / 2) * アスペクト比
upScaled    = camUp * tan(fovY / 2)
```

これは**NDCがいくつでも厳密**（外挿ではなく、透視投影の逆関数そのもの。
`perspective()`の行列の作り方と代数的に対応する）。扱う数値はどれも大きさ~1、
行列もワールド座標の絶対値も一切GPUに渡らない。`ground-grid.ts`も同じ方式に
揃え、グリッド平面上の2D座標を作るための水平基底（`gridRight`/`gridForward`。
シーンのupAxisに直交する、カメラ基底とは別物）と組み合わせている。

**数値検証（`scripts/diag-sky-ray.ts`、およびその値を担保する`mat4.test.ts`の
`cameraBasis`テスト）:** autzenの実座標・FOV60°・アスペクト16:9で、画面の
中心・上下端・4隅（NDCが±1に近い、視野の端に一番近い場所）それぞれについて、
新方式の方向ベクトルとf64の真値（`invert(viewProj)`から直接求めた方向）との
誤差を測った。

| 方式 | 最大誤差 |
|---|---|
| 1回目（頂点方向の線形補間） | 約0.48（真値と無関係なレベル） |
| 2回目（基底から画素ごとに再構成、f64） | 約2e-8（f64の丸め誤差そのもの） |
| 2回目（基底から画素ごとに再構成、f32キャスト後） | 約3e-8（f32でも実用上ずれない） |

3〜4桁の差があり、壊れているかどうかは閾値（f64は1e-6、f32は1e-4を採用）で
明確に判別できる。

**担保したこと（テストで自動化できる範囲）:**

- `scripts/diag-sky-ray.ts`を全面的に書き直し、3世代（0: invViewProjをf32で
  渡す、1: 頂点方向の線形補間、2: 基底から画素ごとに再構成）を並べて検証する
  ようにした。世代0・1は既知の不具合が再現することを、世代2は真値と数値的に
  一致することを、それぞれ閾値つきでassertする（NaNの有無だけでなく、
  値そのものを検証する）
- `mat4.test.ts`に`cameraBasis()`のテストを追加: 基底が直交単位ベクトルに
  なること、`forward`が`eye→target`の正規化方向と一致すること、そして
  autzen相当の座標・実際のFOV/NEAR/FARで、画面の中心・4隅・上下端における
  再構成方向がf64の真値と1e-6以内で一致すること（回帰テスト。1回目の
  不具合の再発を防ぐ）
- `raycast.test.ts`の`ndcPointToWorldRay`テストは真値の計算そのものとして
  引き続き使う（カーソルズームのM1-5機能が使っていて正しく動くことが
  確認済みの実装であることが前提になっている）

**目視でしか担保できない範囲（GUIを持たないエージェントの限界）— 確認済み:**

- 空を有効にしたとき、画面の上側が空色・下側が地面色になっているか →
  所有者が実機で確認し、その後は色の見え方（白っぽさ・明るさ）についての
  フィードバックのみで、上下の色分け自体への指摘は無かった
- グリッドを有効にしたとき、実際に格子線が見えるか、位相のずれや歪みが
  気にならない程度か → 所有者が実機で確認し、既定オンにするよう指示するに
  至った（下記「既定の決定」参照）
- 点群がこれまで通り正しく描画され続けているか（M1の挙動を壊していないか） →
  上記2点の確認と同じ実機セッションで、点群側の描画崩れの報告は無かった

### 既定の決定（実機フィードバックを2往復して、最終的に単色(暗)+グリッドオンへ）

空とグリッドが実機で正しく動くようになった後、所有者から次のフィードバックが
2回に分けて来た。この節はその判断過程をすべて残す（**当初の記述を消すのではなく、
変わった理由ごと記録する**）。

**策定時点の記述（M2-0c）:**

> 既定で強制しない。点群ビューアが伝統的に暗い背景を使うのは、点のコントラストが
> 最大になるからである。明るい空は暗い点を見えにくくする。「空 / 単色（暗） /
> 単色（明）」を切り替えられるようにし、既定をどれにするかは実データを見て決める

つまり策定時点でも「既定は単色(暗)で確定」とは書いておらず、**実データを見て
決める**という条件付きの保留にしていた。以下の2回のフィードバックは、どちらも
この「実データを見て決める」を実際にやった結果であり、**途中で空/オンに触れて
いても、それ自体は方針転換ではない**。

**1回目のフィードバック（既定を空/オンに変更）:**

> 「良い感じ。空とグリッドはありをデフォにしたほうが良い気がするな。空はちょっと
> 白っぽくて違和感あるけど」

これを受けて`DEFAULT_BACKGROUND_MODE`を`"solid-dark"`から`"sky"`へ、
`DEFAULT_GRID_ENABLED`を`false`から`true`へ変更した。判断の根拠:

1. **策定時の根拠は「明るい空は暗い点を見えにくくする」だった。** 実際、初期の
   `horizon`色はRGB約0.75〜0.83（ほぼ白）で、この懸念がそのまま実機で
   「空はちょっと白っぽくて違和感ある」というフィードバックになって出た
2. **空を暗くしたことで、その根拠自体が弱まったと判断した。** `horizon`/`zenith`/
   `horizonLine`の明度を大きく下げ（彩度は保ったまま）、地平線が線として見える
   ことは`horizonLine`で維持した。背景が暗くなった分、点のコントラストを奪う
   という当時の懸念は当てはまりにくくなったと考えた
3. **向きと尺度が常に見えている利点のほうが大きいと判断した。** 空は上下判断の
   基準（地平線）を、グリッドは向き・尺度・地平線の3つを常に画面に与える
   （M2-0c冒頭「なぜ装飾ではないのか」、補強Bの記述を参照）
4. **グリッドは既定オフにする理由がもともと薄かった。** グリッドは薄い線
   （`GRID_MAX_ALPHA = 0.35`）を背景にアルファブレンドで重ねるだけで、点群の
   コントラストをほとんど損なわない

**2回目のフィードバック（背景の既定を単色(暗)へ戻す。グリッドは維持）:**

> 「もうちょっと明るくてもよいと思う。グリッドはありで黒をデフォルトにしよう。
> これで調整はいったん最後だ」

所有者が空/オンの状態を実際に実機で使ってみたうえで、**背景は単色(暗)のほうが
良いと判断した。** これを受けて`DEFAULT_BACKGROUND_MODE`を`"sky"`から
`"solid-dark"`へ戻した（`DEFAULT_GRID_ENABLED`は`true`のまま変更していない）。

**これは1回目の判断が誤りだった、という話ではなく、「実データを見て決める」を
2段階でやった結果である。** 1回目の変更（空をもっと暗くする）は2回目の判断の
前提になっており、無駄ではない。整理すると:

- **上の項目1〜3（点のコントラスト・向き/尺度の価値）は、実際に使ってみた結果
  「背景は単色(暗)のほうが良い」という判断に落ち着いた。** つまり策定時点の
  「暗い背景が既定」という判断が、実データによって裏付けられた形になる
- **項目4（グリッドは既定オフにする理由が薄い）は変わらず有効。** グリッドの
  既定はオンのまま維持した。所有者からも「グリッドはありで」と明示されている
- 空の色そのもの（`SKY_COLORS`）は、1回目で暗くしすぎた分を「白っぽくならない
  範囲で、元の値と暗くした値のおおよそ中間」まで明るく戻した
  （`src/renderer/sky.ts`参照）。空は既定ではなくなったが、選択肢としては
  変わらず残るため、この調整はそのまま活きる

**切り替え自体は残す。** 空 / 単色（暗） / 単色（明）の3モード、グリッドの
ON/OFFはこれまで通り選べる（`PointCloudRenderer.setBackgroundMode()`/
`setGridEnabled()`、`ViewerPanel`のUI）。変えたのは既定値だけで、選択肢そのものは
変えていない。

**所有者から「これで調整はいったん最後」と明示されたため、M2-0b/M2-0cの色・既定
まわりの調整はここで区切りとする。** 以後、見え方が気になった場合は`SKY_COLORS`
（`src/renderer/sky.ts`）を調整すればよい状態にしてある。

Potree が採用している。sofi のような RGB 無しデータを判読可能にする中心的な機能。

- 強さをパラメータ化し、UI から調整できるようにする（0 で無効）
- 半径（近傍として見るピクセル距離）も調整できると望ましい

## M2-2: カラーマップ切替

### やること

点の色をどの属性から決めるかを切り替えられるようにする。

| ソース | 対象 | 備考 |
|---|---|---|
| RGB | format 2/3/5/7/8/10 | 持たないファイルでは選べないようにする |
| 強度（intensity） | ほぼ全て | 最頻の代替。レンジの自動調整が要る |
| 標高（elevation） | 全て | 地形の判読に有効 |
| 分類（classification） | 分類済みデータ | 離散値。地面/植生/建物などに色を割り当てる |

ノードのバイナリ形式は既に intensity（u16）と classification（u8）を運んでいる。
**形式は変えずに実装できる。**

- 強度と標高は連続値なので、レンジの決め方（実データの分布に合わせる）が要点になる
- 分類は離散値なので、カラーマップは配色表になる
- **配色は明度が単調に変化するものを選ぶこと。** 虹色（jet）は明度が非単調で、
  実際には無い構造が見えてしまう

### 受け入れ条件

- [ ] 4つのソースを UI から切り替えられる
- [ ] RGB を持たないファイルでは RGB が選べない（グレーアウト等）
- [ ] `sofi.copc.laz` で強度・標高の切替が機能する
- [ ] `autzen-classified.copc.laz` で分類の切替が機能する
- [ ] `points-jack_he.copc.laz` で RGB が出る

## M2-4: ガラスの性能を実測する

### なぜ独立した項目にするのか

ADR-0005 で「`backdrop-filter` は背景が毎フレーム変わると毎フレーム再計算され、
**カメラ操作中という点群描画が最も苦しい瞬間**と競合する」というリスクを引き受けた。
そのとき「推測で大丈夫としない。必ず実測する」と定めた。

### やること

ガラスあり / なしで fps を比較する。M0・M2-1 と同じく**数値を残す**。

- ガラスパネルを表示した状態と、非表示にした状態での fps
- カメラを動かしている最中の fps（静止時ではない。ここが競合する瞬間）
- ぼかし半径を変えたときの影響

### 実測の結果に応じた対処（先に決めておく）

| 結果 | 対処 |
|---|---|
| 影響が小さい（数 fps） | そのまま |
| 無視できない | ぼかし半径を下げる、ガラス面積を絞る |

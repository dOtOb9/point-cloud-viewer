# M2: 点群を読めるようにする（陰影・カラーマップ・UI シェル）

- 状態: 未着手
- 前提: [M1](./M1-point-rendering.md) 完了、[ADR-0002](./ADR-0002-rendering-api.md)、[ADR-0005](./ADR-0005-ui-shell.md)

## このマイルストーンの目的

M1 で「点が出る」ようになった。M2 の目的は **「点群が読める」ようにすること**である。

この違いは実データで明確になった。`sofi.copc.laz`（3億6,438万点）は point format 6 で
**RGB を持たない**。現状では真っ白な塊にしか見えず、形状を判読できない。
そして調べた公開データ10件のうち**色を持つのは4件だけ**だった。

> 航空 LiDAR は基本的に強度と分類しか持たず、RGB は写真から後付けした製品にしかない。
> **現場のデータは色を持たないほうが多数派である。**

したがって EDL とカラーマップは「あると良い」ではなく、**無いと道具として使えない**機能である。

## M2-0: レンダラを描画対象の種類で分ける

### なぜ最初にやるのか

[ROADMAP.md](./ROADMAP.md) で、将来の DTM / TIN 表示が現状の構成に乗らないことを記録した。
`src/renderer/` は point sprite 専用に書かれており、三角形メッシュのパイプラインが無い。

**追加自体は難しくないが、「点群を描くもの」として書かれた構造のまま機能を積むと、
後から構造ごと作り直しになる。** 今なら安く、EDL とカラーマップを積んだ後では高い。

M1 では「点が正しく見える」というスコープを守るため意図的に触らなかった。ここで手当てする。

### やること

描画対象を1種類に決め打ちしている箇所を、複数種類を並べられる形にする。
**TIN の実装はしない。** 点群以外を受け入れられる構造にするところまで。

- 描画対象（現状は点群ノードのみ）を、パイプラインとバッファの組として抽象化する
- 1フレームの描画が「対象の集合を順に描く」形になっていること
- ノードのバイナリ形式は既に `magic "PCVN"` と `version` を持つので、
  将来 `"PCVM"`（メッシュ）を足せる。**この形式は変えない**

**やりすぎないこと。** 「将来こう拡張するかもしれない」を根拠に抽象を増やさない。
根拠のある拡張（メッシュ）に必要な分だけにする。所有者が追える構造を保つこと。

### 受け入れ条件

- [ ] 点群の描画が、種類を持つ描画対象の1つとして扱われている
- [ ] 見た目と性能が M1 から変わっていない（リグレッションが無い）
- [ ] 既存のテストが通る

## M2-0b: 上方向（up 軸）を確定させる

### これが先に要る理由

**点群データは Z-up だが、カメラは Y-up を仮定しており、変換する箇所がどこにも無い。**

```
autzen-classified.copc.laz の範囲:  X 3426 m × Y 4656 m × Z 209 m
                                                          ↑ Z だけ極端に薄い = Z が標高
```

LAS / COPC は投影座標系なので Z が標高である。一方 `orbit-camera.ts` は:

```ts
lookAt(this.eye(), this.target, [0, 1, 0]);   // Y を上と仮定
const worldUp: [number, number, number] = [0, 1, 0];  // パンも同じ
```

### 実機で確認した症状（当初の推定を訂正）

当初このファイルには「点群が横倒しで描画されている」と書いたが、**これは不正確だった。**
所有者に実機で確認してもらった結果は「**上から俯瞰したように見える**」であり、
以下が正しい説明である。

初期状態（`pitch = 0.3` rad ≈ 17°、`yaw = 0`）では、カメラはほぼ **+Z の真上**に位置して
−Z 方向を見る。データは Z が薄い（autzen で 209 m）ため、**XY 平面を正面から見る
＝真上からの俯瞰**になる。所有者の観察と一致する。

問題はここから。カメラの「上」は **+Y**、つまりデータ上は**水平方向**（北など）である。

| `pitch` | 本来あるべき見え方 | 実際 |
|---|---|---|
| 0° | **水平。地平線が見える** | **真上からの俯瞰** |
| ±90° | 真上 / 真下 | 真横 |

**つまり「横倒し」ではなく、仰角の軸が 90 度回っている。**

決定的なのは、**地平線を見る姿勢に自然に到達できない**こと。カメラにとっての「水平」が
データの水平と一致していないため、空を入れても地平線が正しい向きに出ない。

**気づかれなかった理由は、画面に上下を判断する手がかりが一つも無いこと。**
空も地平線もグリッドも無いため、真上から見ている間は不一致が現れない。
カメラを傾けると、建物や樹木が画面の横方向に伸びて見えるはずである。

所有者の「形状は大丈夫そう」という当初の判断は正しい（形そのものは正しく出ている）。

### 影響範囲（空だけの問題ではない）

| 機能 | 上方向への依存 |
|---|---|
| パン | 画面の上下方向の算出 |
| ピッチ | 回転する平面 |
| **標高カラーマップ**（M2-2） | どの軸が標高か |
| **EDL**（M2-1） | 陰影の向き |
| **空と地平線**（M2-0c） | 地平線の向きそのもの |
| DTM / TIN（[ROADMAP](./ROADMAP.md)） | 地面の定義そのもの |
| タッチ操作（[M3-6](./M3-release-and-update.md)） | パンと同じ |

### やること

**まず現状を確認すること。** 「横倒しになっている」は本ファイルを書いた時点での推定であり、
実機で確定させてから直す。所有者に見てもらうか、既知の形状のデータ（autzen は
スタジアムと周辺地形）で判断する。

そのうえで、上方向の扱いを1箇所に集約する。

- **点群の上方向は Z** を既定とする（LAS / COPC の投影座標系に従う）
- カメラ・パン・ピッチ・標高・EDL がすべて同じ定義を参照すること。
  **`[0, 1, 0]` をコード中に散らさない**
- 将来 CRS やデータによって上方向が変わりうるので、**定数ではなく設定可能な値**にしておく
  （[ADR-0008](./ADR-0008-formats-and-crs.md) の通り PLY / PCD は座標系を持たないため、
  上方向が Z とは限らない）

### 実装（3段階に分けた。所有者の指示）

上方向を直す前に「空」という計器を先に用意しないと、直ったかどうかを確認する基準が
無いという指摘を受け、次の順で進めた。

1. **段階1（リファクタのみ、挙動不変）**: `src/renderer/up-axis.ts` を新設し、
   `DEFAULT_UP_AXIS`（この時点ではまだ`[0, 1, 0]`）と、上方向に直交する水平基底を作る
   `horizontalBasis()` を集約。`orbit-camera.ts` の `lookAt()` の up、`pan()` の
   `worldUp`、`eye()` の球面座標の式を、すべて `OrbitCamera.upAxis`
   （`setUpAxis()`/`getUpAxis()` で変更可能）経由に統一した。既存テストは無改造のまま
   全通過（`up=[0,1,0]`のとき新旧の式が代数的に一致することを確認済み）。
2. **段階2**: 空の背景（M2-0c）を実装。この時点ではまだ上方向が`[0,1,0]`のままなので、
   地平線が90度ずれて見える状態を意図的に作った（不具合の可視化）。
3. **段階3**: `up-axis.ts` の `DEFAULT_UP_AXIS` を `[0, 0, 1]` に変更（1行）。
   `src/renderer/orbit-camera.ts` の `pitch` 既定値(0.3 rad ≈ 17°)は変更していない
   — 上方向がYのままだったときにこの値が「ほぼ真上からの俯瞰」になっていたのは
   上方向のバグそのものが原因で、上方向を直せば同じ値が意図通り
   「少し見下ろしつつ地平線も見える」角度として機能する。

### 受け入れ条件

- [x] パンの上下方向が画面の上下と一致する — `pan()`が設定した`upAxis`だけを参照する
      ことを数式で確認（`orbit-camera.test.ts`「pan()も設定した上方向を使う」）。
      体感としての確認は下記「実機で、地面が水平に見える」と合わせて所有者の実機待ち
- [x] ピッチが地面に対して正しい平面で回る — `pitch=0`で視線が`upAxis`と直交（水平）に
      なること、`pitch`がクランプ境界付近で`upAxis`とほぼ平行になることをテストで確認
      （`orbit-camera.test.ts`「OrbitCamera 上方向 (M2-0b)」）
- [x] 上方向の定義がコード中で1箇所に集約されている — `src/renderer/up-axis.ts`。
      `[0, 1, 0]`/`[0, 0, 1]`のリテラルはこのファイルの`DEFAULT_UP_AXIS`定義以外に無い
      （`grep -rn "\[0, *1, *0\]\|\[0, *0, *1\]" src/renderer`で確認可能）
- [x] 上方向を変えられる（将来 PLY / PCD 等で Z-up でないデータに備える） —
      `OrbitCamera.setUpAxis()`。任意の軸で`eye()`/`pan()`が追従することをテストで確認
- [x] 実機で、地面が水平に見える（横倒しになっていない） — **確認済み。** M2-0cの
      空/グリッドを実機で確認する過程で、所有者から地面が横倒しに見えるという
      報告は出ておらず、以後のフィードバックは色と既定値のみ（下記M2-0c「既定の
      決定」参照）。`npm run tauri dev`のstdoutに`pitch=... upAxis=[...]
      eye=[...]`を出力する機械的な裏付けも変更なし

## M2-0c: 空の背景

### なぜ装飾ではないのか

**上下を判断する手がかりを画面に与えるため。** 現状は背景が単色で、地平線も空も無いため、
自分がどちらを向いているのか・どれだけ傾いているのかが分からない。
所有者からも「操作性は改善の余地がありそう」という指摘が出ている。

M2-0b で上方向を確定させたうえで空を入れると、**地平線が向きの基準**になる。

### 方式: 手続き的なグラデーション（テクスチャを使わない）

| 案 | 判断 |
|---|---|
| **グラデーション（天頂→地平線）を全画面パスで描く** | **採用。** アセット不要、メモリ増加なし、Adreno 610 でも軽い |
| キューブマップ / スカイボックス画像 | 却下。アセットが要り、RAM 4 GB の端末でメモリを食う |
| 大気散乱シミュレーション（UE 相当） | 却下。解析ツールに対して過剰。コストも高い |

ビューのレイ方向から色を決めるだけなので、テクスチャも頂点も要らない。

### 守ること

- **点より必ず奥に描く。** 深度書き込みを切り、点が常に手前に出るようにする
- **切り替えられること。** 「空 / 単色（暗） / 単色（明）」を選べるようにする。
  策定当時ここには「点群ビューアが伝統的に暗い背景を使うのは点のコントラストが
  最大になるからで、既定で強制せず実データを見て決める」と書いていた。
  実データを見た結果、**最終的な既定は単色(暗)**（策定時の判断通り）。
  グリッドの既定はオン。**判断の経緯（一時「空」を既定にした後に単色(暗)へ
  戻した理由）は本セクション末尾の「既定の決定」を参照。**
- **地平線の下も描く。** 空だけだと下を向いたときに背景が消える

### EDL との相互作用（先に書いておく）

[M2-1](./M2-shading-and-ui.md) の EDL は深度の不連続から陰影を作る。
**点群の輪郭と空の境界は深度差が無限大**になるため、EDL が輪郭に濃い縁取りを描く可能性がある。
良く見えるか汚く見えるかはやってみないと分からないが、**空を入れてから EDL を調整する**
順序にすること。逆だと EDL のパラメータを二度調整することになる。

### ガラス UI との相互作用

[ADR-0005](./ADR-0005-ui-shell.md) で「点群は高周波ノイズがありガラス上の文字が読みにくい」と
記録したが、**空はなめらかなので、ガラスの下が空になる領域はむしろ読みやすい**。
問題になるのは点群が背景の領域だけである。

### 実機報告と補強（段階2の後）

段階2（グラデーションのみ）を所有者が実機で確認した結果:

> 「地平線が分からない状態だ。地面がない？」「単色は機能している」

原因は2つ特定した。

1. **点群が地平線を隠している。** 段階2の時点では上方向がまだ`[0,1,0]`のままで
   ほぼ真上からの俯瞰になっており、点群が画面の大半を覆っていた
2. **グラデーションだけでは境界に見えない。** 色が滑らかに変わるだけで、
   「地面がある」ことを示す手がかりが無かった

対策として2つ補強した（太陽・雲は却下: 太陽は輝点で周辺の点を見えなくし、
雲は解析中の目線を引っ張る。空はこの道具では表現の対象ではなく向きを示す計器）。

**補強A: 地平線をはっきりさせる。** `src/renderer/sky.ts`の`groundColor`を、
`horizonColor`とは明度・色相の両方で明確に区別される中立な暗色に変更し、
`t=0`（地平線）に`fwidth()`基準の細い線を明示的に描くようにした。

**補強B: 地面のグリッド（本命）。** `src/renderer/ground-grid.ts`を新設。
上方向に直交する水平面とレイの交点を求め、アンチエイリアスされた格子線を
アルファブレンドで背景に重ねる全画面パス（sky.tsと同じ手法）。
Blender / CloudCompare / QGIS 3D 等の定番手法で、**向き**（水平面が見える）・
**尺度**（目盛りで距離感がつかめる。測量ツールとして本質的）・**地平線**
（遠方で収束して自然に地平線が現れる）の3つを同時に与える。
グリッド間隔は`niceGridCellSize()`でシーンのバウンディングボックス対角線から
1-2-5系列のキリのいい値を自動選択する（**固定値にしない**。例:
autzenのY幅4656m相当では100m刻み）。策定当時は既定オフだったが、実機フィードバックを
受けて**既定オンに変更**した（背景の既定は単色(暗)に戻ったが、グリッドの既定は
オンのまま。経緯は本セクション末尾の「既定の決定」を参照）。トグルでの
オン/オフ切り替えは変わらず残す。

### 地面グリッド（補強B）の受け入れ条件

- [x] グリッド間隔が点群のスケールに応じて自動で決まる（尺度。固定値ではない） —
      `niceGridCellSize()`をシーン対角線に対してテスト（`ground-grid.test.ts`）
- [x] グリッドの表示/非表示を切り替えられる（切替） — `PointCloudRenderer.setGridEnabled()`、
      `ViewerPanel`のチェックボックス
- [x] グリッドが上方向に直交する水平面上に表示され、向きの手がかりになる（向き） —
      **確認済み。** 所有者が実機でグリッドを確認したうえで「グリッドはありでデフォに
      したほうが良い」と判断しており（下記「既定の決定」参照）、向きの手がかりとして
      機能していることの裏付けになる

### 実機不具合（1回目）: 空にすると地面しか見えない／グリッドが効かない（NaN）

補強A/Bを実装した後、所有者の実機で次の2つが報告された。

> 「背景を『空』にすると地面しか見えない（どこを見ても地面色）」
> 「グリッドにチェックしても表示が変わらない」（点群は正しく見えている）

**原因は1つ。ワールド空間の行列をf32でGPUに渡していたこと。**

`sky.ts`/`ground-grid.ts`は当初、`invert(viewProj)`（ワールド空間のview-projection
逆行列）をuniformバッファ経由でf32のままGPUへ渡し、フラグメントシェーダで
`invViewProj * ndc`からレイ方向を復元していた。`scripts/diag-sky-ray.ts`で
実測すると、この設計には次の問題があった。

- `NEAR = 0.01` / `FAR = 1e7`（`point-cloud-renderer.ts`の実際の値）でダイナミック
  レンジが10^9あり、そこにautzenのような大きなワールド座標（X約637,000）が乗ると、
  `invViewProj`の成分は1.72e-9〜8.55e+7まで開く
- この行列でNDC座標を変換した後のw（同次座標の第4成分）は1.00e-7という小さい値に
  なる。これは1e7規模の成分どうしの引き算（桁落ちを伴う）から作られる値で、
  正しく求めるには14桁程度の精度が要るが、**f32の有効桁は約7桁しかない**
- 結果、f32にキャストした瞬間にwが0に桁落ちし、`farPoint4.xyz / w`がInf、
  `normalize(...)`がNaNになる。**f64では正しく計算できる同じ式が、f32にした
  瞬間に全ピクセルでNaNになる**（`diag-sky-ray.ts`の実行結果を参照）
- WGSLでは`NaN >= 0.0`が`false`と評価されるため、空のシェーダは全ピクセルが
  `else`分岐（`groundColor`）に落ちる。「空にすると地面しか見えない」という
  報告はこれで説明できる。グリッドのシェーダでは、`t = (groundHeight -
  dot(eye, up)) / denom`の`denom`（またはdirそのもの）がNaNになるため、
  すべての交点判定が意味を持たなくなり格子線が一切描かれない。「グリッドに
  チェックしても表示が変わらない」もこれで説明できる。**1つの原因が2つの
  症状として現れていた。**

**これは`mat4.ts`冒頭の既存の規約への違反だった。**同ファイルはこう書いている。

> ワールド座標そのものを行列に持たせず、カメラとノード原点の差分だけを
> 最終行列に残す

点群パイプライン（`multiply(viewProj, translation(origin))`をf64で計算してから
f32にキャストする、M1-2）はこの規約を守っていたので正しく動いていた。空と
グリッドは、ワールド空間の逆行列をそのままf32でGPUに渡してしまい、この規約を
破っていた。**M1-2で点の座標をノードローカル相対にしたのと同じ種類の問題が、
背景パスで再発した形。**

**直し方: 行列をシェーダに渡すのをやめた。** 代わりにJS側(f64)でレイ方向を
計算し、正規化済みの小さいベクトル（大きさ~1。f32で何の問題も起きない）だけを
GPUに渡すようにした。

- `raycast.ts`から`ndcPointToWorldRay(viewProj, ndcX, ndcY)`を新設（カーソル
  ズームが使っていて正しく動くことが確認済みの`screenPointToWorldRay`から、
  NDCを受け取る核の部分を抽出したもの。ndcは`[-1, 1]`の外側も扱える）
- `sky.ts`/`ground-grid.ts`の全画面三角形（頂点バッファ不要の巨大三角形）の
  3頂点それぞれについて、`point-cloud-renderer.ts`がこの関数をf64で呼び、
  得られた3つの方向を頂点シェーダへ`@location`で渡す。頂点シェーダの
  `clipPosition.w`はどの頂点でも1なので、フラグメントシェーダで受け取る
  補間値は単純な線形補間になる。**正規化は補間の後に行う**（先に正規化すると
  頂点ごとに違う縮尺で割ることになり、補間結果が本来の方向からずれるため）
- `sky.ts`のフラグメントシェーダはもう`invViewProj`も`eye`も要らない
  （`t = dot(normalize(補間したdir), up)`にeyeは不要）
- `ground-grid.ts`は交点の位置が要るため、**すべてカメラ相対**にした:
  平面の高さは`groundHeight - eyeHeight`（カメラからの相対値）として渡し、
  グリッドの位相合わせには「カメラ位置をグリッド間隔で割った余り」
  （`floorMod()`、`[0, cellSize)`に収まる小さい値）を渡す。大きい絶対座標は
  一切GPUに渡らない

補間で正規化前後の順序を変えたことによる近似誤差（頂点の方向を先に正規化せず、
線形補間してから正規化する分、画面の隅では真の透視方向とわずかにずれる）は
残るが、フルスクリーン三角形でスカイボックス/地面を描く際の標準的な手法であり、
このプロジェクトのFOV(60°)では実用上問題にならない、と当時は判断した。
**この判断は誤りだった。次項参照。**

当時の`scripts/diag-sky-ray.ts`は旧方式のNaN再現に加えて、新方式（3頂点の方向→
f32キャスト→GPUのラスタライザと同じ重心補間→正規化）をシミュレートし、
**NaNが出ないことだけ**を確認して「修正できた」と判断していた。

### 実機不具合（2回目）: 空やグリッドを入れると画面が真っ黒になる（同じ根本原因が別経路で再発）

1回目の修正をリリースした後、所有者の実機で次が報告された。

> 「空とかグリッド入れると画面が真っ黒になっちゃう」

**1回目の「対策」自体が壊れていた。原因は、正規化済みの方向ベクトルを
広い角度にわたって線形補間したこと。**

全画面三角形の頂点はNDCで`(-1,-1), (3,-1), (-1,3)`である。**NDC=3は画面の
右端の3倍外側**で、FOV60°（アスペクト16:9なら水平の半画角は約46°）でも、
NDC x=3へのレイは画面中心から**70度以上**離れる。正規化済みの単位ベクトル
（球面上の点）をこれだけ広い角度で線形補間すると、球面上の弧ではなく**弦**を
取ることになり、結果のベクトルは向きがずれるだけでなく**長さが縮む**
（実測: 画面中心付近で長さ0.55、隅では最大1.0だが場所によって0.53まで縮む。
角度が開くほど0に近づく設計上の欠陥で、条件によってはほぼゼロベクトルになり
`normalize(0)`がNaNになる）。**1回目と同じNaNが、別の経路（invViewProjの
桁落ち→線形補間による弦の短縮）で戻ってきていた。**

**教訓1（次に踏みやすい罠）: 単位ベクトル（方向）を広い角度にわたって
線形補間してはいけない。** 線形補間は「位置」や「まっすぐ変化する量」には
正しいが、正規化された方向ベクトルは球面上の点であり、補間は弦を取ることに
なる。全画面三角形は頂点が画面の3倍外側まで延びるため、この誤差が致命的な
大きさになる。

**教訓2（検証手法そのものの欠陥。次に踏みやすい罠）: 「NaNが出ないこと」は
「値が正しいこと」の証明にならない。** 1回目の受け入れ条件は
「`scripts/diag-sky-ray.ts`を拡張し、新方式でも同じ検証をしてf32でNaNが出ない
ことを示す」だったが、診断スクリプトはNaNの有無だけを確認しており、
**f64で直接計算した真値と数値的に一致するかを検証していなかった**。実際、
1回目の新方式は真値から最大0.48（3〜4桁大きい誤差）もずれていたが、
NaNにならない限りスクリプトは「成功」と表示していた。
**「NaNが出ない」は必要条件であって十分条件ではない。以後、レイ方向の
検証は必ず真値との数値比較（許容誤差つきのassert）で行うこと。**

**直し方（2回目）: レイ方向の補間そのものをやめた。** 頂点シェーダで補間する
のはNDC座標（位置）だけにする（位置の線形補間はアフィンな量なので正しい）。
フラグメントシェーダで、画素ごとに

```wgsl
let dir = normalize(u.forward.xyz + ndc.x * u.rightScaled.xyz + ndc.y * u.upScaled.xyz);
```

としてレイ方向を直接組み立てる。JS側(f64)で用意する値は次の3つ
（`mat4.ts`の`cameraBasis()`、および`point-cloud-renderer.ts`のFOV/アスペクト比から
求める）。

```
forward     = normalize(target - eye)                    // カメラの視線方向
right       = normalize(cross(forward, upAxis))
camUp       = normalize(cross(right, forward))
rightScaled = right * tan(fovY / 2) * アスペクト比
upScaled    = camUp * tan(fovY / 2)
```

これは**NDCがいくつでも厳密**（外挿ではなく、透視投影の逆関数そのもの。
`perspective()`の行列の作り方と代数的に対応する）。扱う数値はどれも大きさ~1、
行列もワールド座標の絶対値も一切GPUに渡らない。`ground-grid.ts`も同じ方式に
揃え、グリッド平面上の2D座標を作るための水平基底（`gridRight`/`gridForward`。
シーンのupAxisに直交する、カメラ基底とは別物）と組み合わせている。

**数値検証（`scripts/diag-sky-ray.ts`、およびその値を担保する`mat4.test.ts`の
`cameraBasis`テスト）:** autzenの実座標・FOV60°・アスペクト16:9で、画面の
中心・上下端・4隅（NDCが±1に近い、視野の端に一番近い場所）それぞれについて、
新方式の方向ベクトルとf64の真値（`invert(viewProj)`から直接求めた方向）との
誤差を測った。

| 方式 | 最大誤差 |
|---|---|
| 1回目（頂点方向の線形補間） | 約0.48（真値と無関係なレベル） |
| 2回目（基底から画素ごとに再構成、f64） | 約2e-8（f64の丸め誤差そのもの） |
| 2回目（基底から画素ごとに再構成、f32キャスト後） | 約3e-8（f32でも実用上ずれない） |

3〜4桁の差があり、壊れているかどうかは閾値（f64は1e-6、f32は1e-4を採用）で
明確に判別できる。

**担保したこと（テストで自動化できる範囲）:**

- `scripts/diag-sky-ray.ts`を全面的に書き直し、3世代（0: invViewProjをf32で
  渡す、1: 頂点方向の線形補間、2: 基底から画素ごとに再構成）を並べて検証する
  ようにした。世代0・1は既知の不具合が再現することを、世代2は真値と数値的に
  一致することを、それぞれ閾値つきでassertする（NaNの有無だけでなく、
  値そのものを検証する）
- `mat4.test.ts`に`cameraBasis()`のテストを追加: 基底が直交単位ベクトルに
  なること、`forward`が`eye→target`の正規化方向と一致すること、そして
  autzen相当の座標・実際のFOV/NEAR/FARで、画面の中心・4隅・上下端における
  再構成方向がf64の真値と1e-6以内で一致すること（回帰テスト。1回目の
  不具合の再発を防ぐ）
- `raycast.test.ts`の`ndcPointToWorldRay`テストは真値の計算そのものとして
  引き続き使う（カーソルズームのM1-5機能が使っていて正しく動くことが
  確認済みの実装であることが前提になっている）

**目視でしか担保できない範囲（GUIを持たないエージェントの限界）— 確認済み:**

- 空を有効にしたとき、画面の上側が空色・下側が地面色になっているか →
  所有者が実機で確認し、その後は色の見え方（白っぽさ・明るさ）についての
  フィードバックのみで、上下の色分け自体への指摘は無かった
- グリッドを有効にしたとき、実際に格子線が見えるか、位相のずれや歪みが
  気にならない程度か → 所有者が実機で確認し、既定オンにするよう指示するに
  至った（下記「既定の決定」参照）
- 点群がこれまで通り正しく描画され続けているか（M1の挙動を壊していないか） →
  上記2点の確認と同じ実機セッションで、点群側の描画崩れの報告は無かった

### 既定の決定（実機フィードバックを2往復して、最終的に単色(暗)+グリッドオンへ）

空とグリッドが実機で正しく動くようになった後、所有者から次のフィードバックが
2回に分けて来た。この節はその判断過程をすべて残す（**当初の記述を消すのではなく、
変わった理由ごと記録する**）。

**策定時点の記述（M2-0c）:**

> 既定で強制しない。点群ビューアが伝統的に暗い背景を使うのは、点のコントラストが
> 最大になるからである。明るい空は暗い点を見えにくくする。「空 / 単色（暗） /
> 単色（明）」を切り替えられるようにし、既定をどれにするかは実データを見て決める

つまり策定時点でも「既定は単色(暗)で確定」とは書いておらず、**実データを見て
決める**という条件付きの保留にしていた。以下の2回のフィードバックは、どちらも
この「実データを見て決める」を実際にやった結果であり、**途中で空/オンに触れて
いても、それ自体は方針転換ではない**。

**1回目のフィードバック（既定を空/オンに変更）:**

> 「良い感じ。空とグリッドはありをデフォにしたほうが良い気がするな。空はちょっと
> 白っぽくて違和感あるけど」

これを受けて`DEFAULT_BACKGROUND_MODE`を`"solid-dark"`から`"sky"`へ、
`DEFAULT_GRID_ENABLED`を`false`から`true`へ変更した。判断の根拠:

1. **策定時の根拠は「明るい空は暗い点を見えにくくする」だった。** 実際、初期の
   `horizon`色はRGB約0.75〜0.83（ほぼ白）で、この懸念がそのまま実機で
   「空はちょっと白っぽくて違和感ある」というフィードバックになって出た
2. **空を暗くしたことで、その根拠自体が弱まったと判断した。** `horizon`/`zenith`/
   `horizonLine`の明度を大きく下げ（彩度は保ったまま）、地平線が線として見える
   ことは`horizonLine`で維持した。背景が暗くなった分、点のコントラストを奪う
   という当時の懸念は当てはまりにくくなったと考えた
3. **向きと尺度が常に見えている利点のほうが大きいと判断した。** 空は上下判断の
   基準（地平線）を、グリッドは向き・尺度・地平線の3つを常に画面に与える
   （M2-0c冒頭「なぜ装飾ではないのか」、補強Bの記述を参照）
4. **グリッドは既定オフにする理由がもともと薄かった。** グリッドは薄い線
   （`GRID_MAX_ALPHA = 0.35`）を背景にアルファブレンドで重ねるだけで、点群の
   コントラストをほとんど損なわない

**2回目のフィードバック（背景の既定を単色(暗)へ戻す。グリッドは維持）:**

> 「もうちょっと明るくてもよいと思う。グリッドはありで黒をデフォルトにしよう。
> これで調整はいったん最後だ」

所有者が空/オンの状態を実際に実機で使ってみたうえで、**背景は単色(暗)のほうが
良いと判断した。** これを受けて`DEFAULT_BACKGROUND_MODE`を`"sky"`から
`"solid-dark"`へ戻した（`DEFAULT_GRID_ENABLED`は`true`のまま変更していない）。

**これは1回目の判断が誤りだった、という話ではなく、「実データを見て決める」を
2段階でやった結果である。** 1回目の変更（空をもっと暗くする）は2回目の判断の
前提になっており、無駄ではない。整理すると:

- **上の項目1〜3（点のコントラスト・向き/尺度の価値）は、実際に使ってみた結果
  「背景は単色(暗)のほうが良い」という判断に落ち着いた。** つまり策定時点の
  「暗い背景が既定」という判断が、実データによって裏付けられた形になる
- **項目4（グリッドは既定オフにする理由が薄い）は変わらず有効。** グリッドの
  既定はオンのまま維持した。所有者からも「グリッドはありで」と明示されている
- 空の色そのもの（`SKY_COLORS`）は、1回目で暗くしすぎた分を「白っぽくならない
  範囲で、元の値と暗くした値のおおよそ中間」まで明るく戻した
  （`src/renderer/sky.ts`参照）。空は既定ではなくなったが、選択肢としては
  変わらず残るため、この調整はそのまま活きる

**切り替え自体は残す。** 空 / 単色（暗） / 単色（明）の3モード、グリッドの
ON/OFFはこれまで通り選べる（`PointCloudRenderer.setBackgroundMode()`/
`setGridEnabled()`、`ViewerPanel`のUI）。変えたのは既定値だけで、選択肢そのものは
変えていない。

**所有者から「これで調整はいったん最後」と明示されたため、M2-0b/M2-0cの色・既定
まわりの調整はここで区切りとする。** 以後、見え方が気になった場合は`SKY_COLORS`
（`src/renderer/sky.ts`）を調整すればよい状態にしてある。

## M2-1: EDL（Eye-Dome Lighting）

### なぜ必要か

隣接ピクセルの深度差から陰影を作り、**色を持たない点群でも凹凸構造が読めるようにする**手法。
Potree が採用している。sofi のような RGB 無しデータを判読可能にする中心的な機能。

### やること

深度バッファを入力に取るポストプロセスパスを追加する。

- 各ピクセルについて近傍の深度と比較し、手前にある隣接点との差を陰影として落とす
- 強さをパラメータ化し、UI から調整できるようにする（0 で無効）
- 半径（近傍として見るピクセル距離）も調整できると望ましい

### 実装

**方式: 点群だけを独立したオフスクリーンの色+深度テクスチャに先に描き、EDLの
合成パスでそのテクスチャだけを読む。** 空・グリッドは今まで通りスワップチェーンへ
直接描く。

既存の`drawFrame()`は、空・グリッド・点群を1つのレンダーパスの中に順番に描いて
いた（空・グリッドは`depthWriteEnabled=false, depthCompare="always"`で深度を
書かないので、後から描く点群が常に手前に残る、という既存の設計）。この構成の
まま点群にだけEDLを掛けようとすると、フラグメントシェーダの中で「このピクセルが
点由来か背景由来か」を区別する手段が無い。そこで次の2パス構成にした。

- **パス1（オフスクリーン）**: 既存の点群パイプラインをそのまま使い、
  `src/renderer/point-cloud-renderer.ts`が新設したオフスクリーンの色テクスチャ
  (`rgba8unorm`)・深度テクスチャ(`depth24plus`、スワップチェーン用の深度とは別物)
  に描く。色はクリア時に`alpha=0`にする。
- **パス2（スワップチェーン）**: 空・グリッドを**今まで通り**スワップチェーンへ
  直接描く（`sky.ts`/`ground-grid.ts`は一切変更していない）。その直後・最後に
  `src/renderer/edl.ts`の`EdlPass.draw()`を呼び、パス1のオフスクリーンの色・深度を
  読んで陰影を掛けてから、点群を空・グリッドの手前に合成する。
- **分離の要**: `EdlPass`のフラグメントシェーダは、オフスクリーンの深度が
  クリア値(1.0=遠クリップ)のまま、つまり「そのピクセルには点が1つも描かれて
  いない」場合に`discard`する。WebGPUの`discard`はフラグメントの書き込みを
  完全に取りやめる動作なので、そのピクセルには既に描かれている空・グリッド・
  単色の背景がそのまま残る。**これにより、EDLの陰影計算そのものが空・グリッドの
  ピクセルに一切触れない**（掛けてから戻す、ではなく、そもそも触らない）。

**EDLのアルゴリズム**（`src/renderer/edl.ts`、Potreeのedl.fragが元ネタ）:

1. NDC深度(0..1)を`linearizeDepth()`でカメラからの実距離に戻す
   （`mat4.ts`の`perspective()`に対応する式: `near*far/(far - ndcDepth*(far-near))`）
2. 8方向の近傍ピクセル（距離は`radiusPx`で調整可能）と深度を比べ、
   「自分のほうが奥にある」ぶん(`max(0, 自分の深度 - 近傍の深度)`)だけ足し合わせて
   平均する（`response`）
3. `shade = exp(-response * 300 * strength)`を色に掛ける。自分が近傍より
   手前にある場合は差が0にクリップされるので暗くならない。奥まった場所だけが
   暗くなる（Eye-Dome Lightingの見た目の根拠）

`edlShadingFactor()`/`linearizeDepth()`はGPUに依存しない純粋関数として
`src/renderer/edl.ts`に切り出し、`src/renderer/edl.test.ts`でvitestから直接
検証している。WGSL側（`EDL_SHADER_SRC`内の同名ロジック）はこれと同じ式を
手で再実装したものであり、**GPUが無い環境では直接は検証できない**
（式が一致していることはコメントで対応を明記し、目視で保っている）。

### 他に検討した案（空・グリッドとの分離の方式）

- **深度バッファの1ビットやステンシルバッファで「点かどうか」を区別する**:
  実装できるが、深度/ステンシルの1ビットに意味を持たせる分、後から読む人が
  「このビットは何のためにあるか」を深度バッファの外から探す必要が生まれる。
  別テクスチャに分けたほうが「オフスクリーンに何が入っているか」がテクスチャの
  宣言そのものから読み取れる。
- **1本のレンダーパスの中で空・グリッドのシェーダ自体にEDL用の深度参照を混ぜる**:
  `sky.ts`/`ground-grid.ts`の見通しが悪くなり、両ファイルへの変更が必要になる。
  今回採用した方式では**`sky.ts`/`ground-grid.ts`は1行も変更していない**。

いずれも「所有者が実装を追えること」を優先し、既存コードへの侵襲が小さい方を選んだ。

### なぜ既定値は未検証か

### 実機不具合: 画面が真っ黒になる（パイプライン/レンダーパスの互換性を誤解していた）

最初の実装をリリースした後、所有者の実機で次が報告された。

> 「画面が真っ黒になり、何も描画されなくなった」

**原因はEDL合成パス(`EdlPass`)のパイプラインが`depthStencil`を宣言していな
かったこと。** 当初のコメントにはこう書いていた。

> depthStencilを指定しない = このパイプラインは深度の読み書きを一切しない。
> 呼び出し元のレンダーパスがdepthStencilAttachmentを持っていても
> (空・グリッドのパイプラインが使うため)、このパイプラインには影響しない
> （WebGPUの仕様上、depthStencilを宣言しないパイプラインはパスの深度
> アタッチメントを無視できる）。

**この理解が誤りだった。** WebGPUでは、レンダーパスが`depthStencilAttachment`を
持つ場合、そのパス内で`draw`するすべてのパイプラインは**同じdepth-stencil
フォーマットの`depthStencil`を宣言していなければパスと互換にならない**
（「深度を読み書きしないから宣言不要」ではなく、「パスとパイプラインの
フォーマットの組み合わせが一致するか」という別の要件だった）。EDLの合成パスは
空・グリッドと同じレンダーパス（`point-cloud-renderer.ts`の`drawFrame()`パス2、
`depthStencilAttachment`を持つ）の中で呼ばれるため、`depthStencil`を宣言
していないこのパイプラインはそのパスと非互換になる。**非互換なパイプラインで
`draw`するとバリデーションエラーになり、そのコマンドエンコーダ全体が無効になる**
（`encoder.finish()`が無効なコマンドバッファを返し、`submit()`でそのフレームが
まるごと捨てられる）。空・グリッド・点群のすべてが同じ`encoder`・同じ`pass`に
乗っていたため、EDL合成の呼び出し1つが失敗しただけで**フレーム全体**が
描画されなくなっていた。これが「画面が真っ黒」の直接の原因。

**直し方:** `sky.ts`/`ground-grid.ts`が最初から正しくやっていた通り
（`depthStencil: { format: depthFormat, depthWriteEnabled: false, depthCompare:
"always" }`）、深度に触れないパイプラインでも、パスの深度アタッチメントと
同じフォーマットの`depthStencil`を明示的に宣言する必要がある。`EdlPass.init()`
のシグネチャに`depthFormat`引数を追加し（`sky.ts`/`ground-grid.ts`と同じ形）、
呼び出し側`point-cloud-renderer.ts`の`this.edl.init(device, this.format)`を
`this.edl.init(device, this.format, DEPTH_FORMAT)`に直した。誤っていた
コメントも、上記の正しい理解に書き直した（`src/renderer/edl.ts`の`init()`の
コメント参照）。

**教訓（次に踏みやすい罠）:** 「このパイプラインは深度を読み書きしないから、
`depthStencil`の宣言は不要」という直感は誤り。`depthStencil`の宣言は
「このパイプラインが深度に触れるかどうか」ではなく、「このパイプラインを
使うレンダーパスがどんな深度アタッチメントの構成か」で決まる、パイプラインと
パスの**互換性の要件**である。深度に触れないパイプラインでも、深度
アタッチメントを持つパスで使うなら、`depthWriteEnabled: false, depthCompare:
"always"`という「触れない」ことを明示する`depthStencil`を宣言しなければ
ならない。`ground-grid.ts`も同じ全画面パスの構成だが、こちらは最初から
正しく宣言されていたため、同じ誤りは無かった（確認済み）。

**この修正が実際に効いたかどうかはGUIを持たないため確認できていない。
所有者の実機確認待ち。**

## M2-2: カラーマップ切替

### やること

点の色をどの属性から決めるかを切り替えられるようにする。

| ソース | 対象 | 備考 |
|---|---|---|
| RGB | format 2/3/5/7/8/10 | 持たないファイルでは選べないようにする |
| 強度（intensity） | ほぼ全て | 最頻の代替。レンジの自動調整が要る |
| 標高（elevation） | 全て | 地形の判読に有効 |
| 分類（classification） | 分類済みデータ | 離散値。地面/植生/建物などに色を割り当てる |

ノードのバイナリ形式は既に intensity（u16）と classification（u8）を運んでいる。
**形式は変えずに実装できる。**

- 強度と標高は連続値なので、レンジの決め方（実データの分布に合わせる）が要点になる
- 分類は離散値なので、カラーマップは配色表になる
- **配色は明度が単調に変化するものを選ぶこと。** 虹色（jet）は明度が非単調で、
  実際には無い構造が見えてしまう

### 実装の進め方（2段階に分けた理由）

このタスクに着手した時点で、**別のエージェントが`src/renderer/point-cloud-renderer.ts`を
複数ファイルに分割する作業を並行して進めていた。** 点群のシェーダ・パイプラインへの
結線はこのファイルを直接書き換える必要があり、分割の途中で触ると確実に衝突する。
そこで次の2段階に分けた。

1. **分割と無関係な部分を先に作る**（このコミット）: 色を決める純粋な計算を
   `src/renderer/colormap.ts`に切り出し、`colormap.test.ts`で検証する。
   UI（`LayerPanel`の着色モード選択）と`useCopcViewer.ts`のstateもここで作る。
   **この時点では、着色モードを切り替えても実際の点の色はまだ変わらない**
   （後述「未実装（次段階）」参照）。
2. **レンダラへの結線**（分割が`origin/main`に入ってから、別コミットで実施・記録する）。

#### 段階1: 色計算・state・UI（このコミット）

**`src/renderer/colormap.ts`（新規）:** GPUに依存しない純粋関数だけを置いた
（`edl.ts`と同じ方針。EDLは深度だけを見て色を作らず、こちらは色だけを決めて
深度を見ない。両者は独立で、合成は「着色→EDLの陰影を掛ける」の順になる想定）。

- `ColorMode`: `"rgb" | "elevation" | "intensity" | "classification"`の4種類
  （受け入れ条件の「4つのソース」に対応）
- `resolveColorMode(mode, hasColor)`: RGBを持たないファイルで`"rgb"`が要求された
  ときだけ`FALLBACK_COLOR_MODE_WITHOUT_RGB`（`"elevation"`）に落とす
- `normalizeValue` / `extendRange`: 連続値(標高・強度)をレンジに対して0..1へ
  正規化する。`extendRange`は強度のように**開いた時点ではレンジが分からない**
  値のためのヘルパーで、ノードを読み込むたびに観測値を渡してレンジを広げていく
  想定（標高は`CloudInfo`のバウンディングボックスから即座に分かるため使わない）
- `sampleRamp` / `ELEVATION_RAMP` / `INTENSITY_RAMP`: 値→色のランプと、その線形補間
- `classificationToColor`: ASPRS LAS標準分類コード(0〜18)への配色表。表に無い
  コードは`UNKNOWN_CLASSIFICATION_COLOR`（シアン、表中のどの色とも被らない）に
  フォールバックする

**既定の着色モードと、RGB無しファイルでのフォールバック先の理由**
（所有者の体験に直結するため、判断の根拠をここに残す）:

- 既定(`DEFAULT_COLOR_MODE`)は`"rgb"`。ファイルが実際にRGBを持つなら、それが
  最も素直な見た目になる
- RGBを持たないファイル（`sofi.copc.laz`）を開いたとき、あるいは`"rgb"`を
  手動で選んだときのフォールバック先は**標高**にした。理由:
  1. 標高はCOPCの全点が必ず持ち、`CloudInfo`のバウンディングボックス(z成分)から
     開いた瞬間にレンジが決まる。強度のように「実データに意味のある値が
     入っているか」をファイルごとに気にしなくてよい
  2. 分類は「分類済みデータでのみ意味を持つ」（このタスクシート冒頭の表）。
     未分類の点群では全点が同じ色になり、構造が全く見えない
  3. EDL（既定オン、M2-1）は深度差から陰影を作るが色そのものは作らない。
     標高を重ねることで「陰影(構造)」+「高さ(標高)」という、RGB無し点群を
     開いた直後として最も情報量の多い組み合わせになる
  4. 強度をフォールバック先にしなかったのは、センサー・取得条件によって
     実際の値域が大きく異なり（0-255しか使っていない等）、標高ほど
     「開いた瞬間に必ず意味のある絵になる」保証が無いため

**配色（明度単調の要件への対応）:**

- 標高: **viridis風**（暗い紫→青→緑→黄、明度単調増加）。科学可視化で標準的に
  使われる配色で、虹色(jet)のような「実際には無い構造が見える」問題が無い
- 強度: グレースケール（暗い灰色→白）。標高と見た目をはっきり区別できるよう
  あえて無彩色にした。下端を純黒ではなく暗い灰色(0.08)にしたのは、既定の
  単色(暗)背景(およそ(0.05,0.05,0.08))に対して強度最小の点が背景と
  見分けられなくなるのを避けるため
- どちらも`colormap.test.ts`で、制御点を順に見て相対輝度が単調非減少であることを
  機械的に確認している（虹色のような後戻りが将来紛れ込んでもテストで検出できる）
- 分類: ASPRS LAS標準の分類コード(地表=2など)に沿って配色した。似た意味の
  コードは近い色相にまとめ(低/中/高植生はすべて緑系)、ノイズ系(7・18)は
  彩度の高い赤系にして異常値として目立つようにした

**`src/state/useCopcViewer.ts`:** `colorMode: ColorMode`と`setColorMode`を
`CopcViewerState`に追加した。`openFile`が成功した後、開いたファイルの
`hasColor`で`resolveColorMode`を通し、RGB無しファイルなら自動的に標高へ
落とす（`useState`の関数形更新を使い、`openFile`が`[]`依存の`useCallback`でも
最新の`colorMode`を正しく参照できるようにした）。`setColorMode`自体も
念のため同じ解決を通す(二重の安全策)。

**`src/ui/shell/LayerPanel.tsx`:** 「着色」の`<select>`を追加した(RGB/標高/強度/分類)。
`cloudInfo.hasColor`が`false`のときは`<option value="rgb">`を`disabled`にし、
ラベルにも「（RGB無し）」を付けて選べないことを見た目でも示す(受け入れ条件
「RGBを持たないファイルではRGBが選べない」)。フォールバックが起きている間は
補足テキストを出す。

**触ったファイル（段階1）:** 追加: `src/renderer/colormap.ts`,
`src/renderer/colormap.test.ts`。変更: `src/state/useCopcViewer.ts`,
`src/ui/shell/LayerPanel.tsx`。`src/renderer/point-cloud-renderer.ts`は
触っていない(分割中のため)。

#### 段階2: レンダラへの結線

`point-cloud-renderer.ts`の分割コミット（`refactor(renderer): split
point-cloud-renderer into node-selection / gpu-resources / orchestrator`）が
`origin/main`に入ったのを確認してから着手した。分割後の構成
（`node-selection.ts`＝どのノードを描くかの純粋関数、`gpu-resources.ts`＝
WebGPUを直接叩く実体、`point-cloud-renderer.ts`＝rAF・カメラ・統計の
オーケストレーション）に沿って、WebGPUを直接触る部分はすべて
`gpu-resources.ts`に置いた。

**頂点属性: intensity/classificationを1つの`uint32`として読む**

ノードのバイナリ形式（`node_format.rs`）はオフセット16から
`u16 intensity, u8 classification, u8 padding`の4バイト連続レイアウトを
持つ。この4バイトをそのまま`format: "uint32"`の頂点属性として読み、
シェーダ側でビット演算により`intensity = packed & 0xffffu`、
`classification = (packed >> 16u) & 0xffu`に分解した。

- 採用した理由: 属性を1つ追加するだけで済み、`arrayStride`（頂点バッファの
  レイアウト）を変更する必要が無い。属性を2つ（`uint16`のintensityと
  `uint8`のclassification）に分けることも検討したが、WebGPUの頂点フォーマットに
  単独の`uint8`スカラー形式が無く(`uint8x2`/`uint8x4`のようにまとめて読む形式
  しか無い)、結局複数バイトをまとめて読んでからビット演算で分解する必要が
  あるのは同じだったため、属性1個で済むこちらを選んだ
- ノードのバイナリ形式（`node_format.rs`のレイアウト）は変更していない
  （タスクシート冒頭の「形式は変えずに実装できる」の通り）

**標高: ノード原点のワールドZ + 頂点のノードローカル相対Z**

点の座標はノード原点からの相対座標(f32)で運ばれる（`node_format.rs`の
「なぜノードローカル相対座標にするのか」参照）。標高の計算にはワールド座標の
Zが要るため、ノード原点のワールドZ（`CachedNode.origin[2]`）を
`Uniforms.originZ`として頂点シェーダへ渡し、`worldZ = originZ +
position.z`で復元する。この`originZ`は、既存の`Uniforms`構造体の
未使用パディング(`_pad`)をそのまま使う形にし、**uniformバッファのサイズは
変えていない**(80バイトのまま)。

標高の軸は**upAxis（カメラの表示上の上方向）ではなく、常にLAS座標系のZ
(3成分目)を使う**ことにした。upAxisはM2-0bで導入した「カメラがどちらを
上として振る舞うか」という表示上の概念で、LASファイルのZ座標（実世界の
高さ、標高）とは別の概念だからである。同じ点群を将来Y-upで表示するように
変えても、標高の色は変わらないほうが自然だと判断した。

**強度・標高のレンジをどう決めたか**

- 標高: `setHierarchy()`が既に計算しているシーンのバウンディングボックス
  （カメラのtarget/distanceを決めるのに使っているのと同じmin/max）の
  Z成分をそのまま使う。ファイルを開いた瞬間に確定するため、動的な追跡は
  不要（`colormap.ts`の`FALLBACK_COLOR_MODE_WITHOUT_RGB`のコメント参照）
- 強度: `CloudInfo`は強度のレンジを持たない（センサー依存で値域が大きく
  異なるため、タスクシートが「レンジの決め方が要点になる」とした通り）。
  そこで`src/datasource/node-format.ts`に`computeIntensityRange(node)`を
  新設し、ノードが1つ届くたびにそのノード内のintensityの最小/最大を求め、
  `colormap.ts`の`extendRange`で全体のレンジを広げていく。ファイルを
  開き直したとき（`setHierarchy()`）は前のファイルの観測値を引きずらないよう
  `null`にリセットする。まだ1件もノードが届いていない間は`{min:0,max:0}`
  にフォールバックし、`normalizeValue`の「縮退レンジは0を返す」契約により
  安全に暗い色になる（`colormap.ts`参照）

**着色設定のuniformバッファをノードごとのuniformとは別に分けた**

着色モード・標高/強度のレンジは1フレームに1つ、全ノード共通の値である
（ノードごとに変わるのはmvp行列とノード原点だけ）。これを毎ノードの
uniformバッファに含めて重複させるのではなく、`binding(1)`として
専用の共有uniformバッファ（`ColorSettings`、EDLの合成パスと同じ8×f32の
サイズに揃えた）を新設した。各ノードの`bindGroup`（ノード読み込み時に
一度だけ作る）は両方のbindingを参照するが、内容の書き込みは
`drawFrame()`が毎フレーム`writeBuffer`で行う（**バッファそのものは
作り直さない**。作り直すと、既に作成済みの各ノードの`bindGroup`が
古いバッファを参照したままになり壊れるため）。

**EDLとの合成順序**

着色（`colorForVertex()`、パス1の頂点シェーダ）は「陰影を一切考えない
素の色」を決めるだけで、EDL（`edl.ts`、パス2の合成シェーダ）はパス1の
オフスクリーン出力を読んで深度差から求めた陰影係数をその色に掛けるだけ、
という既存の2パス構成（M2-1）をそのまま利用した。**着色→EDLで陰影、の順序は
既存のパイプライン構造から自動的に決まっており、この段階で新たに何かを
考える必要は無かった。** EDLは色を一切見ずに深度だけを見るため
（`edl.ts`冒頭のコメント）、どの着色モードでも同じように陰影が掛かる。

#### 不具合: 標高が全部紫になる

**症状:** `sofi.copc.laz`を開いて着色を「標高」にすると、地形の起伏に関わらず
ほぼ全ての点が同じ色（当時のランプの最初の色＝紫）になった。

**原因:** `point-cloud-renderer.ts`の`setHierarchy()`は、カメラの初期位置
決め用に「ノードのbounds(`HierarchyNodeInfo.boundsMin`/`boundsMax`)の
和集合」を計算していたが、この同じ`min`/`max`を標高の正規化レンジにも
そのまま使い回していた。COPCのoctreeは**ルートが立方体**（`crates/pcv-core/
src/copc.rs`の`voxel_bounds`が返すノードのboundsは、その立方体を素直に
分割したセル）なので、Z方向の範囲は水平方向の広さに合わせて大きく
引き伸ばされる。航空測量データ（`sofi.copc.laz`）は水平方向が数km、
実際の標高差は数十mしかないため、標高の正規化レンジが実際の何十倍にも
広がってしまい、全点の正規化値`t`がほぼ0（レンジの下端）に張り付いていた。

**直し方:** カメラ位置決め用の「シーンのバウンディングボックス」（ノードの
bounds由来。**この用途では立方体のままで問題無いため変更していない**）と、
標高カラーマップ用の「標高の正規化レンジ」（LASヘッダーの実データ範囲、
`CloudInfo.min`/`max`のZ成分。`crates/pcv-core/src/copc.rs`の
`build_cloud_info`がLASヘッダーの`min_z`/`max_z`をそのまま入れている）を、
新設した`src/renderer/scene-bounds.ts`の別々の純粋関数（`computeSceneBounds`/
`elevationRangeFromCloudBounds`）にはっきり分離した。同じ`min`/`max`変数を
2つの用途に使い回していたことが混同の原因だったため、`elevationRangeFromCloudBounds`
のシグネチャ自体が「ノードのboundsを一切受け取らない」ことを示す形にした。
`PointCloudRenderer`に`setElevationRange(cloudMin, cloudMax)`を新設し、
`useCopcViewer.ts`の`openFile()`が`renderer.setHierarchy(opened.nodes)`とは
別に、`renderer.setElevationRange(opened.info.min, opened.info.max)`を呼ぶ
よう結線した。

**テスト:** `scene-bounds.test.ts`に、ノードのセル範囲（水平±1000mに合わせて
Z方向も-900〜1100まで引き伸ばされた想定）とヘッダーの実データ範囲（Z=100〜150）
を両方与え、`elevationRangeFromCloudBounds`の結果がヘッダー側（100〜150）に
なり、ノードのセル範囲とは一致しないことを確認する回帰テストを追加した。

#### 配色をCloudCompare風（青→緑→黄→赤）に変更

所有者の要望:「CloudCompareのように、青→緑→赤で標高とIntensityは表示しよう」。

**変更内容:**

- 標高・強度で**別々だったランプ（標高=viridis風、強度=グレースケール）を
  1つに統合**し、`src/renderer/colormap.ts`の`ELEVATION_INTENSITY_RAMP`
  （青→緑→黄→赤の4点）にした。`elevationToColor`/`intensityToColor`は
  どちらもこの1つのランプを参照する
- 分類の配色（ASPRS標準）は変更していない（所有者の要望も「分類の色は
  今のまま」）

**なぜ緑→赤の間に黄色を挟むか（所有者の「青→緑→赤」をそのまま3点の
ランプにしなかった理由）:** 緑(0,1,0)と赤(1,0,0)をRGB空間でそのまま線形
補間すると、中間点は(0.5, 0.5, 0)になる。これは彩度の高い黄色ではなく、
**暗く濁ったオリーブ色（茶色がかった黄緑）**に見える。正反対の原色
（緑=G成分のみ、赤=R成分のみ）を直線でつなぐと、通過点はどちらの性質も
弱め合った暗い色になるためである。CloudCompareの実際の既定配色も、
公式には「Blue > Green > Yellow > Red」と黄色を挟んだ4点であり、同じ
理由（濁りを避けるため）と考えられる。所有者の要望（CloudCompareのように、
かつ青→緑→赤で）を両立させるため、CloudCompareの実際の配色（黄色を挟んだ
4点）をそのまま採用した。

**明度は単調ではないことの記録:** M2-2着手当初に立てていた「配色は明度が
単調に変化するものを選ぶこと（虹色/jetは明度が非単調で、実際には無い
構造が見えてしまうため避ける）」という指針からすると、この配色は
黄(1,1,0)の相対輝度≈0.93に対し赤(1,0,0)は≈0.21で、黄→赤の間で明度が
大きく下がる非単調な配色である。これは当初の指針とは厳密には矛盾するが、
今回は**所有者が実機の使用経験（CloudCompareを日常的に使っている）から
名指しで要望した配色であり、所有者自身の判断を当初の一般的な指針より
優先した。** CloudCompare自体がこの配色を既定にしており、点群業界で
広く使われている実績のある配色でもある。

**TS/WGSLの制御点を一致させる仕組み:** これまでEDL(`edl.ts`)などでは、
WGSL側のロジックをTypeScript側の対応する純粋関数と手で一致させ、コメントで
対応を明記する、という方針を採ってきた。しかし色のランプでは「片方だけ
値を変えてもう片方を直し忘れる」事故が起きやすい（実際、変更前の
`gpu-resources.ts`は標高・強度それぞれのランプの数値をWGSLの文字列に
手で書き写しており、値の食い違いを検出する手段が無かった）。そこで
`src/renderer/colormap.ts`に`rampToWgslFunction(fnName, stops)`を新設し、
**制御点の定義を`ELEVATION_INTENSITY_RAMP`の1箇所だけに持ち、WGSLのコードは
そこから生成する**ようにした。`gpu-resources.ts`はこの関数の戻り値を
`SHADER_SRC`のテンプレートリテラル内へ直接埋め込んでいる（文字列としては
2箇所に同じランプのコードがあるが、生成元は1つ、という構造）。生成される
WGSL関数のロジックは`sampleRamp`と等価（両端はクランプ、区間ごとに`mix`で
線形補間）。

**テスト:** `colormap.test.ts`に次を追加した。
- `ELEVATION_INTENSITY_RAMP`の両端が青(0,0,1)・赤(1,0,0)で、途中に
  緑(0,1,0)・黄(1,1,0)が来ることの確認
- `intensityToColor`が`elevationToColor`と全く同じ色を返すこと（標高と
  強度が同じランプを使うことの確認）
- `rampToWgslFunction`が生成したWGSLの文字列に、制御点として渡した色が

## M2-3: UI シェル

### やること

[ADR-0005](./ADR-0005-ui-shell.md) の決定を実装する。**決定済みなので設計は蒸し返さない。**

- 3Dビューをウィンドウ全面に敷く
- 画面下部中央にフローティングのツールドック
- 画面左にレイヤーパネル、画面右に情報パネル（どちらも折りたたみ可能）
- 設定画面は**不透明**なモーダル
- ダーク / ライト両対応（OS 設定に追従）

### 守ること（ADR-0005 の帰結）

- **ぼかしの下に必ず tint（単色の薄い層）を敷く。** 純粋な透明ガラスにしない。
  点群は色が任意で高周波ノイズがあるため、tint 無しでは文字が背景依存で読めなくなる
- **tint はテーマごとに別の値を持つ。** ライトテーマ × 暗い点群 × 白いガラスが最も破綻しやすい
- ドックのアクティブなツールは明確なハイライトで示す（モード状態の表現が弱いため）

### 実装

`src/ui/shell/` にADR-0005の5面をそれぞれ独立したコンポーネントとして実装した。

- **`AppShell.tsx`**: 組み立て役。`useCopcViewer()`と`useTheme()`をここで一度だけ呼び、
  `canvasRef`とviewer状態を各パネルへpropsで配る。以前は`ViewerPanel`が
  `useCopcViewer()`を自分で呼び、HUDのテキストも自分で描いていたが、パネルを
  複数に分けるにはどこか1箇所で状態を持って配る必要があるため、ここへ引き上げた。
  全パネルは`ViewerPanel`(canvas, `absolute inset-0`)の上に重ねた絶対配置の層。
- **`ViewerPanel.tsx`**: `canvasRef`を受け取って`<canvas>`を`absolute inset-0`で
  敷くだけのdumbな部品にした（ADR-0005の「全面ビューア」）。HUDは全部後述のパネルへ移した。
- **`Dock.tsx`**: 下部中央のフローティングドック。中身はレイヤー/情報パネルの
  開閉ボタンと設定ボタンの3つだけ。選択・計測・断面のようなモード切替ツールは
  まだ無い(M3以降)ため、今それらの分の場所を先取りして確保することはしなかった
  （ADRの「やりすぎないこと」の精神と、所有者の「実装を追えること」を優先）。
  開いている側のボタンは背景色反転でハイライトする(ADR-0005が指摘した「ドックは
  モード状態が見えにくい」への対処)。
- **`LayerPanel.tsx`**（左）/ **`InfoPanel.tsx`**（右）: 折りたたみ可能な2枚。
  開閉ボタンは畳んだ状態でも常に画面内に残る(パネル本体とは別要素にした)ので、
  畳んだ後に開き直す手段が必ずある。
- **`SettingsModal.tsx`**: 唯一の不透明な面。`backdrop-blur`もtintも使わず、
  単色の背景(`bg-white` / `dark:bg-slate-900`)にした。

### ガラスの質感（tint）

`src/ui/shell/glass.ts`に`GLASS_SURFACE`として1箇所に集約した。
`backdrop-blur-md`の上に`bg-white/65`(ライト)・`dark:bg-slate-950/70`(ダーク)の
tintを重ねる。値をやや高め(65〜70%)にしたのは、ADR-0005が挙げたリスク
「点群は色が任意・高周波ノイズがあり、tintが薄いと文字が背景依存で読めなくなる」
への対処で、特にライト×暗い点群×白いガラスが最も破綻しやすいとADRに明記されて
いたため、ライト側のtintも薄くしなかった。**この不透明度は設計時の判断であり、
fpsは測っていない。**`backdrop-filter`の描画コスト実測はM2-4の担当。

ダーク/ライトの切り替えは`src/state/useTheme.ts`が担う。ADR-0005の決定である
「OS設定に追従」を既定(`preference="system"`)として維持しつつ、所有者が実機で
OSの設定を変えずに両テーマを見比べられるよう、設定モーダルから手動固定
(`system`/`dark`/`light`)も選べるようにした。これはADRの決定を覆すものではなく、
既定値は変えていない。判定ロジック(`resolveTheme()`)はDOM/localStorageに触れない
純関数として切り出し、`useTheme.test.ts`でvitestから直接検証している
（OSの`prefers-color-scheme`メディアクエリの発火自体はGUI側の確認が要るため、
そこは目視待ち。下記「自分で確認する手順」参照）。

### 他の選択肢を採らなかった理由

- **状態を各パネルの中で個別に`useCopcViewer()`するのではなく、`AppShell`で
  一度だけ呼んでpropsで配る構成にした。** `useCopcViewer()`の`useEffect`は
  `canvasRef.current`に対して`PointCloudRenderer`を1つだけ生成する前提で
  書かれており、複数箇所で呼ぶとレンダラが複数生成されてしまう。所有者が
  「実装を追えること」を優先する方針とも合う(状態の出どころが1箇所で分かる)。
- **UIライブラリは追加していない。** 既存のTailwindだけで済んだ(ADR-0005が
  求める見た目は角丸・半透明・ぼかしのような基本的なユーティリティの組み合わせで
  表現できるため、コンポーネントライブラリを足す理由が無い)。
- **テーマの適用は`prefers-color-scheme`のメディアクエリ直接ではなく、
  `<html data-theme>`属性 + Tailwindのカスタムvariantにした。** 設定画面からの
  手動固定(OSの設定を変えずに両テーマを確認したいという、GUIを目視できない
  制作環境ならではの要求)を素直に実装するには、CSS側の分岐を「OSの状態」ではなく
  「アプリが決めた1つの値」に一本化する必要があったため。

### 追記: 自動点予算調整(ADR-0009)との隙間を埋めた

UIシェルの実装と並行して、別エージェントが`src/renderer/point-budget.ts`と
`point-cloud-renderer.ts`に「点予算をフレーム時間の閉ループで自動調整する」機能
(タスクB、ADR-0009)を入れた。仕様は次の3点。

- 既定で自動調整がオン(`PointCloudRenderer`の`autoPointBudgetEnabled = true`)
- `setPointBudget()`を呼ぶと自動調整が**黙って**オフになる(手動設定を優先するため)
- `setAutoPointBudgetEnabled(enabled)` / `getAutoPointBudgetEnabled()`で戻せる。
  `RenderStats`に`autoPointBudgetEnabled: boolean`が追加されている

このAPIが入った時点で`LayerPanel`の点予算欄は先に実装済みだったため、次の隙間が
生まれていた。スライダーを動かすと自動調整が黙って止まるが、UI上にそれを示す
表示も、戻す手段も無かった。さらに、自動調整が`pointBudget`を直接書き換える
(`setPointBudget()`を経由しない)ため、`useCopcViewer.ts`の`pointBudget`state
(手動設定時にしか更新していなかった)は自動調整が動くと古い値のまま固まっていた。

**直した内容:**

- `src/state/useCopcViewer.ts`
  - `CopcViewerState`に`autoPointBudgetEnabled: boolean`と
    `setAutoPointBudgetEnabled(enabled: boolean): void`を追加
  - `onStatsUpdate`のコールバックで、`stats`だけでなく`pointBudget`と
    `autoPointBudgetEnabled`もstatsから同期するようにした(自動調整は
    `setPointBudget()`を経由せず値を書き換えるため、statsが唯一の
    正しい値の出どころになる)
  - `setPointBudget()`のラッパー内で`autoPointBudgetEnabled`をその場でfalseに
    倒すようにした。renderer側の`setPointBudget()`も内部でfalseにするが、
    その反映がUIに届くのは次のstats更新(最大`STATS_INTERVAL_MS`=500ms後)であり、
    それを待つと一瞬黙って切り替わったように見えるため、即時反映を別に足した
- `src/ui/shell/LayerPanel.tsx`
  - 「点予算を自動調整する」チェックボックスを追加(`viewer.autoPointBudgetEnabled`
    ⇄ `viewer.setAutoPointBudgetEnabled()`)
  - 自動調整中は点予算の数値入力を`disabled`にし、ラベルに
    「(自動調整中)」と表示。値自体は`viewer.pointBudget`(statsに追従)なので、
    自動調整が動いている間は数値が自分で変わっていくのがそのまま見える
  - チェックを外すと入力が編集可能に戻り、手動で変更すると
    `setPointBudget()`が呼ばれる(実際のrenderer側の停止条件と一致)。
    このときチェックボックス自体が即座に外れる(上記の即時反映のおかげ)ので、
    自動調整が止まったことが画面から分かる

**採用しなかった案:** 数値入力を常に編集可能にして、自動調整中にユーザーが
値を変えた瞬間に自動的にオフへ切り替わる方式も検討した。実装は可能だが、
自動調整中に0.5秒ごとに値が動く数値入力へ同時にユーザーが入力するという
状態遷移が生まれ、挙動の説明が複雑になる。所有者が「実装を追えること」を
優先しているため、自動調整中は読み取り専用・チェックを外すと編集可能という
単純な2状態を選んだ。チェックを外す動作自体が「自動をやめる」という明確な
意思表示になる点も理由。

**触ったファイル:** `src/state/useCopcViewer.ts`、`src/ui/shell/LayerPanel.tsx`
(`src/renderer/`配下は今回も触っていない)

- 「点予算を自動調整する」のチェックを外すと、入力が編集可能になるか

## M2-4: ガラスの性能を実測する

### なぜ独立した項目にするのか

ADR-0005 で「`backdrop-filter` は背景が毎フレーム変わると毎フレーム再計算され、
**カメラ操作中という点群描画が最も苦しい瞬間**と競合する」というリスクを引き受けた。
そのとき「推測で大丈夫としない。必ず実測する」と定めた。

### やること

ガラスあり / なしで fps を比較する。M0・M2-1 と同じく**数値を残す**。

- ガラスパネルを表示した状態と、非表示にした状態での fps
- カメラを動かしている最中の fps（静止時ではない。ここが競合する瞬間）
- ぼかし半径を変えたときの影響

### 実測の結果に応じた対処（先に決めておく）

| 結果 | 対処 |
|---|---|
| 影響が小さい（数 fps） | そのまま |
| 無視できない | ぼかし半径を下げる、ガラス面積を絞る |
| 大きい | **カメラ操作中だけぼかしを落として不透明寄りにする。** 操作中は背景が流れるので失うものが少ない |

### 受け入れ条件

- [ ] ガラスあり / なしの fps が数値で並んでいる（カメラ操作中を含む）
- [ ] 上の表のどれに該当するかが確定し、対処が実装されている

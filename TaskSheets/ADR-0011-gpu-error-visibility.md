# ADR-0011: WebGPUのエラーを握りつぶさず画面に出す

- 状態: 採択
- 日付: 2026-09-23
- 前提: [ADR-0002](./ADR-0002-rendering-api.md)（WebGPU採用）、
  [M2-shading-and-ui.md](./M2-shading-and-ui.md) M2-1（この作業のきっかけになった事故）

## 決定

1. `device.onuncapturederror` と `device.lost` を監視し、WebGPUのエラーを
   捕捉する。捕捉した文字列の蓄積・重複抑制は、WebGPUに依存しない純粋な
   クラス `src/renderer/gpu-error-log.ts` の `GpuErrorLog` に任せる。
2. `point-cloud-renderer.ts` の `init()`（点群パイプライン本体、および
   `sky.ts`/`ground-grid.ts`/`edl.ts` の `init()` の呼び出し）を
   `pushErrorScope("validation")`/`popErrorScope()` で1ステップずつ囲み、
   失敗した場合に「どの生成が失敗したか」を先頭に含むメッセージで報告する。
3. 画面の最前面（`z-50`）に不透明なエラーバナー（`src/ui/shell/GpuErrorBanner.tsx`）
   を出す。エラー本文をそのまま表示し、複数出ても最初のエラーを隠さず、
   個別に閉じられるようにする。

規約3（ARCHITECTURE.md）に従い、`src/renderer/`はコールバック
（`onGpuErrorReported`）でエラーを外へ渡すだけにし、蓄積ロジック
（`gpu-error-log.ts`、GPUに依存しない）と表示（`src/state/`・`src/ui/`）は
Reactの側に置く。既存の`onStatsUpdate`と同じ形。

## 背景: この仕組みを入れるきっかけになった事故

直前のEDL（M2-1）の実装で、レンダーパイプラインに`depthStencil`を宣言し
忘れる不具合があった。WebGPUでは、`depthStencilAttachment`を持つレンダー
パスの中で`draw`するパイプラインは、同じフォーマットの`depthStencil`を
宣言していないとパスと互換にならない。互換でないパイプラインで`draw`すると
バリデーションエラーになり、**コマンドエンコーダ全体が無効化されて、その
フレームが丸ごと捨てられる**（詳しい技術的な経緯は
[M2-shading-and-ui.md](./M2-shading-and-ui.md) M2-1「実機不具合: 画面が
真っ黒になる」を参照。ここでは繰り返さない）。

結果、所有者の画面は**完全に真っ黒**になった。点群も空もグリッドも出ない。
そして次のすべてが成功していた。

- `npm run typecheck`
- `npm run lint`
- `npm test`
- `npm run build`
- CI 全ジョブ

**どれ一つ異常を示さなかった。** バリデーションエラーはブラウザのWebGPU
実装が実行時に出すものであり、静的解析・単体テスト・ビルドのいずれの
経路にも現れない。所有者は「真っ黒」という情報しか得られず、原因の特定に
時間がかかった。

`grep -rn "onuncapturederror|pushErrorScope|popErrorScope" src/renderer/`
の結果が空だったことが、この作業が着手される直接のきっかけになった。
**このコードベースはそれまでWebGPUのエラーを一切拾っていなかった。**

## なぜ4層すべてが必要か

事故の教訓は「1つの仕組みでは足りない」ということだった。想定される
WebGPUの異常には性質の異なる3種類があり、それぞれ拾う手段が違う。

| 異常の種類 | 例 | 拾う手段 |
|---|---|---|
| 初期化時のバリデーションエラー | パイプラインの`depthStencil`宣言漏れ（今回の事故そのもの） | `pushErrorScope`/`popErrorScope`（どの生成か特定できる） |
| 実行時の（毎フレーム起きうる）バリデーションエラー | 上記のエラーがスコープで捕まらず素通りした場合、または毎フレームの`draw`で新たに起きるエラー | `device.onuncapturederror` |
| デバイスそのものの消失 | GPUのリセット、ドライバのクラッシュ、OSのスリープ復帰 | `device.lost`（Promise） |

`onuncapturederror`だけで済ませなかった理由: これはデバイス全体に1つしか
設定できないハンドラで、メッセージを見ても「点群パイプラインなのかEDL
合成パイプラインなのか」が分からない。今回の事故はまさにこの曖昧さが
無関係だったが（画面が真っ黒になるという症状で気づけたため）、次に
似た不具合が起きたときに原因箇所を即座に特定できるよう、初期化の
ステップごとにエラースコープで区切ることにした。

`pushErrorScope`/`popErrorScope`だけで済ませなかった理由: エラースコープは
初期化のように「ここで何かが起きたら知りたい」と決め打てる場所にしか
仕込めない。毎フレームの`draw`呼び出しをスコープで囲むのは非現実的（性能上
も、コードの見通しの上でも）なので、実行時の異常は`onuncapturederror`に
任せる。

`device.lost`だけで済ませなかった理由: バリデーションエラーは
`device.lost`を発生させない（デバイスは生きたまま、そのフレームだけが
捨てられる）。今回の事故がまさにそれで、`device.lost`だけを見ていたら
何も検知できなかった。

## 連投の抑制（GpuErrorLog）

`onuncapturederror`は、同じ原因のエラーが直っていない限り**毎フレーム**
発火し続ける（今回の事故はまさにこの状態だった）。素通しするとコンソールも
バナーも同じメッセージで埋まる。

`src/renderer/gpu-error-log.ts`の`GpuErrorLog`は、「直前に報告された
エントリと同じメッセージなら、新しいエントリを作らずcountを増やすだけに
する」という一番単純な抑制をする。異なるメッセージは別エントリとして
両方保持する（「複数のエラーが出たときに最初のエラーが見えなくならない」
という要件のため）。

**WebGPUに一切依存しない純粋なクラスとして切り出した。** GPUDeviceの
モックを用意しなくても、蓄積・重複抑制のロジック単体を`vitest`で検証
できるようにするため（`gpu-error-log.test.ts`）。「同じメッセージが
連続したら1件にまとめる」「異なるメッセージは両方保持される」
「間に別のメッセージを挟むと別エントリになる（直前との一致だけを見る、
という設計の境界をそのままテストにした）」「`dismiss()`で指定したidだけ
消える」を確認済み。

## 画面への出し方（GpuErrorBanner）

コンソールだけでは不十分と判断した。所有者は真っ黒な画面を見ている状態
から、devtoolsを開かなくても原因が分かる必要がある。

- **本文をそのまま表示する。要約しない。** WebGPUのバリデーションメッセージ
  は具体的で、原因の特定に直接役立つため
- **不透明な単色背景にした。** ADR-0005の`GLASS_SURFACE`（ぼかし+tint）を
  意図的に使わなかった。背景が真っ黒なときも点群の上に出たときも確実に
  読める必要があり、半透明はどちらの条件でも「背景次第で読みにくくなる」
  リスクを持ち込む。これはこのバナーが存在する理由そのものと矛盾する
- **`z-50`で全パネル・設定モーダル(`z-30`)より前面に置いた。** どんな状態
  でも隠れないようにするため
- **複数出ても最初のエラーを消さない。** 置き換えではなく縦に積む
  （`overflow-y-auto`で画面からはみ出す分はスクロール）。消えるのは
  ユーザが閉じたときだけ
- 通常UIのライト/ダーク追従からも意図的に外し、警告色（赤系）に固定した。
  エラーであることが一目で分かることを、テーマの統一感より優先した

## 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 既存の`LayerPanel`のエラー表示（`viewer.error`、赤文字）に混ぜる | パネルが畳まれていると見えない。1件しか保持できず、複数のエラーが出ると最初のエラーが上書きされて消える。半透明なガラス面の上にあるため、点群の上では読みにくくなりうる |
| トースト通知ライブラリを導入する | 依存が増える。要件（本文そのまま・複数保持・不透明・閉じられる）は自前の小さいコンポーネントで満たせる。所有者が実装を追える単純さを優先した |
| `onuncapturederror`だけで初期化のエラーも拾う | どの生成が失敗したか分からない。EDLの事故の再発時に「点群かEDLか」の切り分けに再び時間がかかる |

## 検証について（正直に）

**この仕組み自体が正しく動くこと（実際にバリデーションエラーが起きたときに
バナーが出ること）は、GUIを目視できないため確認していない。** 確認済み・
未確認を以下に分ける。

**確認済み（機械的に）:**

- `GpuErrorLog`の蓄積・重複抑制ロジックは`gpu-error-log.test.ts`で
  vitestから直接検証した（WebGPUに依存しないため、GPUが無い環境でも
  確認できる）
- `npm run typecheck` / `npm run lint` / `npm test` / `npm run build` が
  成功することを確認した（下記「実行結果」参照）

**未確認（GUIを持たないエージェントの限界。所有者の実機確認が必要）:**

- `device.onuncapturederror`が実際に発火し、メッセージがバナーに表示されるか
- `pushErrorScope`/`popErrorScope`が実際に効き、「どの生成が失敗したか」が
  メッセージに含まれるか
- バナーが実際に不透明に見え、黒背景・点群の上のどちらでも読めるか
- バナーの「閉じる」ボタンが実際に機能するか
- `device.lost`の経路（GPUのリセット等）は人為的に発生させるのが難しく、
  今回は動作確認の手順を用意していない

## 自分で確かめる手順

以下は「わざとエラーを起こしてバナーが出ることを確認する手順」。
`npm run tauri dev`で実行しながら試すこと。

### 手順1: 初期化時のバリデーションエラー（pushErrorScopeの経路を確認する）

1. `src/renderer/point-cloud-renderer.ts`の`init()`内、点群パイプラインの
   生成箇所にある

   ```ts
   depthStencil: { format: DEPTH_FORMAT, depthWriteEnabled: true, depthCompare: "less" },
   ```

   の行を一時的にコメントアウトする（EDLの事故と同じ種類の不具合を
   意図的に作る）。
2. `npm run tauri dev`を実行し、アプリを開く。
3. **期待される結果:** 画面右上あたりに赤いバナーが表示され、
   「点群パイプラインの生成でバリデーションエラー: 」に続けて、
   WebGPU実装が返す具体的なメッセージ（パイプラインの深度アタッチメントと
   レンダーパスの互換性に関する内容のはず）が表示される。
4. バナー右上の「✕」でエラーが個別に閉じられることを確認する。
5. 確認後、コメントアウトした行を必ず元に戻すこと。

### 手順2: 実行時のバリデーションエラー・連投抑制（onuncapturederrorの経路を確認する）

1. `src/renderer/edl.ts`の`init()`内、`depthStencil: { ... }`の行を
   一時的にコメントアウトする（EDLの実機事故そのものの再現）。
2. `npm run tauri dev`を実行し、COPCファイルを1つ開く（点群がロードされ、
   毎フレーム`drawFrame()`が呼ばれる状態にする）。
3. **期待される結果:** 画面が真っ黒になり（今回の仕組みを入れる前と同じ
   症状）、同時に赤いバナーが表示される。バナーのタイトルに
   「（同じエラーが N 回発生）」という表示が出て、Nが時間とともに
   増えていくこと（＝同じメッセージが毎フレーム連投されているが、
   エントリは1件のまま件数だけが増えている＝連投が抑制されている）を
   確認する。
4. devtoolsのコンソールも合わせて確認し、同じメッセージが1行ごとに
   延々と出力され続けていないこと（`console.error`自体は毎回呼んでいるが、
   バナー側の集約とは別の話なので、コンソールの見え方は連投抑制の
   確認には使わない。バナーのカウント表示だけで判断すること）。
5. 確認後、コメントアウトした行を必ず元に戻すこと。

### 手順3: 複数のエラーが同時に出た場合に最初のエラーが隠れないこと

1. 手順1と手順2を同時に行う（点群パイプラインとEDLの両方から
   `depthStencil`を外す）。
2. **期待される結果:** 2種類のメッセージがバナーに縦に並んで両方表示され、
   どちらか一方が消えたり上書きされたりしないこと。

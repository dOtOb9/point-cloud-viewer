# ADR-0006: LAS/LAZ から COPC への変換方式

- 状態: 採択
- 日付: 2026-09-24
- 根拠: [M4-1 / M4-1b の実測](./M4-import-and-conversion.md)

## 決定

**LAS/LAZ → COPC の変換には `copc-writer` クレート（`convert_las_to_copc_streaming`）を使う。**
自前の octree ビルダは書かず、untwine / PDAL も同梱しない。

- 変換は `pcv-core` の外（`crates/pcv-convert`）に置く。`pcv-core` は wasm32 でビルドできる状態を保つ（規約1）
- **変換はデスクトップ・Android・Web のすべてで行う**（2026-09-24 に所有者の方針で改めた。下の「追記」参照）。
  デスクトップと Android は M4-3、Web は M4-6 で扱う
- 変換の一時ファイルはファイルサイズの数倍になるため、M4-3 で空き容量を事前に確かめる

## 背景

COPC を内部形式にしたことで octree 構築は実行時から消えたが、変換側に移っただけである
（[ADR-0001](./ADR-0001-architecture.md) の追記）。現実のデータの大半は生の LAS/LAZ なので、
どこかで数億点の octree を組む必要がある。このプロジェクトの前提は「数億点で破綻しないこと」。

### 実測（開発機: Core i5-14600K / RAM 31.8GB / Windows 11）

**M4-1: 素朴な実装（全点をメモリに載せる。`crates/pcv-convert` の本体）**

| 入力 | 点数 | 時間 | ピークメモリ |
|---|---|---|---|
| autzen | 10,653,336 | 8.98秒 | 0.761GB |
| beer.laz | 66,848,096 | 58.3秒 | 4.116GB |

ピークメモリは点数にほぼ比例する（約62バイト/点）。**sofi（3.64億点）なら約22GB**（計算上。
実測していない）となり、所有者の実データを変換できない。

**M4-1b: `copc-writer` の out-of-core 変換**

| 入力 | 点数 | 時間 | プライベートメモリのピーク | ワーキングセットのピーク |
|---|---|---|---|---|
| beer.laz | 66,848,096 | 171〜190秒（コーディネーター、2回） | **0.021GiB** | 3.07GiB |
| sofi.copc.laz | 364,384,576 | **1,079秒（18.0分）**（コーディネーター） | **0.053GiB** | 17.3GiB |

出力は `pcv-core` で開け、hierarchy の点数の合計が入力と一致し、ノードを読めた（両方）。

### 判断表への当てはめ

M4-1b の基準は測る前に決めた:「sofi が 30分以内かつピークメモリ 8GB 以内、出力が正しく、
ライセンスが両立 → 採用」。**18.0分・0.053GiB・出力正常・ライセンス両立なので1行目に入る。**

### 「ピークメモリ」を測り直した理由

M4-1b の最初の計測（エージェント）はワーキングセットで測り、sofi で 18.6GB と基準を超えた。
しかし `copc-writer` は一時ファイルを `memmap2` でメモリマップして読むため、ワーキングセットには
**ファイルに裏付けられたページ**が大量に入る。これはメモリが足りなくなれば OS が捨てて読み直せるので、
**メモリ不足で落ちる原因にならない**。RAM の多い開発機では捨てずに置いてあるだけである。

基準の「8GB」が守りたかったのは「メモリが足りずに落ちないこと」なので、指標を
**プライベートメモリ（ファイルに裏付けられていないメモリ）**に正した。基準の値は変えていない。
測ってから指標を選び直すことは、都合よく解釈する危険と紙一重なので、理由をここに残す。

### 計測値の食い違い（未解決）

エージェントの計測では beer.laz が 46.27秒・sofi が 553.81秒だった。コーディネーターの再計測は
beer.laz が 171〜190秒（約4倍）、sofi が 1,079秒（約2倍）で、比がそろっていない。
Defender のリアルタイム保護（有効）が一時ファイルを検査している可能性などが考えられるが、
**原因は突き止めていない**。判断には遅い側（コーディネーター）の値を使い、それでも基準に収まる。

## 帰結

### 得るもの

- 数億点を、プライベートメモリ数十MBで変換できる。メモリの少ない PC でも落ちにくい
- 純粋な Rust で、読み込み（`copc-core` / `copc-reader`、[ADR-0003](./ADR-0003-copc-crate.md)）と同じ系列。
  `las` / `laz` の版がそろっていて衝突しない（`copc-rs` はここで失敗した）
- 外部バイナリを同梱しないので、インストーラが大きくならず、ライセンスの確認も Rust の依存だけで済む
  （`copc-writer` / `copc-core` / `memmap2` / `tempfile` は MIT OR Apache-2.0、`las` は MIT、`laz` は Apache-2.0）

### 払うもの

- **一時ディスクを大量に使う。** sofi で約21.9GB（入力 2.0GB の約11倍）。変換前に空き容量を確かめ、
  一時ファイルの置き場所を選べるようにする（M4-3）
- **時間はかかる。** 3.64億点で約18分。進捗の表示とキャンセルが欠かせない（M4-3 の要件どおり）。
  `copc-writer` が進捗の通知と中断に対応しているかは未確認。対応していなければ、変換を別プロセスで
  走らせて中断はプロセスを止める形にする
- 変換の速さは外部のクレートの実装に依存する。遅さが問題になったら、まず原因（一時ファイルの I/O、
  Defender の検査など）を測ってから手を入れる
- ~~Android と Web では生の LAS/LAZ を開けない~~（追記で撤回。下を参照）

### 素朴な実装（M4-1）の扱い

`crates/pcv-convert` の素朴な実装は、計測の記録として残す。本番の変換経路には使わない。
M4-3 で `copc-writer` を使った経路を作るとき、不要になった部分は整理してよい。

## 却下した案

- **自前の素朴な実装**: 1億点までは速いが、ピークメモリが点数に比例し、sofi 級（数億点）を変換できない
- **自前の out-of-core 実装**: `copc-writer` が既に基準を満たしている。同じものを書く理由が無い
- **untwine / PDAL の同梱**: 外部バイナリが要り、インストーラが大きくなり、ライセンスと配布の確認が増える。
  Android と Web では動かない点は `copc-writer` と同じだが、それ以上の利点が無い

## 追記: Android と Web でも変換する（2026-09-24）

当初は「変換はデスクトップだけ」とした。所有者の方針で、**Android と Web でも変換できるようにする**ことになった。
`copc-writer` 0.9.0 のソースを読んで、それぞれ何が要るかを確かめた。

### 分かったこと

- **中断は最初から対応している。** `CancelCheck` トレイトと `*_with_cancel` 系の関数がある。
  そのため**別プロセスを立てずに、同じプロセスの中で変換して止められる**。Android はアプリが別プロセスで
  自分の実行ファイルを起動しにくいので、これが前提になる。デスクトップも同じ方式にそろえる
- **進捗の通知は無い。** ただし `write_streaming_with_cancel` は点のイテレータを受け取るので、イテレータを包んで
  読んだ点数を数えれば、読み込み段階の進捗は出せる
- `convert_las_to_copc_streaming_with_crs_wkt_override` があり、CRS の WKT を上書きできる
- 点の一時ファイルは `spill_dir` に作るが、**LOD の索引の一時ファイルは常に OS 既定の一時ディレクトリ**
  （`tempfile::Builder`、`std::env::temp_dir()`）に作られる。点の一時ファイルは `memmap2` でメモリマップして読む

### Android（M4-3 に含める）

- 入力は `content://` の URI から得た `File`（Read + Seek）を `las` で読み、イテレータとして
  `write_streaming_with_cancel` に渡す
- Android の `std::env::temp_dir()` はアプリから書けない場所を指すため、起動時に一時ディレクトリを
  アプリのキャッシュ領域に向ける
- 一時ファイルは入力の約11倍。タブレットでは容量が足りないことが多い見込みで、事前の空き容量の確認が特に重要
- タブレットの CPU での所要時間は**未計測**

### Web（M4-6 として別に扱う）

**`copc-writer` はそのままではブラウザで動かない。** 一時ファイルをファイルシステムに作り（`tempfile`）、
メモリマップして読む（`memmap2`）が、`wasm32-unknown-unknown` にはどちらの仕組みも無い。

見込みのある道筋: ブラウザの **OPFS（Origin Private File System）** は、Worker の中では同期的に読み書きできる
（`FileSystemSyncAccessHandle`）。`copc-writer` を `vendor/` に取り込み（`copc-reader` と同じ扱い。
[ADR-0003](./ADR-0003-copc-crate.md)）、一時ファイル・索引・出力の読み書きを差し替えられる形に改修して、
Web では OPFS を使う。**外部クレートに相応の改修が入る**うえ、ブラウザの保存容量の上限で大きなファイルは
変換できない場合がある。M4-3 が終わってから、まず実現できるかを確かめるスパイクから始める
（M4-3 の途中で `copc-writer` を差し替えると衝突するため）。

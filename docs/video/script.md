## 1. つかみ（0:00〜0:45）

**画面**: Windows 版で sofi（2.03GB・3.64億点）を開く。開いた直後は粗い全体像、すぐに細部が詰まっていく。カメラを回す・寄る

**字幕**: 2.03 GB / 364,384,576 points

> 2ギガバイト、3億6千万点の点群です。開くと、一瞬で全体が出て、見ている場所から細かくなっていきます。
> ブラウザでも、Windows でも、Android でも、同じものが動きます。
> この動画では、これをどういう仕組みで作ったのか、そしてどこでつまずいたのかを話します。

## 2. なぜ一瞬で開けるのか（0:45〜2:00）

**画面**: 図「COPC の中身」（ファイルの先頭にヘッダーと hierarchy、その後ろにノードごとの LAZ のかたまり。octree の木）

> 点群のファイル形式に COPC というものがあります。中身は普通の LAZ、圧縮された LAS ですが、点が octree の順に並んでいて、
> どのノードがファイルのどこにあるかの一覧、hierarchy が入っています。
> だから開くときに読むのは、ヘッダーとこの一覧だけです。点そのものは、まだ1つも読みません。

**画面**: 実測の表

| ファイル | 大きさ | 開く時間 | ピークメモリ |
|---|---|---|---|
| autzen | 78MB | 11.1ms | 9MB |
| sofi | 2.03GB | 32.0ms | 13MB |

（記録: `TaskSheets/M1-point-rendering.md`）

> ファイルが25倍になっても、開く時間とメモリはほとんど変わりません。
> 画面に出す点の数には上限、点予算を決めていて、300万点ぶんを読み込むのに転送したのは、78MBのファイルでも2GBのファイルでも、同じ約58メガバイトでした。
> 読む量は、ファイルの大きさではなく、画面に出す点の数で決まります。

## 3. どのノードを先に読むか（2:00〜3:30）

**画面**: 図「画面空間誤差」。ノードの点の間隔を画面に投影したピクセル数

> 次に、どのノードを先に細かくするか。基準は、そのノードの点と点の間隔が、画面上で何ピクセルに見えるかです。
> 間隔が大きく見えるほど粗いので、先に細かくします。

**画面**: 式の比較。旧: 画面上の大きさ × 体積 ÷ 点数 → 新: (体積 ÷ 点数)^(1/3) × ピクセル/ワールド単位

> 実は最初、この式を間違えていました。点の間隔を「体積 ÷ 点数」で測っていたんです。これは長さではなく、長さの3乗です。
> octree は1段深くなると体積が8分の1になるので、優先度が1段ごとに16分の1に落ちていました。
> 距離の効果は1乗しかないので、深い段は、画面のどこにあってもまず読まれない。
> 点予算300万点はノード約120個ぶんで、sofi のノードの98%を占める深い段は、事実上読まれていませんでした。
> 3乗根を取って長さに直したら、1段ごとの減り方は2分の1になり、距離とちょうど釣り合うようになりました。

（記録: `TaskSheets/ADR-0010-lod-priority-and-point-budget.md`）

**画面**: 中央優先度 0 と 4 を並べて、同じ視点で読み込み直す

> さらに、画面の中央からの距離で重みを掛けて、見ている場所から先に細かくするようにしています。
> 端が永久に後回しにならないよう、重みには下限があります。

## 4. 1つの Rust のコアが3つの形で動く（3:30〜5:00）

**画面**: 構成図（画面と描画は共通 → データの入口が2つ → Tauri の Rust ／ Web Worker の中の wasm → 共通の Rust の COPC 読み込み）

> 画面は React、描画は WebGPU です。ここは3つの形で共通です。違うのはデータをどこから読むかだけで、
> その違いはデータの入口の1つのファイルに閉じ込めています。CI でも、その約束が守られているかを機械的に検査しています。

> Windows と Android では、独自の URL `pcv://` で Rust にノードを頼みます。
> Rust 側は、ファイルを開いたリーダーを何本もプールしておき、並列に読みます。

> 面白いのはブラウザです。COPC を読む Rust のコードは、普通のファイルを同期で読む前提で書かれています。
> ブラウザのファイル API は非同期なので、そのままでは動きません。
> ところが Web Worker の中だけは、`FileReaderSync` や同期の XHR という同期の API が使えます。
> そこで、Rust のコードを wasm にして Worker の中で動かし、ファイルの必要な範囲だけを同期で読むようにしました。
> デスクトップとまったく同じ読み込みのコードが、書き直さずにブラウザで動いています。

（記録: `TaskSheets/ADR-0012-web-worker-sync-io.md`）

**画面**: 読み込みの速さの改善（並列数を上げても伸びなかった → 1ノードの読み方を直したら伸びた）

| | 1スレッド | 20スレッド |
|---|---|---|
| 直す前 | 11.3 ノード/秒 | 71.1 ノード/秒（8スレッドで頭打ち） |
| 直した後 | 110.7 ノード/秒 | 1,050.6 ノード/秒 |

（記録: `TaskSheets/ADR-0007-pcv-protocol-concurrency.md`）

> ここでも1つ失敗しています。読み込みが遅いので並列数を上げたら、8で頭打ちになりました。
> 原因は並列数ではなく、1つのノードを読むのに、その段全体を検索して大半を捨てていたことでした。
> hierarchy にはノードの位置が書いてあるので、そこへ直接飛べばよかった。直したら1ノードあたり10分の1になりました。
> 並列数という1つの軸だけを振って、1回あたりのコストを疑わなかったのが失敗です。

## 5. ブラウザで数億点を変換する（5:00〜6:30）

**画面**: Web 版で LAZ を選ぶ → 準備 → 読み込み中（点数が進む）→ 完了 → 段階ごとの内訳が出る → そのまま表示

> 実際のデータの多くは、COPC ではない普通の LAS や LAZ です。そこで、変換もできるようにしました。ブラウザの中だけで、です。

**画面**: 図「変換の流れ」（展開 → 一時ファイル → octree に分割 → ノードごとに圧縮 → COPC）

> 変換は、点を一度一時ファイルに書き出し、それを読み戻しながら octree に分けて、ノードごとに圧縮し直します。
> 大事にしたのは、メモリが点数に比例しないことです。最初に素朴に書いたものは、全点をメモリに載せていて、
> 3億点なら20ギガを超える計算でした。そこで、一時ファイルを使って少しずつ組み立てる方式にしました。
> 一時ファイルの置き場所は差し替えられるようにしてあって、デスクトップではディスク、ブラウザでは OPFS という
> ブラウザ専用のファイル領域を使います。

**画面**: 実測（デスクトップ）

| | 時間 | プライベートメモリのピーク |
|---|---|---|
| 3.64億点の PCD → COPC | 171秒 | 0.23GiB |

（記録: `TaskSheets/M4-import-and-conversion.md` の M4-9）

> デスクトップでは、3億6千万点を、メモリ0.23ギガで変換できます。
> LAZ の展開・octree の分割・圧縮は並列にしていて、それぞれ約5倍・2倍・4倍速くなりました。
> ブラウザ版はまだ1スレッドで、ネイティブよりかなり遅いです。どこに時間がかかっているかを、今測っているところです。

## 6. つまずき集（6:30〜8:00）

**画面**: Console を開き、該当の事例を図か再現で見せる（再現が難しいものは図とコミットの差分）

> 最後に、つまずいた話をいくつか。この開発は AI と一緒に進めたのですが、何度も同じ罠にはまりました。
> **テストも CI も全部緑なのに、実際には壊れている**、という罠です。

1. **画面が真っ黒**: 陰影の処理に使う WebGPU のパイプラインで、深度の設定を宣言し忘れていた。
   WebGPU ではそれだけでフレームの命令がまるごと捨てられる。エラーは実行時にしか出ないので、テストにも CI にも出なかった
2. **ノードが1つも読めない版を公開した**: `pcv://` の URL に `:` を入れたら、URL を作るときに `%3A` に変換され、
   Rust 側がそれを解析できなかった。テストは変換前の文字列しか使っていなかった
3. **ブラウザの変換が毎回失敗する**: 時間を測るために入れた `Instant::now()` が、ブラウザの wasm では panic する。
   ビルドは通る。実行して初めて出る

> どれも「部品は正しいけれど、つないで実際に動かすと壊れる」ものでした。
> 今は、実際のブラウザで変換を一通り流すテストを CI に入れています。

**画面**: f32 の NaN の図（大きな座標を f32 の行列に入れて桁落ち）

> 数値の話も1つ。UTM のような大きな座標を、そのまま32ビット浮動小数点の行列に入れると、桁が落ちて NaN が出ます。
> 点の座標は、ノードの原点からの相対座標で持つようにしています。

**画面**: vsync の図（フレーム間隔が16.7msの倍数に揃う）

> フレームの重さに合わせて点予算を自動で上げ下げする仕組みも、最初は動きませんでした。
> 60Hz の画面ではフレームの間隔が16.7ミリ秒にぴったり揃うので、「余裕があるから増やそう」という判断が、原理的に起きなかったんです。
